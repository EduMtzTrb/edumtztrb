## Filter semantics

Filter (narrows a known set) is kept structurally distinct from Lens (M3.10's route-based dimension, changes what body of content is being read) and Sort (order only, not implemented — `IndexModel.ts`'s ordering is fixed and deterministic). `FilterModel.ts`'s `applyFilterCriteria` only ever removes entries from an already-ordered `IndexResult`; it never reorders, widens, or mutates a record.

## Why plain links, not M2.6's `FilterToggle`/`RemovableFilter`

Audited both M2.6 controls before building anything: `FilterToggle` is a `<button aria-pressed>` requiring an `onClick` handler, and `RemovableFilter` requires an `onRemove` callback — both assume client-managed state. This task's own §E3 states a clear preference: "prefer native/shareable URL state... query parameters are a strong default because they support refresh, direct linking, browser history, later Return restoration, accessibility, no hidden app-only state." A criterion living only in client component state would satisfy none of those. Reusing `FilterToggle`'s button shape unmodified would also have been ARIA-incorrect for a link-based control — `aria-pressed` is only valid on `role="button"`, not `role="link"`.

**Decision**: filter options and removal/reset controls are plain `next/link`s to precomputed URLs, using the exact same `aria-current="true"` idiom `GlobalNav`/`DistrictNav`/`Breadcrumb` (M3.7–M3.9) already use for "this link represents where you already are" — one consistent navigation idiom across the whole M3-B batch, zero JavaScript required for filtering to function at all, full refresh/direct-link/back-button correctness by construction. `ActionLink` (M2.5) is reused directly for the Remove/Reset controls. This is a considered architectural substitution, not an unreviewed skip of M2.6 — recorded here per this task's own instruction to document any deviation.

## Filter model

`src/domain/records/FilterModel.ts` — pure functions only:

- **`parseFilterCriteria(searchParams)`** — reads exactly two known keys (`district`, `contentType`); every other parameter (`fixture`, a future `q`) is ignored here and left untouched by every href builder.
- **`isFilterActive(criteria)`** / **`activeCriteriaEntries(criteria)`** / **`describeCriteria(criteria)`** — visible-state derivation.
- **`applyFilterCriteria(entries, criteria)`** — combinable (AND) narrowing over an already-resolved `IndexResult`'s entries.
- **`distinctDistricts(entries)`** / **`distinctContentTypes(entries)`** — filter *options* are derived from what's actually present in the current (already lens-scoped) view, never a hardcoded global list — this task's own §E2: "only expose filters useful to the current view."
- **`buildToggleHref` / `buildRemoveHref` / `buildResetHref`** — pure URL construction from the current pathname + raw `searchParams`, always preserving every non-filter parameter untouched (verified directly: the `fixture` flag survives every filter operation).

## Visible active state

`FilterBar` marks the currently-selected option `aria-current="true"` plus the same non-color visual cue (underline removed, weight increased) every other navigation system in this repository uses. `ActiveFilters` renders one chip per active criterion (label + a real "Remove" link) whenever any filter is active, and renders nothing otherwise — never a stray empty region (tested directly).

## Reset

`ActiveFilters`' "Reset filters" link uses `buildResetHref`, which strips only the two known filter keys and preserves everything else (e.g. `fixture`) — tested directly. Reset restores the full (lens-scoped) result set, keeps the visitor on the same utility route, and remains a native, keyboard-reachable link — this task's own §E5 checklist met exactly.

## Persistence

Filter state lives entirely in the URL query string — no client-only store, no canonical-record mutation, no encoding into a canonical route (M3.3's routes remain untouched by any filter operation, verified directly against `resolveCanonicalRoute`). This is real, working persistence: refreshing, sharing, or reopening a filtered `/index?district=work` URL reproduces the exact same view.

## Intentional recomposition

`IndexResults` (M3.10, reused unchanged in shape) re-renders the filtered entry list directly — no arbitrary hole is left where a filtered-out row used to be; the list reflows as a normal DOM list update. No motion was added (none is required — this task's own instruction: "static recomposition must work now").

## Corrected M3.10 defect: empty vs. no-result state selection

While wiring Filters into `/index`, an M3.10 defect was found: `IndexResults`' empty-state branch decided between `EmptyState` ("nothing exists") and `NoResultState` ("no match for this scope") using `result.lens` alone. A filter-narrowed-to-zero result on `/index` (no lens, but a filter active) has no `lens`, so it would have incorrectly rendered `EmptyState`'s "no public records exist yet" even though the underlying fixture source was non-empty and simply didn't match the filter. **Fixed**: `IndexResults` now accepts an explicit `scopeDescription?: string` prop; its presence (from either a lens route or an active filter) selects `NoResultState`, its absence selects `EmptyState`. All five M3.10 lens routes were updated to pass their own scope description explicitly (previously implicit via `result.lens`); their existing M3.10 tests continue to pass unchanged, and a new test proves the previously-incorrect filter case now renders `NoResultState` correctly, plus a new explicit test proves the genuinely-empty (no filter, no fixture) case still renders `EmptyState`. No canonical/domain logic was affected — this was a presentation-layer branch condition only.
