## Resolver architecture

One centralized module, `src/domain/records/RouteResolver.ts`, exporting:

- `resolveCanonicalRoute(record)` — pure function, identity fields in, one `CanonicalRoute` (a branded string) out.
- `buildCanonicalRouteRegistry(records)` — the registry-level mirror, throwing on the first duplicate canonical route across a record set.
- `RESERVED_ROUTE_SEGMENTS` — the reserved-segment table (see below).

No route-building logic exists in any component, district page, Search, Index, or filter code — there is no such code yet to contain it, and this module is the single place it will live once one exists.

## Canonical route law

`resolveCanonicalRoute` reads **only** `ownerDistrict`, `slug`, and `contentType` (the last only to validate About's special case, below) — nothing else on a record can influence the resolved route. This is a structural guarantee, not merely an observed behavior: `route-resolver-source-contract.test.ts` inspects the function body's own source text and asserts it never references `record.visibility`, `record.lifecycle`, `record.curatorialInclusion`, `record.disciplines`, `record.themes`, `record.featured`, `record.editorial`, or `record.date`. `RouteResolver.test.ts`'s "Temporary context never changes canonical route" suite additionally proves this behaviorally, for every one of those fields, plus Lab's success/failure state and Products' availability specifically (this task's own explicit examples).

## About route handling

About's approved route family (IA §11.8 / `PLATFORM_SPECIFICATION.md` §5.8) is a small **fixed** set of named routes — `/about`, `/about/profile`, `/about/practice`, `/about/experience`, `/about/education`, `/about/capabilities`, `/about/recognition`, `/about/current-focus`, `/contact`. There is no approved generic `/about/{entry}` anywhere in either authoritative document, and none exists in the live route tree (confirmed directly). Per this task's own instruction (§B3): "If this creates a genuine unresolved contradiction with M3.1's current generic slug model: STOP and report it rather than silently inventing `/about/{slug}`." This was audited carefully rather than assumed, and resolves as follows — **not a contradiction requiring a stop**, for three independent, converging reasons:

1. `INFORMATION_ARCHITECTURE.md` §13.3's approved 17-value content-type vocabulary contains exactly **one** About-flavored entry — "Profile Record." There is no "Experience Record," "Credential Record," or similar in the approved vocabulary, meaning IA itself does not contemplate multiple independently-routed canonical About record shapes.
2. M3.2's `AboutExtension` (this task's own prior phase) already resolved the underlying data-modeling question by nesting Experience, Education, and Value as **typed arrays inside one record's extension**, not as separate canonical records each carrying their own `id`/`slug`. That decision was made on M3.2's own terms (avoiding overbuilding relative to "smallest coherent architecture") and turns out to directly determine M3.3's answer: there is only one About canonical-record shape to route.
3. Both source documents explicitly anticipate this. About Universe §7: "these layers may live as one continuous district or as linked internal views." `PLATFORM_SPECIFICATION.md` §5.8: "the implementation may use in-page sections where separate routes add no meaningful independent value... provided... the approved public hierarchy remain[s] intact."

**Resolution:** an About-owned record with `contentType: "profile-record"` always resolves to the one fixed route `/about/profile` (About Universe §8's own "Entrance: Position"), regardless of its own `slug` value — `RouteResolver.test.ts` proves this directly ("About route ignores the record's own slug entirely"). The other six named About routes are approved **section views** over that same one record, never independent canonical-record destinations — consistent with how `/work/selected` and `/work/all` are curated/comprehensive *views* over Work records without being canonical routes themselves. If an About-owned record ever carries a content type other than `"profile-record"`, `resolveCanonicalRoute` throws explicitly rather than guessing a route for it (`RouteResolver.test.ts`: "throws for an About record with an unrecognized content type rather than guessing a route") — surfacing any future genuine gap instead of silently inventing a slug-based path.

**Consequence, tested directly:** because every About record resolves to the same fixed route, a *second* About-owned record is a genuine duplicate-route error — `buildCanonicalRouteRegistry` rejects it (`RouteResolver.test.ts`: "rejects two About records"). This is the correct behavior for the current single-person model; the platform's own documented future evolution toward multi-author/studio (About Universe §23) is explicitly out of this package's scope — see "Deferred items."

## Reserved segments

Each slug-routed district's own static sibling route names (IA §11.3–§11.7 / `PLATFORM_SPECIFICATION.md` §5.3–§5.7, reproduced verbatim) are protected:

| District | Reserved segments |
|---|---|
| Work | `selected`, `all`, `practice`, `collections` |
| Research | `current`, `themes`, `publications`, `writing`, `talks`, `archive` |
| Lab | `active`, `prototypes`, `tools`, `studies`, `archive` |
| Art | `selected`, `series`, `medium`, `exhibitions`, `archive` |
| Products | `featured`, `collections`, `digital`, `physical`, `services`, `archive` |

A canonical slug equal to any of these would be unreachable in practice — Next.js's App Router resolves the static sibling route (e.g. `/work/selected`) ahead of the dynamic `[entry]` segment — so `resolveCanonicalRoute` **rejects** the collision explicitly with a thrown error naming the exact reserved word, rather than silently resolving it (e.g. by appending a number), per this task's own explicit instruction. Tested directly for Work and Research; the same mechanism (one shared function, one shared table) covers Lab/Art/Products identically.

## Route collision handling

`buildCanonicalRouteRegistry` throws on the first duplicate canonical route across a record set — the registry-level mirror of the per-record reserved-segment check. Two records in *different* districts never collide, since the district name is always the route's first segment (tested: identical slug `"shared-slug"` under `work` and `art` produces two distinct, valid routes). Two About-owned records always collide (see above). Duplicate collisions are never silently resolved by appending a suffix — the error is explicit and names both colliding record IDs.

## Route identity versus public-delivery authorization

`resolveCanonicalRoute` never reads `visibility` or `curatorialInclusion` — a private, excluded record still receives a well-defined canonical route (`RouteResolver.test.ts`: "a private, excluded record still has a well-defined canonical route"). This is deliberate: route *identity* and delivery *authorization* are kept as two fully separate operations, exactly as this task requires. Delivery eligibility remains owned entirely by M3.1's `isPubliclyDiscoverable`/`isDirectlyAccessible` (`registry.ts`) — untouched by this package, and exercised in the same test file to prove the two functions compose rather than overlap. This module does not become, and must never become, the public-delivery security boundary M3.1 already documented (`registry.ts`'s own doc comments on the "fetch everything then filter client-side" anti-pattern) — a real future query layer must still apply `isPubliclyDiscoverable`/`isDirectlyAccessible` at the query level; this resolver only ever answers "what is this record's address," never "who may load it."

## Archive route invariance

An archived record (`lifecycle: "archived"`) keeps its plain `/work/{slug}` route — never `/work/archive/{slug}` — tested directly. Archive is a lifecycle state (M3.1), not a route segment; the `/work/archive`, `/research/archive`, `/lab/archive`, `/art/archive`, and `/products/archive` routes are comprehensive-archive *views* that list/link to existing canonical routes, never a distinct namespace a record's own identity moves into.

## Grouping/lens/filter boundary

`resolveCanonicalRoute` never returns a bare reserved-segment path (e.g. `/work/selected`) for an actual record, and never returns anything under `/index` — tested directly for every fixture. Collection, series, territory, family, practice-area, and theme membership (M3.4's eventual territory) play no role in route resolution at all, since the resolver never reads any classification-shaped field in the first place.

## Relationship-resolution boundary

Relationships (M3.1) continue to reference record IDs, never copied URLs — unchanged by this package. `route-resolver-source-contract.test.ts` confirms `RouteResolver.ts` never references `relationships` at all. A future consumer wanting a relationship target's route calls `resolveCanonicalRoute(registry.get(targetId))` rather than any stored URL — the two concerns (identity reference vs. resolved address) stay composed, not merged.

## Direct-entry boundary

A resolved `CanonicalRoute` is a plain, JSON-serializable string, independent of any navigation history, session, or prior page — tested directly. This package deliberately does not build breadcrumbs, Return, or orientation state (`IMPLEMENTATION_PLAN.md` §7's own M3.13, "Direct-entry orientation," is a separate later package) — it only guarantees the stable identity those later features will resolve against.
