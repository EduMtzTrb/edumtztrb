## Architecture

Three independent components, no forced shared base: `TextField` (native `<input>`), `TextAreaField` (native `<textarea>`), `FormConfirmation` (the confirmation-hook slot). `TextField`/`TextAreaField` share the same *anatomy* (label, guidance, required marker, error, disabled) but not a shared implementation component — the two wrap genuinely different native elements, and the amount of real shared logic (a few lines of id-generation and `aria-describedby` composition) is small enough that duplicating it matches this project's own established "duplication over premature abstraction" precedent (explicitly defended in the M2.7 and M2.8 reports for their own record/media families).

**No `<Form>` wrapper was built.** A native `<form>` already is the correct primitive; wrapping it would add no capability this package's own parts don't already provide, and this task's own §D22 only asked for one "if implemented" — it wasn't, deliberately. **No `FormFieldGroup` component was built** either: a plain native `<fieldset><legend>` (the same primitive `RadioGroup` already uses) is sufficient for grouping several `TextField`s, and inventing a component around it would add no real capability. Both omissions are documented decisions, not gaps.

## Form Anatomy

Both `TextField` and `TextAreaField` render the same structure: a real `<label htmlFor>` (always visible, always persistent — never hidden or replaced by `placeholder`), an optional `<p>` guidance line, the native control itself (with `aria-describedby` composed from whichever of guidance/error IDs actually exist), and an optional error `<p role="alert">`. `className`/`id`/all other native props pass straight through via prop spreading, so nothing about native `<input>`/`<textarea>` behavior is hidden or reimplemented.

## Persistent Labels

`label: string` is a required prop on both components — there is no way to render either without a real, visible, natively-associated `<label>`. Protected by test (`getByRole("textbox", { name: ... })`, which only succeeds when the accessible name genuinely comes from a real label association, not from `placeholder` or `aria-label` alone).

## Placeholder Rule

`placeholder` passes through as an ordinary native `<input>`/`<textarea>` attribute — nothing in either component gives it any special treatment, and no CSS in `form.css` styles `::placeholder` at all (asserted by contract test: "no `::placeholder` rule exists"). `label` and `placeholder` can coexist; `placeholder` never substitutes for `label`, and there is no floating-label mechanic anywhere in this package.

## Guidance

Optional `guidance: ReactNode` renders as its own `<p id="{fieldId}-guidance">`, referenced by the control's `aria-describedby`. Guidance is a plain, always-visible line (`.form-guidance`, `--color-mist-300`) — distinct from both `placeholder` (which it isn't) and metadata (M2.9, which it also isn't — guidance describes how to fill in the field, not a structured fact about a record).

## Required State

Native `required` passes straight through (implying the browser's own `aria-required` semantics — nothing duplicated). When `required` is true, an explicit, always-visible text marker — literally the words `"(required)"`, not a bare asterisk — renders next to the label. This directly implements this task's own explicit warning: a marker "must be understandable, must not rely on red color only, must not become decorative punctuation with unclear meaning." An unadorned `*` character was deliberately rejected for exactly that reason. Optional fields never show the marker (protected by test).

## Focus

`.text-field:focus-visible`/`.textarea-field:focus-visible` reuse the shared shell outline **byte-for-byte** (verified by string-equality assertion in `form-contract.test.ts`, the same technique every prior M2 control package uses) — no form-specific focus color, nothing new.

## Errors

`error: ReactNode`, when supplied, sets `aria-invalid="true"` on the control and renders a real `<p role="alert">` containing the actual error text, associated via `aria-describedby`. This is deliberately **more than a red border**: the border-color change (`.text-field[aria-invalid="true"]`, `--color-error`) is one signal, but the structural presence of the error paragraph — and its `aria-invalid`/`role="alert"` programmatic exposure — carries the actual meaning, not the color alone. Rendering an error never clears or replaces the field's own value (protected by test: a `TextField` with both a `defaultValue` and an `error` keeps that value).

## Error Explanation

The error text itself is always consumer-supplied — no vague generated `"Invalid input"` default exists anywhere in either component. `TextField`/`TextAreaField` render exactly the `ReactNode` a consumer passes as `error`; this package invents no domain validation copy (see **Domain Validation Boundary**).

## Disabled State

Native `disabled` passes through; `.text-field:disabled`/`.textarea-field:disabled` reuse `--opacity-disabled` (M2.5, already resolved) plus `cursor: not-allowed` — the same disabled model every prior control package already uses, not a second one.

## Confirmation Hooks

`FormConfirmation` is the entire realization of this task's own "confirmation hooks" (not "the whole confirmation-state system") requirement: a `<p role="status" aria-live="polite">` slot a consumer renders conditionally once a real submission genuinely succeeds. It carries no icon, no success animation, no color-coded box beyond reusing the already-resolved `--color-success` text color, and it does not decide *when* to appear, *whether* to clear the form, or *where* to navigate next — all of that stays the consumer's decision, per this task's own explicit instruction not to decide that globally. It is absent from the DOM entirely unless a consumer renders it (protected by test).

## M2.5 Submit Integration

`Action.tsx` (M2.5) is extended with an optional `type?: "button" | "submit"` prop, defaulting to `"button"` — every existing call site (including M2.6's `RemovableFilter`) is completely unaffected, confirmed by the full test suite still passing unchanged plus a new dedicated test (`Action.test.tsx`: `"supports type=submit for real form submission"`). `"reset"` was deliberately not added — nothing has asked for it, and adding it speculatively would repeat exactly the mistake M2.5's own original docstring warned against. This is documented in `Action.tsx`'s own comment as a legitimate, narrow, first-genuine-consumer extension: M2.10 is that consumer, and the extension preserves M2.5's full visual hierarchy (Primary/Secondary/Tertiary), disabled/loading semantics, and focus behavior for a submit action exactly as for any other `Action` — no second button visual language was created.

## M2.6 Selection-Control Integration

`Select` and `Checkbox` needed **zero changes** — both already spread arbitrary native props (including `required`/`aria-describedby`/`aria-invalid`) onto their underlying native element, confirmed by `ControlIntegration.test.tsx` rendering both inside a real `<form>` alongside `TextField` and a submit `Action`. `RadioGroup` was deliberately **not** extended: this package's own deliverables (`TextField`/`TextAreaField`/`FormConfirmation`) never needed a `RadioGroup`-level guidance/error hook to function, so adding one now would be exactly the speculative, ahead-of-a-real-consumer extension this project has consistently avoided (the same discipline `Action.tsx`'s own original docstring modeled). `RadioGroup` is demonstrated working correctly, unmodified, inside a real form in the same integration test. A future consumer that genuinely needs group-level error association on `RadioGroup` can add a minimal `describedBy` prop then, following the exact precedent this package's own `Action` extension sets.

## M2.11 Boundary

Not implemented, correctly: the full shared static-state family (loading, empty, sparse, no-result, unavailable, archived, error, success, confirmation, restricted/unpublished as a unified system). `FormConfirmation` covers only the narrow "confirmation hook" this task's own scope explicitly names — it is not a generic Success/Confirmation state component, has no variant prop, and makes no attempt to also cover the other nine M2.11 states.

## Domain Validation Boundary

Not implemented, correctly: email format policy, password policy, checkout/quantity/eligibility rules, or any validation engine. `error`/`required` are plain props a consumer supplies from whatever validation logic it already has (native browser validation via `required`/`type="email"`/etc. remains available and untouched); `TextField`/`TextAreaField` never inspect or judge the value themselves.

## Typography / Geometry / Surfaces

`.form-label` uses `.type-label` (M2.2, the same role M2.6's own field/control labels already use); `.form-guidance`/`.form-error`/`.form-confirmation` use `.type-body-small`; the control text itself uses `.type-body`. No new role, no forced uppercase, no default Mono (asserted by contract test). Geometry reuses `--radius-control` (already-approved, 2px) — no pill, no giant radius. No field is wrapped in `.plane`/`.frame`/a card — `form.css` contains no such reference (asserted by contract test); a bordered `.text-field`/`.textarea-field` box is the input's own necessary affordance, not a decorative container around it.

## Responsive Behavior

`.text-field`/`.textarea-field` are `width: 100%` with no fixed pixel width anywhere in `form.css`, so fields naturally fill whatever width their container provides at any of the task's named widths (~390/768/1024/1440–1600px) without a breakpoint override. No side-by-side field layout exists in this package (no `FormFieldGroup`/grid was built), so there is no "two fields becoming unusably narrow" case to guard against — a future consumer that lays out fields side-by-side owns that composition decision and its own responsive behavior.

## 200% Zoom / Reflow

No fixed-height container, no `overflow: hidden`, and no viewport-locked value exists anywhere in `form.css` — labels, guidance, and error text all wrap in normal block flow, and `.textarea-field`'s `resize: vertical` lets a user manually grow it if content still doesn't fit. Real 200%-zoom verification in an actual browser is deferred to the human visual round, same posture as every prior M2 package.

## Accessibility

- **Label association:** every field has a real, natively-associated `<label>` — verified via `getByRole` name-based queries, which only succeed on genuine association.
- **Required semantics:** native `required` (implies native `aria-required`) plus the explicit visible `"(required)"` text marker — never color-only, never a bare unexplained glyph.
- **Guidance/error association:** both composed into one `aria-describedby` value (space-separated when both exist), verified by test resolving the referenced element(s) by ID.
- **`aria-invalid`:** set exactly when `error` is supplied, cleared otherwise.
- **Disabled:** native `disabled` — automatically removes the control from the tab order and blocks interaction, no separate ARIA state needed.
- **Keyboard operation:** fully native (`<input>`/`<textarea>`/`<button type="submit">`) — nothing here intercepts or reimplements keyboard behavior.
- **Focus-visible:** byte-identical to the shared mechanism (see **Focus** above).
- **No placeholder-as-label:** confirmed structurally (label and placeholder are always two separate things) and by test.
- **No color-only state:** required uses text, error uses a real text paragraph plus `aria-invalid` plus border color (three channels, not one).
- **No motion dependency:** nothing in this package uses `transition`/`animation` (asserted by contract test).
