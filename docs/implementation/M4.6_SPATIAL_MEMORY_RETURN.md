## Starting-state audit

No spatial-memory, Return, or session-storage-backed persistence existed anywhere in the repository before this package. `src/lib/return/` did not exist.

## Return is not Back

Three concepts are kept structurally distinct, per this task's own explicit §C1:

- **Close** — M4.5's `Overlay.onClose`: ends the current Focus/overlay state, nothing more.
- **Back** — native browser history, completely untouched by this package (`returnMemory.ts` never calls `history.back()`, `pushState`, or `replaceState` — confirmed by source contract). M4.7 verifies Back/Forward integration.
- **Return** — this package: restores a *known, previously captured* context. It is a data-lookup-and-apply operation, not a history navigation.

`returnMemory.ts` contains zero calls into the History API in either direction — it neither reads nor writes browser history state.

## No fabricated history

`retrieveReturnContext(key)` returns `null` when nothing was ever captured under that key — the direct-entry / cold-open case. Tested directly: a fresh render of the fixture, before any capture, correctly reports "nothing to return to" rather than inventing a plausible-looking prior context. This is the same honesty boundary M3.13's `DirectEntryOrientation` already established for structural orientation — Return is an *additional*, optional enhancement on top of that, never a replacement that could regress it.

## Return state model

`ReturnContext` (`src/lib/return/returnMemory.ts`) is the entire model — one flat, JSON-serializable interface covering every field this task's own list names: `originUrl` (route + full query string), `parentDistrict`, `selectedRecordId`, `resultKey`, `scrollY`, `originControlKey`, `comparisonState`, `galleryPosition`, `expandedIds`, plus `capturedAt` (informational only). Every field is a string, number, boolean, or plain array/object of those — no function, no React node, no DOM element, no class instance. A round-trip test (`JSON.parse(JSON.stringify(restored))` equals `restored`) proves this directly rather than merely asserting the type.

## No duplicate filter/lens store

`originUrl` (query string included) is the *only* place filter/lens state lives in this model — there is no separate `filters`/`criteria` field (confirmed by source contract and by a dedicated test capturing a URL with two query parameters and confirming both survive inside `originUrl` alone). This directly follows this task's own §C4 instruction: M3.11 already makes the URL the authoritative filter/lens store; a second one here would let the two drift.

## No canonical-record duplication

`selectedRecordId` is a string identifier only. `returnMemory.ts` never imports anything from `src/domain/records/` (confirmed by source contract) — a full record is never captured, only its ID, exactly mirroring the discipline `RelationshipModel.ts` already used for cross-record references.

## Origin references — the same-document/cross-route boundary, resolved

M4.4 and M4.5 both deliberately kept `origin` as a live, same-document `HTMLElement` reference and explicitly deferred "what happens across a real navigation" to this package. M4.6 resolves it: `originControlKey` is a plain string stored in `ReturnContext`; `findElementByReturnKey(key)` resolves it back to a live element via `document.querySelector('[data-return-origin-key="..."]')` on demand, after a real or simulated navigation. A missing key — because the element never existed after the layout changed, or genuinely doesn't exist yet — resolves to `null` without throwing (tested directly), never a stale/detached-node `.focus()` call. `restoreFocusByKey` builds on this and returns whether it actually succeeded, so a consumer can degrade gracefully (the fixture falls back to leaving focus wherever it already is).

## Storage lifetime

`sessionStorage`, not `localStorage` — confirmed both behaviorally (a test spies on `localStorage.setItem` and proves it is never called) and by source contract (the literal string `localStorage` does not appear anywhere in the module). This is genuinely session-scoped browser storage, cleared when the tab closes, matching this task's own §C6 instruction ("the expected behavior is session navigation context, not permanent user profile state") without needing any manual expiry logic — the browser already provides exactly the right lifetime semantics for free.

## Scroll restoration

Native scrolling remains untouched: `history.scrollRestoration` is never referenced anywhere in this module (confirmed by source contract) — no global scroll-restoration behavior was changed, per this task's own explicit "do not set `history.scrollRestoration = "manual"` without a demonstrated need," and no need was demonstrated. `restoreScroll(scrollY)` is a narrow, explicit, opt-in helper a Return control calls deliberately — it performs one instant `window.scrollTo({ top, behavior: "auto" })`, never `"smooth"` (confirmed by source contract) — an immediate jump, not an animated/hijacked scroll, consistent with this task's repeated "no scroll hijacking" prohibition.

## Index position — stable identity over raw pixels

`resultKey` (a stable item identity) is captured alongside, and preferred over, `scrollY` (a best-effort restoration target only) — per this task's own §C8 instruction not to assume a pixel coordinate remains meaningful after filtering or a viewport change. Neither is treated as authoritative on its own; a real future consumer (M4.8) would use `resultKey` to re-locate the item and `scrollY` only as a fallback/refinement.

## Comparison / gallery / expanded state — modeled, not built

`comparisonState`, `galleryPosition`, and `expandedIds` are all real, typed fields on `ReturnContext`, captured and restored by real code and real tests — but no actual Comparison or Gallery feature exists yet to generate this data organically (M4.10's separate scope), so the fixture supplies clearly-labeled placeholder values for them, per this task's own explicit §C9 instruction ("use clearly labeled fixture state," "do not invent full feature implementations merely to exercise storage").

## Return efficiency

No choreography was built — Return in this package is a single synchronous state lookup plus one simulated-latency restore in the fixture (see below); this deliberately does not implement M4.8's actual record-passage choreography, per this task's own repeated instruction (§C8/§C10).

## Cancellation — genuine async race, guarded by M4.2's real primitive

Unlike M4.4 (which audited and found no async settle to guard), Return genuinely does have one: restoring scroll/focus after a real navigation must wait for the destination's content and layout to be ready (§C7) — an inherently asynchronous step. The fixture's `handleReturn` demonstrates this honestly with a simulated latency (`window.setTimeout`, standing in for "waiting for the destination page"), guarded by M4.2's real `createMotionCancellation` — the exact primitive `InterruptionDemo` (M4.3) already proved, reused here rather than a second cancellation mechanism. Three rapid Return clicks resolve to only the third intent's message; the first two never settle late and never overwrite the final state (tested directly, mirroring `InterruptionDemo.test.tsx`'s own methodology).

## Fixture

`src/components/return/ReturnMemoryFixture.tsx` demonstrates the complete cycle: capture the current fixture state (including a `data-return-origin-key` on the capture control itself, so `restoreFocusByKey` has something real to resolve); change the *live* fixture state afterward (toggling an "expanded" flag); Return, and observe that the *captured* (old) value is what comes back, not the current one — directly proving fidelity, not just presence. A cold Return before any capture correctly reports there is nothing to return to. Composed into the same `?motion-fixture=m4b` gate M4.4/M4.5 already established, alongside `OverlayFixture` — no new query value, no new route.
