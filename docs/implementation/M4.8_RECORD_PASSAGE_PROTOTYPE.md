## Reconciliation

### Reconciliation reason

After M4-C's own initial reconciliation pass, a narrow follow-up audit found a genuine mismatch between this report's original claim and `ANIMATION_SYSTEM.md`'s own authority. Independently reconfirmed before editing anything: §4 (Motion Hierarchy) names **Record Passage** as its own distinct level, above Focus and below District Passage/World Threshold; §5.2 (Passage) explicitly allows "translation, shared geometry, controlled depth, directional cropping, persistent anchors"; §9.5 (Index → record) states "the selected record acts as the spatial origin of the detail view"; §28 (Reduced-Motion System) gives Passage its own explicit reduced-motion role equivalent ("concise replacement preserving shared anchors") — never "not applicable." `IMPLEMENTATION_PLAN.md` §9's MOT-04 prototype wording ("Implement index → record → Return within one district") matches this package's own scope exactly, confirming Record Passage was always meant to include this temporal dimension, not only the navigation/Return architecture.

### Previous mechanical gap

The original implementation correctly proved Index → canonical record → Return as a *navigation and state* architecture (origin capture, canonical destination, filter/lens preservation, selected-record identity, scroll restoration, direct-entry behavior, Return vs Back, native links/history) but genuinely contained zero motion of any kind, and its own "Reduced motion" section stated "not applicable — no motion exists in this package." That claim is corrected by this reconciliation; every other finding in the original report (origin capture, canonical destination, Return vs Back, browser-history boundary, etc.) was independently re-verified and remains accurate, unchanged below.

### Record-Passage temporal treatment

A new component, `RecordPassageArrival.tsx`, wraps `WorkEntryPage`'s existing content. On a **genuine** passage arrival only, it renders one small, real "shared-origin anchor" (`Arrived from Index — {record title}`) that mounts at a restrained, receded/offset "arriving" visual state and settles to its final "settled" state one animation frame later — a real, visible entrance in any browser, not merely a declared-but-inert CSS rule. The record's own primary content (heading, evidence, etc.) is never wrapped in any conditional motion — it renders identically and immediately regardless of arrival state (see **Entry motion contract** below).

### Genuine-passage detection

Reuses the exact check `RecordReturnControl` already established: a real captured `ReturnContext` whose `resultKey` matches this exact record's slug (`WORK_RECORD_PASSAGE_RETURN_KEY`, M4.6's own unmodified `retrieveReturnContext`). Detected via `useSyncExternalStore` (the same SSR-safe pattern `RecordReturnControl`/`ThresholdIndicator` already use) — a side-effect-free snapshot, never mutated inside an effect, so it does not trigger this repository's `react-hooks/set-state-in-effect` rule.

### Direct-entry distinction

A cold/direct entry (no capture, or a capture belonging to a *different* record) causes `RecordPassageArrival` to render `children` completely unwrapped — no anchor, no `data-record-passage-state` attribute, no motion of any kind, exactly `ANIMATION_SYSTEM.md`'s "abbreviated/static orientation only" for a context with no genuine origin. This is the same honesty boundary `RecordReturnControl` already enforces for the Return control itself, now also applied to the passage treatment.

### Entry motion contract

No navigation is ever delayed: `children` (the real canonical record content) renders in the exact same pass regardless of arrival state — only the small anchor's own presentation is conditional. The two-frame "arriving → settled" sequence is driven by a **ref callback**, not a `useEffect` calling `setState`: React invokes ref callbacks synchronously during the commit phase, so `attachArrivalNode` calls `node.setAttribute("data-record-passage-state", "settled")` directly inside a `requestAnimationFrame` scheduled from the ref callback — no React state is involved in the sequencing at all, avoiding both the lint rule an effect-based approach would trip and the "insert a brand-new DOM node already at its final values, so it never visibly animates" limitation a conditionally-*mounted* element would otherwise have (the wrapper mounts once, already in the DOM, and only its own attribute value changes afterward — a real, native CSS transition target).

### Return motion contract

No motion was added to the Return side. `IndexPassageRestoration`'s existing instant, non-smooth scroll restore already satisfies this task's own "Return should be faster/lighter/less ceremonial than entry" requirement by construction — zero duration is unambiguously less ceremonial than the entry anchor's one `--motion-duration-deliberate` settle. `Return` was not converted into `history.back()`; browser Back remains independently valid (unchanged, see **Return vs Back** below).

### Token use

Only already-declared M4.1 tokens, confirmed by source contract — no new token, no new family, no M4.1 modification:

- `--motion-duration-deliberate` (360ms) — the same tier `Focus` (M4.4) already uses. Record Passage is distinguished from Focus not by a longer duration (no token exists strictly between `deliberate` and `spatial`) but by using an *additional* channel — translation — that Focus never uses.
- `--motion-ease-move` — already declared for "repositioning in place," the exact semantic fit for this restrained translation.
- `--motion-distance-record` (32px) — declared by M4.1 specifically as "the largest current/near-term local-passage distance any current or near-term component needs," unconsumed anywhere until now. This is its first real consumer.
- `--motion-recession-subtle` (0.9 opacity) — declared, unconsumed until now.

This file deliberately never references `--motion-duration-spatial`, the tier M4.9's Home-Threshold prototype already claimed for District Passage/World Threshold — Record Passage stays strictly below it, satisfying `ANIMATION_SYSTEM.md` §4's ordering without inventing a new tier to enforce it numerically.

### Reduced-motion equivalent

No longer "not applicable." `RecordPassageArrival` consumes M4.2's centralized `useReducedMotion()` directly (no component-local `matchMedia`). When active, the anchor mounts straight at `"settled"` — the `"arriving"` visual values (the opacity/translate offset) never apply at all, confirmed directly by test. This is exactly `ANIMATION_SYSTEM.md` §28's own named equivalent: "Passage → concise replacement preserving shared anchors" — the shared anchor is still shown immediately, canonical content still loads immediately, selected identity remains clear, passage origin remains knowable through the unchanged Return control, and no meaning disappears; only the spatial travel collapses.

### Responsive equivalent

The restrained translation (`--motion-distance-record`, 32px) is already small enough not to require narrower-viewport reduction — it does not depend on desktop-only shared geometry, introduces no horizontal movement (`translateY` only, confirmed by source contract), and cannot cause horizontal overflow at 390px. Direct content access is unaffected by viewport size, since `children` never depends on the arrival state.

### Accessibility

The anchor is a real `<p role="status">`, announced to assistive technology without needing motion to convey meaning; the canonical `next/link`s (Index departure, Return) remain fully keyboard-operable (Tab, Enter) and touch-direct, unaffected by this reconciliation. `focus-visible` is untouched (this package adds no new interactive control). Direct entry works identically to before — no passage state is required for the record to be fully usable.

### Browser-history boundary

Unchanged and reconfirmed: no `history.pushState`/`replaceState`/`back()` call exists anywhere in `RecordPassageArrival.tsx` (the same repository-wide `tests/lib/native-history-source-contract.test.ts` M4.7 built still passes with this new file present).

## Record-passage architecture

Three small, cleanly separated pieces, all under a new `src/components/return/`:

- **`PassageIndexRecord.tsx`** (client) — the Index-side departure point. Visually identical to `IndexRecord` (same classes, same structure) but captures Return context in a synchronous `onClick` before the real `next/link` navigation proceeds — never delaying or gating access to the destination.
- **`RecordReturnControl.tsx`** (client) — the canonical-record-side arrival point. Renders a real `next/link` back to the captured origin, but *only* when a genuine, matching capture exists.
- **`IndexPassageRestoration.tsx`** (client, invisible) — mounted on the Index-district-work route only. On mount, restores scroll and clears the capture, but only when the captured `originUrl` matches the *current* URL exactly.

`IndexResults.tsx` (M3.10) gained one new, optional, default-`undefined` prop, `passageCaptureDistrict` — every other Index route (`/index`, `/index/type/...`, `/index/theme/...`, `/index/discipline/...`, `/index/year/...`) passes nothing and is byte-for-byte unaffected; only `/index/district/[district]` passes `"work"` when `district === "work"`. `IndexRecord` itself (M2.7) was not modified at all — deliberately: it is a shared primitive used by every Index route and content type, and M4.8 is explicitly scoped to one representative district, not a platform-wide capability.

## Rapid-navigation cancellation

Since every capture/restore operation is synchronous, "rapid navigation" reduces to: does a second capture cleanly supersede a first? Yes — `captureReturnContext` under the one fixed passage key always overwrites, and `IndexPassageRestoration`'s URL-match guard means a stale capture belonging to an *earlier* Index view can only ever restore against a URL that actually matches it, never against wherever the visitor has since navigated. No stale passage can steal focus, restore an old scroll position, or reopen an old record.

Re-audited for the reconciliation's own `requestAnimationFrame`-scheduled settle: no M4.2 cancellation was manufactured for it, and none is needed. Per this task's own §9 instruction ("do not manufacture asynchronous cancellation if the final implementation has no stale settle path"), the settle callback holds a direct reference to the real DOM node and calls `setAttribute` on it — if the visitor navigates away before the frame fires, the callback still runs harmlessly against a now-detached node (a silent no-op; browsers do not error on mutating a disconnected element), and reacts to nothing else, steals no focus, and mutates no route or React state. There is no stale-state path for a cancellation primitive to guard.
