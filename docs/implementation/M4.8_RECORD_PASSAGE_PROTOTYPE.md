## Starting-state audit

No Record-Passage implementation existed anywhere — M4.6's own report explicitly named this as owed to "a later package" (M4.8, this one). `IndexRecord` (M2.7) was a plain, non-interactive `next/link` row with no Return-capture behavior; `/work/[entry]` (`WorkEntryPage`) rendered only `CanonicalRecordShell` + `DirectEntryOrientation`, with its `continuation` region unused.

## Representative district choice

**Work**, per this task's own preference and audit instruction. Confirmed directly: `src/domain/records/fixtures.ts` already defines a real, public, canonical `fixtureWorkRecord` (`slug: "fixture-work-outcome"`), M3.3's `RouteResolver` already resolves it to `/work/fixture-work-outcome`, and `/index/district/work` already exists as a real route narrowing Index to exactly Work's public fixtures (M3.10/M3.11, unmodified). No new canonical record was invented and no new route was created — every piece of infrastructure this prototype needed already existed and required no fabrication.

## Real journey, not a simulation

The entire journey uses real application code: the actual `/index/district/[district]` and `/work/[entry]` page components, the actual `RouteResolver`-resolved canonical route (`entry.route`, computed by `queryIndex`/`resolvePublicRecordSource`, unchanged), and the actual M3-B fixture source (`?fixture=m3b`). `tests/integration/m4c-record-passage-journey.test.tsx` renders the real `IndexByDistrictPage` and `WorkEntryPage` functions directly — no fixture-only stand-in inside `/contact` was built for this package; M4.8 owns no `/contact` fixture at all.

## Canonical destination stays canonical

The destination is the existing `/work/{slug}` route — never a presentation-specific duplicate like `/index/work/example/detail`. `PassageIndexRecord`'s `href` prop is `entry.route`, the same value `IndexRecord` already rendered — Index organization, canonical identity, and Return memory remain three separate concepts throughout: Index narrows *which* records are visible; the route *is* the record's one identity; Return memory is a session-scoped hint about where a visitor came from, never a second identity system.

## Record-passage architecture

Three small, cleanly separated pieces, all under a new `src/components/return/`:

- **`PassageIndexRecord.tsx`** (client) — the Index-side departure point. Visually identical to `IndexRecord` (same classes, same structure) but captures Return context in a synchronous `onClick` before the real `next/link` navigation proceeds — never delaying or gating access to the destination.
- **`RecordReturnControl.tsx`** (client) — the canonical-record-side arrival point. Renders a real `next/link` back to the captured origin, but *only* when a genuine, matching capture exists.
- **`IndexPassageRestoration.tsx`** (client, invisible) — mounted on the Index-district-work route only. On mount, restores scroll and clears the capture, but only when the captured `originUrl` matches the *current* URL exactly.

`IndexResults.tsx` (M3.10) gained one new, optional, default-`undefined` prop, `passageCaptureDistrict` — every other Index route (`/index`, `/index/type/...`, `/index/theme/...`, `/index/discipline/...`, `/index/year/...`) passes nothing and is byte-for-byte unaffected; only `/index/district/[district]` passes `"work"` when `district === "work"`. `IndexRecord` itself (M2.7) was not modified at all — deliberately: it is a shared primitive used by every Index route and content type, and M4.8 is explicitly scoped to one representative district, not a platform-wide capability.

## M4.1 token use

None. Record Passage in this prototype is a *state* transition (which row is captured, which control appears), not an *animated* one — no new CSS, no new motion token consumption. This is a deliberate, minimal first pass: the passage mechanics (capture/restore/verify) are proven before any visual travel/entrance treatment is layered on, consistent with this task's own "content access must remain immediate" and the broader instruction not to gate navigation behind an animation. No dramatic entrance/exit motion exists to critique, by construction.

## M4.2 cancellation

Audited and deliberately not consumed. Every capture/restore operation here is synchronous (a `sessionStorage` read/write plus, on the Index side, one `window.scrollTo` call) — there is no async settle to race, the same conclusion M4.4 independently reached for its own local Focus state. Rapid navigation is still proven safe (§A10, below), just not through the cancellation primitive, because nothing here is asynchronous enough to need it.

## M4.6 Return composition

`PassageIndexRecord`/`RecordReturnControl`/`IndexPassageRestoration` are the *first real, non-fixture consumers* of `src/lib/return/returnMemory.ts` — every function they call (`captureReturnContext`, `retrieveReturnContext`, `clearReturnContext`, `restoreScroll`) is M4.6's own, completely unmodified. No second Return store was created.

## M4.7 browser-history composition

Every navigation step is a real `next/link` click — no `history.pushState`/`router.push` call exists anywhere in this package (confirmed by the same repository-wide source-contract test M4.7 built, which still passes with these new files included). Browser Back remains fully independent and untouched.

## Origin capture

`PassageIndexRecord.handleClick` captures, at the moment of departure: `originUrl` (`window.location.pathname + window.location.search` — includes the `fixture`/any future filter query untouched), `parentDistrict`, `selectedRecordId` (the record's real ID), `resultKey` (the record's real slug — preferred identity per M4.6 §C8), and `scrollY`.

## Selected-record preservation

`selectedRecordId` is captured and available in the restored context; `RecordReturnControl` matches on `resultKey` (the slug) specifically, since that is what the destination route actually has in hand (`params.entry`).

## Filter/lens preservation

`originUrl` is captured verbatim, query string included — proven directly: capturing while on `/index/district/work?fixture=m3b` and restoring reproduces that exact URL, including the fixture flag, with no separate filter field anywhere (reconfirming M4.6's own "no duplicate filter store" boundary against a real, non-fixture consumer for the first time).

## Scroll/Index restoration

`IndexPassageRestoration` restores `scrollY` via M4.6's `restoreScroll` (one instant, non-smooth jump) — but only when `originUrl` matches the current URL exactly, and clears the capture immediately afterward so a later, unrelated visit to the same URL never re-triggers it.

## Return behavior

`RecordReturnControl` renders a real link to `context.originUrl` — clicking it is genuine navigation, not a JS-driven state restoration trick.

## Return vs Back

Kept distinct exactly as M4.6/M4.7 established: Return is the `RecordReturnControl` link (a data-driven, capture-specific navigation); Back is the untouched native browser mechanism. `tests/integration/m4c-record-passage-journey.test.tsx` proves both remain valid independently — a "browser Back remains independently valid" test confirms `window.history.length` reflects only the one real navigation performed, nothing fabricated by the capture step itself.

## Direct entry

A cold `WorkEntryPage` render (no prior Index visit in this session) shows no Return control — tested directly — while `DirectEntryOrientation` (M3.13, untouched) continues to provide the real structural fallback. The passage system adds no dependency on prior navigation for the record to remain fully usable.

## Rapid-navigation cancellation

Since every operation here is synchronous, "rapid navigation" reduces to: does a second capture cleanly supersede a first? Yes — `captureReturnContext` under the one fixed passage key always overwrites, and `IndexPassageRestoration`'s URL-match guard means a stale capture belonging to an *earlier* Index view can only ever restore against a URL that actually matches it, never against wherever the visitor has since navigated. No stale passage can steal focus, restore an old scroll position, or reopen an old record.

## Reduced motion

Not applicable to this package's own code — there is no animation in the record-passage mechanics themselves (see **M4.1 token use** above) for reduced motion to affect. The origin/destination relationship, selected identity, and Return availability are all structural (real props/URLs/session data), unconditional on any motion preference.

## Keyboard / touch

`PassageIndexRecord`'s link and `RecordReturnControl`'s link are both real `next/link` instances — Tab, Enter, and touch activation all work identically to any other link in the application, with no hover prerequisite (confirmed structurally; both components are functionally indistinguishable from a plain link except for the synchronous capture side-effect).

## Browser-native boundary

No custom route stack, no global navigation interception, no manual `scrollRestoration` override, no Back-blocking — confirmed by the same M4.7 audit test suite, unchanged, still passing with these new files present.

## Fixture strategy

None was added — no `/contact` fixture, no new `motion-fixture` value. Per this task's own explicit preference, the real `/index/district/work?fixture=m3b` → `/work/fixture-work-outcome` → Return journey *is* the review surface; a duplicated simulation would have been the wrong kind of evidence for a "prove real routing" package.

## Browser-only verification

Genuine multi-page browser navigation, real Back/Forward button behavior after a Record-Passage journey, and the felt experience of "faster/lighter" Return in an actual browser cannot be mechanically proven by this repository's jsdom-based suite — flagged explicitly for the M4-C integrated human review, per the same honest boundary M4.7 already established.
