## Compact ~390px

Verified via source evidence: `.tab-list`, `.segmented-view-options` (after correction), `.record-index-link`, `.record-editorial-meta`, `.record-product-commercial`, `.media-comparison-pair` all wrap; `.metadata-rail`/`.metadata-group` are single-column below 768px; `.media-comparison-matrix`'s `minmax(200px,1fr)` resolves to one column within the available compact width; no fixed pixel width exceeding 44px exists anywhere outside decorative markers (checkbox box, radio dot, filter-toggle marker — all ≤18px, confirmed by the new fixed-width scan across all nine stylesheets).

## Medium ~768px

The exact breakpoint every compact-reflow rule in this codebase already keys off: `.composition` (M2.3) switches to 8-column/medium margin-gutter here, and `.metadata-rail`/`.metadata-group` (M2.9) switch from one column to `max-content 1fr` here — confirmed identical value via the cross-cutting breakpoint-consistency test (no second, drifted "medium" breakpoint exists anywhere in the nine stylesheets).

## ~1024px

`.composition` switches to 12-column/wide margin-gutter here (`layout.css`, unchanged since M2.3, re-confirmed present and untouched by this package). No other M2.5–M2.11 primitive has its own 1024px-specific rule — none needed one, since their own recomposition (flex-wrap, grid auto-fit, the 768px metadata reflow) already resolves correctly across the medium→wide range without a third breakpoint.

## Wide ~1440–1600px

`--composition-max: 1600px` (M2.3, unchanged) caps `.composition`'s width and centers it (`margin-inline: auto`) — confirmed present, untouched. No M2.5–M2.11 primitive imposes its own competing max-width that would fight this.

## Ultra-Wide

`.composition`'s `max-width` + auto-centering is the entire mechanism (M2.3): beyond 1600px, the grid stops growing and the extra space becomes void on either side — verified structurally present in `layout.css` (unchanged). `.record-editorial` (65ch) and `.record-portal-orientation` (60ch) both cap their own reading measure independently of viewport width via `ch` units, so long-form text never stretches into unreadably long lines on an ultra-wide viewport even before `.composition`'s own ultra-wide behavior takes effect.

## 200% Zoom / Reflow

No fixed-height container, no `overflow: hidden` wrapping essential text, and (per the new fixed-width scan) no large fixed pixel width exists anywhere across all nine M2.2–M2.11 stylesheets that could force horizontal scrolling at 200% zoom. `ch`/`%`/`fr`/`clamp()` are the only sizing units used for anything that could realistically overflow; the handful of literal `px` values remaining are either 44px touch targets (intentionally fixed, not a zoom hazard — a minimum, not a maximum) or small decorative markers (≤18px).

## Touch / No-Hover

Confirmed by the new cross-cutting test: **every** `:hover` rule in all nine stylesheets is exactly `opacity: 0.85` (or `0.7` for `:active`, checked separately) and nothing else — no `display`, `visibility`, or `content` property ever appears inside a `:hover` block anywhere in this codebase. This means, by construction (not by spot-check), no essential information or affordance in Milestone 2 depends on hover to be discoverable or usable. Every interactive target reviewed keeps its `min-height:44px`/`min-width:44px` floor (M2.5's original resolution, reused unchanged by every later package).

|---|---|---|---|

| Latent metadata (`--color-mist-300` × `--opacity-latent`) vs. field | 4.88:1 | 4.5:1 | Pass (matches the value already derived and documented in `opacity.css`'s own header when M2.9 resolved this token) |

## Corrections Made

**One correction**, evidence-based and minimal:

- **`src/styles/selection.css`, `.segmented-view-options`** — added `flex-wrap: wrap`. Before this correction, the rule was `display: inline-flex; border: ...; border-radius: ...; overflow: hidden;` with no wrap — combined with `overflow: hidden` (present for the rounded-corner clipping between segments), a `SegmentedView` with enough options or long-enough labels would have had its later options **clipped**, not wrapped, at compact widths. This is exactly the "essential horizontal scrolling/clipping" defect this task's own §C5/§C6 asks to be caught. The fix does not change any already human-approved desktop visual treatment: at the option counts/label lengths already exercised by every existing test and by M2.6's own human visual review (2–3 short options), the flex row already fit on one line, so wrapping never triggers and the rendered result is pixel-identical to before. A dedicated regression test was added to `tests/tokens/selection-contract.test.ts` (`"[M2.12 responsive correction] segmented-view options wrap rather than clip at narrow widths"`) and to `tests/tokens/responsive-verification.test.ts`.

No other correction was made. Every other primitive verified without change (see the matrix above).
