## Classification architecture

Every dimension in this module falls into exactly one of three structurally distinct kinds — mixing them was the single biggest risk this package had to avoid (IA §9.1's own precise vocabulary — canonical record, collection, grouping, lens, filter — exists specifically to prevent this kind of collapse):

1. **Canonical-derived facets** (`districtFacet`, `contentTypeFacet`, `yearFacet`) — computed directly from fields M3.1 already owns (`ownerDistrict`, `contentType`, `date`). Never separately stored, so there is exactly one source of truth for each — this directly satisfies this task's own §C7 ("do not create two conflicting sources of truth").
2. **State facets** (`lifecycleFacet`, `visibilityFacet`, `curatorialInclusionFacet`) — likewise derived, but each tagged with its own explicit `source`, so distinct state dimensions can never merge into one generic vocabulary (IA §6.3).
3. **Catalog-referenced terms** (`discipline`, `theme`, `collection`, `series`, `territory`, `contribution-role`) — controlled-vocabulary terms a record references by stable ID; a term must exist in the catalog before any record may reference it, and every reference is validated (unknown term, wrong dimension, wrong district scope, and duplicate reference are all rejected).

## Controlled catalog

`ClassificationTerm { id, dimension, label, districtScope?, description? }`, built into a registry via `createClassificationCatalog(terms)`, which throws on the first duplicate term ID — the same registry pattern M3.1's `createRecordRegistry` and M3.3's `buildCanonicalRouteRegistry` already established. `ClassificationDimension` is a **closed literal union** (`"discipline" | "theme" | "collection" | "series" | "territory" | "contribution-role"`), not an open string map — confirmed by `classification-model-source-contract.test.ts`. No `tags: string[]` or equivalent freeform array exists anywhere in this module.

## Term identity

**M3.1's `CanonicalRecordBase.disciplines`/`.themes` fields were deliberately left untouched.** This task's own instruction (§C16) was to audit that field and "strengthen it in the smallest backward-compatible way necessary" if too weak — not to change its type unconditionally. The audit's conclusion: the field's *type* (`string[]`) does not need to change to become controlled — a term's stable ID is itself just a string (e.g. `"computational-design"`), so `disciplines: string[]` can already hold controlled term-ID references without any structural change. What was actually missing was **validation**, not a type change: `validateRecordClassifications(record, catalog)` is the strengthening this task asked for, applied at the smallest possible surface (a new function in a new module) rather than by reopening and re-validating M3.1's already-closed contract. This keeps M3.1 exactly as it was left, satisfies "backward-compatible," and still delivers the actual outcome IA §18.6 requires: classification uses controlled vocabulary, not unrestricted tagging.

## No-tag-cloud enforcement

Enforced four ways, all tested: (1) `createClassificationCatalog` rejects duplicate term IDs; (2) `validateRecordClassifications` rejects any referenced string that isn't a real catalog term; (3) it further rejects a term used under the wrong dimension (a theme term referenced as if it were a discipline); (4) it rejects a term referenced twice on the same record. `classification-model-source-contract.test.ts` additionally confirms no `tags: string[]` field exists anywhere in the source and that `ClassificationDimension` is a closed union.

## Canonical-derived dimensions

- **District** — `districtFacet(record)` reads `ownerDistrict` directly.
- **Content type** — `contentTypeFacet(record)` reads `contentType` directly. IA §14.3: "the Index consumes the platform's approved content classifications — it may not invent a parallel categorization system." No second type taxonomy exists here; M3.1's approved 17-value vocabulary remains the only one.
- **Year/period** — `yearFacet(record)` derives a year from `CanonicalRecordBase.date` (M3.1's `CanonicalDate` discriminated union: `year`, `date`, or `range`), extracting the leading four digits rather than constructing a `Date` object (avoiding timezone-dependent behavior). Tested for all three `CanonicalDate` variants plus the absent-date case.

## Controlled stored dimensions

- **Discipline** and **theme** — the two catalog-referenced dimensions that also double as global lenses (see below). Discipline terms are seeded from Work Universe §9's real approved practice-area vocabulary ("Computational Design"), since discipline is genuine platform-wide controlled vocabulary, not invented demo content (this task's own §C8). Theme terms are deliberately minimal and fixture-labeled (§C9: "do not design an exhaustive theme taxonomy now" — themes emerge from real content over time).
- **Collection, series, territory, contribution-role** — district-specific classification dimensions (IA §18.6: "additional district-specific classifications may exist where useful"), never exposed as global lenses (see "Global Index lens dimensions" below).

## Global Index lens dimensions

`APPROVED_GLOBAL_LENS_DIMENSIONS = ["district", "content-type", "discipline", "theme", "year"]` — IA §8.3/§9.2's exact, closed v1.0 set, reproduced verbatim. `isGlobalLensDimension()` is the only mechanism this module provides for testing lens-eligibility, and it returns `false` for `collection`, `series`, `territory`, and `contribution-role` — confirmed directly (`ClassificationModel.test.ts`: "collection, series, territory, and contribution-role are NOT global lens dimensions") and at the source level (`classification-model-source-contract.test.ts` asserts the exact five-item array literal). No sixth global lens is ever introduced, per this task's own explicit instruction.

## Discipline

Cross-district by design — `disciplineTermComputationalDesign` carries no `districtScope`, so the same term may classify Work, Lab, or any other district's records without duplication (`ClassificationModel.test.ts`'s "Cross-district discovery" test proves both a Work-owned and a Lab-owned record can reference the identical catalog entry). Discipline never becomes ownership — using a discipline term never changes a record's `ownerDistrict` (see "Ownership invariance" below).

## Theme

Modeled identically to discipline mechanically (a catalog-referenced dimension, also global-lens-capable) but deliberately seeded with only one clearly fixture-labeled term, since IA gives no fixed approved theme vocabulary the way Work Universe gives one for discipline — themes are meant to emerge from actual published content, not be pre-invented at this stage.

## Content type

Deliberately **not** re-modeled — `contentTypeFacet` derives directly from `CanonicalRecordBase.contentType`, M3.1's own approved 17-value vocabulary. No second type taxonomy exists in this package (IA §14.3).

## District grouping

Collection, series, territory, and contribution-role all share the same `ClassificationTerm` mechanics while remaining semantically distinct (this task's own §C13: "shared mechanics are allowed; shared meaning is not assumed") — enforced by the `dimension` discriminant field, never collapsed into one generic `"tag"` dimension:

- **Work** — `collection` (IA §18.3's own defined "Collection" concept, matching the existing approved `/work/collections/{collection}` route). Practice areas are **not** separately modeled here — Work Universe §9 itself calls them "lenses," and they are already the correct real-world content of the `discipline` dimension scoped to Work (see M3.2's own "Work extension" reasoning, carried forward here rather than duplicated as a second mechanism).
- **Research** — `territory` (Research Universe's own vocabulary — Territory, Research Line).
- **Art** — `series` (Art Universe §12's own "Series" concept).
- **Products** — `collection`, scoped to `products`. **Products' `productFamily` is deliberately not re-modeled as a classification dimension** — M3.2 already established `productFamily` as *structural* truth (the seven approved commercial mechanics, functionally equivalent to `contentType`), not a discovery/classification facet; re-introducing it here as a "family" dimension would create exactly the two-sources-of-truth problem this task's own §C7 warns against. Products' genuine *new* classification-facing concept — the Product Hierarchy's Level 3 "Collections" (curated groupings that reference records without owning them) — is what `collection` models here, demonstrated with its own fixture term, distinct in ID from Work's collection term despite sharing a dimension.

## Collection / Series / Territory / Family

Kept semantically distinct per this task's explicit instruction: a Research territory is never treated as an Art series, tested directly (`ClassificationModel.test.ts`: "Research territory term is scoped to research, distinct meaning from Art series"). "Family" (Products) is not separately modeled — see "District grouping" above for why `collection` is the correct dimension for Products' M3.4-owned classification concern, with `productFamily` remaining M3.2's structural field.

## Contribution/role

Modeled as its own catalog dimension (`contribution-role`, e.g. `"lead"`) — a controlled, filterable vocabulary distinct from `CanonicalRecordBase.authorship`/`AttributionEntry.role`, which remain M3.1-owned data on the record itself (this task's own §C14: "canonical authorship itself remains owned by M3.1"). This package does not modify `Authorship`/`AttributionEntry` — the catalog exists as the controlled vocabulary a future governance/authoring step could draw `role` values from, without requiring any change to M3.1's or M3.2's already-closed types now.

## Status/state handling

No generic `status` classification exists anywhere in this module — `classification-model-source-contract.test.ts` asserts this directly. Domain-specific state (Research's `researchActivityState`, Lab's `experimentState`, Art's `presentationCondition`, Products' `commercialState` — all M3.2) is **not** duplicated here as a classification term; those fields already carry precise names and live on their own district extension, read directly by any caller that needs them. What this module does add is three narrowly-scoped **state facets** (`lifecycleFacet`, `visibilityFacet`, `curatorialInclusionFacet`), each explicitly tagged with its own `source`, proving these three IA-mandated independent dimensions can never collapse into one blob — tested directly.

## Ownership invariance

Classification never changes a record's owner district — `validateRecordClassifications` only ever reads `ownerDistrict` (to check scope), never writes it; `classification-model-source-contract.test.ts` confirms no assignment to `ownerDistrict` exists anywhere in the source. `ClassificationModel.test.ts`'s "Ownership invariance" test constructs a Work record, classifies it, and confirms `ownerDistrict` is untouched.

## Route invariance (M3.3 integration)

`ClassificationModel.test.ts`'s "Route invariance" test imports `resolveCanonicalRoute` (M3.3) directly and proves the same canonical record, reclassified with different discipline/theme references, resolves to the identical canonical route. `classification-model-source-contract.test.ts` additionally confirms `ClassificationModel.ts` itself never imports `RouteResolver.ts` or references route construction at all — the two modules are integrated only at the test level, never coupled at the source level.

## M3.2 integration

`DistrictExtensions.ts` (M3.2) is not imported by this module — classification operates on the universal `CanonicalRecordBase` fields alone (`ownerDistrict`, `disciplines`, `themes`, `contentType`, `date`, `lifecycle`, `visibility`, `curatorialInclusion`), so it applies uniformly regardless of which (if any) district extension a given record also carries. District-specific domain state added by M3.2 is referenced only in prose above (to explain why it is deliberately *not* duplicated here), never imported or re-modeled.

## Search/Index boundary

No Index UI, no Search ranking, no result rendering exists anywhere in this module — `classification-model-source-contract.test.ts` confirms no `search`/`rankResults`/`renderFilter` function names and no `URLSearchParams` usage. This module prepares the structured classification **truth** a future Index/Search implementation (`IMPLEMENTATION_PLAN.md` §7's M3.10/M3.12) will consume — exactly one catalog mechanism exists (`createClassificationCatalog`), confirmed by source-contract test, so Search and Index are guaranteed to consume the same vocabulary rather than two parallel ones.

## Filters boundary

No filter UI, no filter persistence, no URL/query syntax exists anywhere in this module (same source-contract test as above). `validateRecordClassifications` and the facet functions are read-only projections over already-loaded data — they never create a canonical record, never change an owner district, never create a curatorial judgment, and never convert a curated view into a comprehensive one (IA §9.3's four explicit filter prohibitions) simply because this module performs none of those operations at all.

## Validation

Dependency-free — no new dependency was added, consistent with M3.1/M3.2/M3.3's own decisions and for the same reason (no real data-ingestion boundary exists yet). `validateRecordClassifications` returns a `ClassificationIssue[]` (empty when valid), checking: unknown term references, wrong-dimension term usage, out-of-scope district usage, and duplicate references on one record — the exact validation list this task's own §C17 specifies, minus the items that don't apply to this module's single-catalog design (duplicate term IDs are already the catalog constructor's job, mirroring M3.1's registry pattern) or that belong to a later package (route-collision handling remains M3.3's).
