## Testing Strategy

Test only what M1.1–M1.5 actually built: route presence/shape, shared-shell structure and active-context logic, the seven page-shell types' structural obligations, and the accessibility contracts those pieces already claim to satisfy. Do not test Search/Index/Contact *behavior* (none exists), do not fabricate canonical content, and do not add interaction/E2E/visual-regression/performance testing this milestone — those require product behavior or a real browser that Foundation doesn't yet have a reason to run.

**The `async` Server Component limit shaped the plan directly:** every one of this repository's 16 dynamic routes is an `async` page component (it `await`s `params`). Vitest's own docs say it doesn't support rendering these through React's render tree. Rather than reaching for E2E tooling to route around that limit (which this task explicitly discourages unless simpler checks can't satisfy the requirement), the coverage was split by what each check actually needs:

1. **Shell components** (`PageShell` family, `CanonicalRecordShell`, `AppShell`, `GlobalNav`) are all synchronous — they render directly with Testing Library, exactly as the Vitest guide says is supported, giving full coverage of every page-shell type's real structural logic.
2. **Route *existence and shape*** doesn't need rendering at all — a filesystem contract test (Node's `fs`, no rendering, no async-component limit to hit) protects every one of the 53 routes, static and dynamic alike, against deletion or renaming.
3. **Route→shell *wiring*** (does the real `page.tsx` actually call the right shell with the right heading?) is verified by rendering one real, unmodified static `page.tsx` per page-shell type. For the one type with no static example — Canonical Record, since all 6 of its routes are dynamic — the exported `async` page function is called directly (`await WorkEntryPage({ params, searchParams })`), which resolves `params` exactly as Next.js does at request time and returns a plain React element; *that* element is then handed to Testing Library. This sidesteps the documented limitation (which is about React's reconciler handling an async component *during rendering*, not about calling an exported async function in test code) without needing a browser. It was implemented and run to confirm it actually works, not assumed.
4. **Accessibility** is checked as structural assertions (landmark roles/names, `aria-current` values, one `<main>`/one `<h1>` counts, native link semantics) embedded in the same tests, plus one dedicated composed-page suite — not a separate heavyweight tool.

## Tooling Selected

**Vitest + `@testing-library/react` + `@testing-library/dom` + `@testing-library/jest-dom` + `jsdom` + `@vitejs/plugin-react` + `vite-tsconfig-paths`.** This is the exact stack Next.js 16's own bundled guide documents for App Router unit testing — no substitution, no addition beyond `@testing-library/jest-dom` (a matcher-extension library, not a competing framework, that makes assertions like `toHaveAttribute`/`toBeInTheDocument` read directly instead of via raw DOM property checks).

Why this is the *minimum* appropriate stack, not just *a* reasonable one:

- **No E2E/browser tool (Playwright/Cypress) was added.** Every requirement this task lists — route presence, shell structure, page-shell contracts, accessibility smoke checks — was achievable with component-level rendering plus one filesystem check; nothing here needed a real browser or a running dev server. This task explicitly says not to add browser E2E tooling unless simpler checks can't satisfy the requirement, and here they could.
- **No separate accessibility library (axe-core / jest-axe / vitest-axe) was added.** Testing Library's `getByRole`/`getAllByRole` queries are themselves accessibility-tree-based — they only find elements the way assistive technology would. Asserting on roles, accessible names, and `aria-current` values *is* a legitimate, lightweight way to smoke-test the specific contracts this task lists (labeled landmarks, one main, no empty ARIA landmarks, current-state semantics), without pulling in a second, overlapping tool for the same job. `Do not claim full WCAG compliance from these smoke tests` — none is claimed; see **Deferred Testing**.
- **No Jest.** Next 16's own docs don't even include a Jest guide for the App Router anymore; Vitest is the framework the installed version's own documentation recommends, and it's lighter/faster (native ESM, Vite-powered) than Jest's Next.js integration typically is.
- **`vite-tsconfig-paths`** is required, not optional convenience — without it, Vitest (which runs on Vite, not Next's own bundler) cannot resolve this repository's `@/*` → `./src/*` path alias, which every shell component and every test file uses. (Vitest printed an informational note that newer Vite versions support `resolve.tsconfigPaths` natively instead of this plugin; the plugin form was kept because it's what the installed Next.js version's own guide documents — not a defect, just following the version-appropriate documented setup rather than an undocumented alternative.)
