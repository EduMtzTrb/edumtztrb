## Control Semantic Model

Two independent primitives, not one shared "clickable" abstraction:

- **`Action`** — a state-changing operation: native `<button type="button">`, always. No `href`, no navigation.
- **`ActionLink`** — navigation: wraps Next.js `Link`, always renders an `<a>`. No `disabled`, no `type`, no click-only mode.

## Button vs. Link Boundary

Enforced at the TypeScript type level, not by convention or lint rule alone:

- `Action`'s props extend `ButtonHTMLAttributes<HTMLButtonElement>` (minus `type`/`children`, which are separately controlled); it has no `href` prop at all — passing one is a compile error.
- `ActionLink`'s props extend `ComponentProps<typeof Link>` (minus `children`); it has no `disabled` or button `type` prop at all — passing either is a compile error.
- The two prop interfaces share no common supertype in this codebase, so there is no way to write a single polymorphic `<Control href={x} onClick={y}>` that silently blurs the two — misuse becomes a type error before it becomes a runtime/accessibility bug.
- `Action.test.tsx`/`ActionLink.test.tsx` exercise the resulting DOM directly (`tagName === "BUTTON"` vs. `"A"`), so the boundary is checked at both compile time and render time.

## Action Hierarchy

Three levels, per §28's own explicit "the platform retains three action levels" (confirmed authority, not an invented common-design-system convention — see the Problem Solving note on this exact tension in prior session history):

- **Primary** (`.action-primary`) — inverted fill (`background: var(--color-light-text); color: var(--color-void-1000)`), the strongest available contrast from already-approved neutrals. Default level (`Action` defaults to `level="primary"`).
- **Secondary** (`.action-secondary`) — same geometry, no fill, hairline border (`var(--line-hairline) solid var(--color-mist-300)`) — a containing surface, quieter than Primary.
- **Tertiary** (`.action-tertiary`) — no containing surface, text + underline only, per §28's exact "without a containing surface by default."

No level uses an accent/Signal color to express hierarchy — hierarchy is tonal (fill → outline → text), never chromatic-accent, consistent with the Signal exclusion below.

## Typography

No new typography. Both `Action` and `ActionLink` (for `kind="route"`/`"utility"`) apply the existing `.type-label` class (M2.2) verbatim alongside their level/kind class — `controls.css` itself sets no `font-family`/`font-size`/`font-weight`. `kind="inline"` deliberately does **not** apply `.type-label`, since an inline link must inherit surrounding prose typography rather than impose its own role.

## Geometry

`border-radius: var(--radius-control)` (2px, already-resolved, M1/M2.1) — same rectilinear language as every other primitive in this project; no new radius value. `min-height: 44px` on all buttons and Route/Utility links satisfies §29's 44×44 minimum; `.action-icon-only` adds `min-width: 44px` with zero horizontal padding for glyph-only controls, so the minimum holds even without text driving the width.

## Surfaces / Boundaries

No card-ification: `controls.css` does not use `.plane` or `.frame` (M2.4) for any action level — Primary's fill and Secondary's border are self-contained control geometry, not a reuse of the Plane/Frame compositional primitives, and neither introduces `box-shadow` or `backdrop-filter` (verified by the CSS contract test).

## Default / Hover / Pressed / Focus / Disabled / Loading States

All required by §28's button invariant list; all implemented as static, non-motion tonal shifts:

- **Default** — as described per level above.
- **Hover** — `opacity: 0.85` on `:not(:disabled):hover`. Restrained, uniform across levels, never the sole indicator of interactivity (cursor/underline/fill already establish that at rest).
- **Pressed** — `opacity: 0.7` on `:not(:disabled):active`. Perceptibly stronger than hover, still a flat opacity change — no scale/translate, consistent with this task's "avoid spatial-motion conventions unless Animation System approves."
- **Focus-visible** — `outline: var(--line-emphasis) solid var(--color-focus); outline-offset: 2px;`, **byte-identical** to `shell.css`'s existing rule (verified by a dedicated contract test that parses both rule bodies and asserts string equality, not just visual similarity). §25: "may not redefine... focus behavior" — this reuses the one existing focus mechanism rather than inventing a second.
- **Disabled** — native `disabled` attribute on buttons (browser-enforced non-interactivity) or `aria-disabled="true"` + `pointer-events: none` on links (which have no native disabled state); both get `opacity: var(--opacity-disabled)` (0.5) and `cursor: not-allowed`. Communicated through three independent signals (opacity, cursor, semantic attribute), not color alone.
- **Loading** — `[aria-busy="true"]` on buttons only: same `opacity: var(--opacity-disabled)` dim, `cursor: progress` (distinct from disabled's `not-allowed`), `pointer-events: none`. Structural capability only — no spinner or animation, since nothing in this repository currently loads asynchronously; a real spinner/timing treatment awaits both a genuine consumer and Animation System sign-off.

## Signal Exclusion

`controls.css` contains no `.signal`, `--signal`, or `--color-signal` reference anywhere (asserted by `controls-contract.test.ts`). Hierarchy and every interactive state above are expressed through opacity and tonal fill/outline/text — never through an accent color — consistent with §8/DS-113's explicit "Signal is not a primary-action treatment" and its prohibition on Signal substituting for ordinary hover/focus/CTA/disabled states.

## Responsive Behavior

No breakpoint-specific rule exists in `controls.css` — every declaration is viewport-independent (fixed `44px`/`2px` values, no `clamp()` needed here since none of these properties scales fluidly per the Design System). `.link-inline`'s lack of a forced hit-area means it behaves as ordinary inline text at every width, which is the correct behavior for prose links.

## Light/Dark Compatibility

`color-focus` (used by the focus rule) already resolves to `var(--color-focus-on-dark)` for this project's dark-field default — unchanged, reused exactly as `shell.css` already relies on it. No control here hard-codes a field-direction assumption beyond what already exists platform-wide; `color-light-text`/`color-void-1000`/`color-mist-300` are the same neutrals every other primitive in this project already uses against the dark field.

## Accessibility

- **Hit area:** 44×44px minimum on every button/Route/Utility link, satisfying §29.
- **Accessible names:** icon-only controls require `aria-label` at the type level (`Action`'s discriminated prop type makes `aria-label` mandatory when `iconOnly` is `true` — a missing label is a compile error, not just a convention).
- **Disabled contrast:** opacity-based dimming was chosen over resolving a new `color-disabled` specifically because resolving it against the only plausible existing neutral (`color-graphite-500`) computed 3.98:1 (vs. field) and 3.31:1 (vs. Plane) — both below the 4.5:1 AA floor `DS-141` requires. See `src/styles/tokens/opacity.css`'s header comment for the full reasoning; this avoids creating exactly the "inaccessible low-contrast control" this task was explicitly told not to create.
- **Disabled semantics:** native `disabled` attribute for buttons (removes them from the tab order and blocks all pointer/keyboard activation automatically); `aria-disabled` + `pointer-events: none` for links (since anchors have no native disabled state).
- **Focus:** identical mechanism to the rest of the platform (see **Focus-visible** above) — no separate, inconsistent focus ring for controls.
- **Reduced motion:** unaffected — no animation/transition exists in `controls.css` at all (asserted by the CSS contract test), so the existing global `prefers-reduced-motion` rule in `globals.css` has nothing new to account for.
