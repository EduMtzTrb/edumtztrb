## Starting-state audit

Three of the four dimensions this package must keep separate were **already fully implemented** before this package began: `curatorialInclusion`, `visibility`, and `lifecycle` (M3.1, `CanonicalRecord.ts`), and district-specific state (M3.2's `researchActivityState`/`experimentState`/`presentationCondition`/`commercialState`, `DistrictExtensions.ts`). M3.1's `registry.ts` already provided `isPubliclyDiscoverable`/`isDirectlyAccessible`. What did **not** yet exist: any model of *internal publication state* (an editorial workflow concept, distinct from all four IA dimensions), any derivation of archive eligibility/selection, and any public-safe projection excluding M3.1's `editorial` field. This is exactly M3.6's real, remaining scope.

## State-dimension architecture

The Implementation Plan's phrase "public state" is not a fifth dimension — it reconciles directly to IA's own precise vocabulary (IA §19.4: "do not use `public state` or `status` as unqualified catch-all terms"). Reconciled mapping, used consistently in this module's own code and documentation:

| Implementation Plan phrase | IA term(s) | Owner |
|---|---|---|
| Public state | `curatorialInclusion` + `visibility` | M3.1 (unchanged) |
| District-specific lifecycle | `lifecycle` (universal) + district-specific state fields | M3.1 + M3.2 (unchanged) |
| Internal publication state | *(new)* | M3.6 |
| Archive visibility | derived from `lifecycle === "archived"` + public eligibility | M3.6 (derivation only) |

## Curatorial inclusion

Unchanged from M3.1 — `included`/`excluded`. Not modified or re-modeled by this package.

## Visibility

Unchanged from M3.1 — `public`/`unlisted`/`private`. Not modified or re-modeled by this package.

## Internal publication state

A genuinely new concept this package adds: `InternalPublicationState = "draft" | "in-review" | "ready-to-publish" | "published" | "needs-revision"` — `CROSS_UNIVERSE_SYSTEM_REQUIREMENTS.md` §14's own approved vocabulary, reproduced verbatim. **Modeled entirely outside `CanonicalRecordBase`** — as a separate side-table (`InternalPublicationRecord { recordId; state }`, built into a registry via `createInternalPublicationRegistry`, which rejects a duplicate entry for the same record). This is a deliberate architectural choice: because the canonical record type itself was never given an internal-publication field, leakage into any code that handles a plain `CanonicalRecordBase` is structurally impossible, not merely filtered out by convention. Tested directly, in both directions: a record whose internal workflow state is `"published"` but whose `visibility` is `"private"` remains fully non-discoverable; a record whose internal workflow state is `"draft"` but whose `visibility` is `"public"` remains fully discoverable — the two concepts never influence one another.

## Universal lifecycle

Unchanged from M3.1 — `draft`/`active`/`complete`/`failed`/`abandoned`/`speculative`/`archived`. Not modified or re-modeled by this package. `isArchived(record)` derives from it directly (`record.lifecycle === "archived"`) — there is no second, independently stored archive boolean anywhere (IA §10.2: "archived is a lifecycle value. There is no separate universal archive-state field"), confirmed at the source level.

## Domain-specific state

Unchanged from M3.2 — `DistrictExtensions.ts` is not imported by this module at all except transitively through test fixtures. This package's own source contract explicitly forbids any Lab/Products/Research/Art vocabulary value (`"framed"`, `"stabilized"`, `"forthcoming"`, `"sold-out"`, `"reconstructed"`, `"emulated"`, etc.) from appearing anywhere in `LifecycleArchiveModel.ts` — confirming no universal mega-lifecycle enum was created merging district vocabularies, satisfying this task's own explicit "do not flatten district lifecycles into one sequence."

## No generic status

No field named `status` (qualified or not) exists anywhere in this module — confirmed at the source level, consistent with every prior M3.x package's own equivalent guarantee.

## Public discovery eligibility

`isPubliclyDiscoverable` (M3.1, `registry.ts`) is **reused directly, never re-implemented** — this task's own explicit instruction ("audit M3.1 registry helpers first. Do not duplicate an existing helper"). Tested directly that `included + public` records remain discoverable regardless of: `lifecycle: "failed"`, `lifecycle: "speculative"`, `lifecycle: "archived"`, and a Products-owned record's `commercialState: "discontinued"`. Tested directly that `unlisted`, `private`, and `excluded` are each independently non-discoverable, and that `lifecycle: "complete"` alone does not grant discoverability.

## Direct access

`isDirectlyAccessible` (M3.1, `registry.ts`) is likewise reused unchanged — tested directly that an `unlisted` record remains directly accessible while a `private` record does not.

## Private/excluded handling

Neither concept was re-modeled; both remain M3.1's own fields, read only (never written) by this package's functions.

## Archive definition

`isArchived(record)` — a pure derivation from `lifecycle`, matching IA §10.1's platform-wide definition ("retained canonical records that no longer belong to current primary presentation but still hold historical, evidential, contextual, or lineage value"). No `isArchived` boolean field was added to any record shape — confirmed at the source level.

## Archive eligibility

`isPublicArchiveEligible(record) = isArchived(record) && isPubliclyDiscoverable(record)` — archived AND publicly eligible. Tested directly with both a publicly-eligible archived record (eligible) and a private archived record (not eligible), proving archive status and public eligibility remain two genuinely separate checks composed together, not one flattened concept.

## Canonical identity preservation

Tested directly: an archived record's `id`, `ownerDistrict`, and M3.3-resolved canonical route are all identical before and after setting `lifecycle: "archived"` — the route resolver (M3.3, untouched) never reads `lifecycle` at all, so this is a structural guarantee, not a coincidence of the test data. Outgoing relationships (M3.5) and classification references (M3.4) are likewise proven unaffected by archiving, since neither `RelationshipModel.ts` nor `ClassificationModel.ts` reads `lifecycle` either.

## Work All vs Archive

IA §19.6, reproduced directly in this module's own doc comments: "`All` = all eligible public records within a scope; `Archive` = eligible canonical records whose lifecycle is archived." `selectPublicComprehensiveView(records, district)` selects every publicly-discoverable record in scope (archived or not); `selectPublicArchive(records, district)` selects only the archived subset. Tested directly against the fixture set: the Work comprehensive view includes the (non-archived) `fixtureWorkRecord`, the Work archive does not, and the comprehensive view's size strictly exceeds the archive's — proving `/work/all` and a future `/work/archive` are genuinely different, non-interchangeable selections, never two names for the same set (this task's own explicit §B10/§C9 concern).

## Products lifecycle

Not re-modeled — `commercialState` (M3.2) remains fully independent of `lifecycle`. Tested directly: a `commercialState: "discontinued"` Product remains publicly discoverable and is **not** automatically archived (`isArchived` returns `false` unless `lifecycle` itself is `"archived"`) — matching IA §6.4's own worked example ("Included + Public + Complete + Discontinued → a historically significant Product record whose offer is no longer active") and this task's own explicit "Product discontinued ≠ automatically archived."

## Lab lifecycle/history

Not re-modeled — `experimentState` (M3.2) remains fully independent of `lifecycle`, tested directly (`fixtureLabRecordWithExtension.extension.experimentState !== fixtureLabRecordWithExtension.lifecycle`). Archiving a Lab record's `lifecycle` is proven to leave its outgoing relationships (its lineage to Research/Work/Products) fully intact.

## Research lifecycle

Not re-modeled — `researchActivityState` (M3.2, `ongoing`/`concluded`) remains fully independent of `lifecycle`; no code in this module reads it.

## Art lifecycle

Not re-modeled — `presentationCondition`/`editionNote` (M3.2) remain fully independent of `lifecycle`; tested directly that Art's own `lifecycle` (`"complete"` in the fixture) is unaffected by anything commercial or presentation-related.

## About handling

Not modeled at all in this package (About Universe §24's "Current State" concept remains M3.2's own `AboutExtension` territory, untouched) — no About-specific lifecycle logic exists here, consistent with this task's own instruction not to invent a false cross-district progression.

## Relationship behavior

`RelationshipModel.ts` is imported only by this package's own tests (for integration proof), never by `LifecycleArchiveModel.ts` itself. Tested directly: a Lab record's incoming relationship from Research (M3.5's `listIncomingRelationships`) still resolves correctly after that Lab record is archived — relationships are never stripped, deleted, or filtered based on archive state (confirmed at the source level: no code path clears or filters a `relationships` array). Private-target exposure through relationship traversal remains the caller's own responsibility to check via `isPubliclyDiscoverable`, exactly as it already was before this package — this module does not add or remove any relationship-traversal safety guarantee, it only documents that the existing one (M3.1's `isPubliclyDiscoverable`) still applies unchanged.

## Classification behavior

`ClassificationModel.ts` is likewise imported only by this package's tests. Tested directly: an archived record's `disciplines` reference continues to validate cleanly against the classification catalog — archiving never mutates or clears classification data, confirmed both behaviorally and at the source level (no code path touches `disciplines`/`themes`).

## Public-safe projection

`toPublicSafeProjection(record)` returns `Omit<CanonicalRecordBase, "editorial">` — stripping M3.1's own internal-timestamps field, the one field on the canonical record type itself that was never meant to reach a public client. Tested directly that the projection never carries an `editorial` key. Internal publication state requires no stripping logic at all, by construction (see "Internal publication state" above) — tested directly that no `internalPublicationState`/`state` key ever appears on a projection, since it was never merged into the record shape to begin with.

## Security/public-delivery boundary

Restated explicitly in this module's own doc comments, mirroring `registry.ts`'s (M3.1) original warning: `toPublicSafeProjection` and `isPublicArchiveEligible` are pure, per-record functions, **not** a substitute for query-level enforcement. A real future persistence/query layer must still apply `isPubliclyDiscoverable`/`isPublicArchiveEligible` *before* a record is ever loaded for public delivery, and apply `toPublicSafeProjection` before any record is ever serialized to a public client — "fetch everything, then filter client-side" remains the explicitly rejected anti-pattern. `selectPublicArchive`/`selectPublicComprehensiveView` never mutate their input array, confirmed directly, ruling out the specific footgun of accidentally exposing a shared, unfiltered records array by reference.

## Search/Index shared-source readiness

`selectPublicComprehensiveView` and `selectPublicArchive` both derive from the same single source (`isPubliclyDiscoverable`, M3.1) — no `isSearchable`/`isIndexable` divergent pair was created, directly satisfying Gate M3's "Search and Index query the same public source" criterion in advance of M3.10–M3.12's actual implementation. Neither Search ranking nor Index query/UI logic exists anywhere in this module, confirmed at the source level.
