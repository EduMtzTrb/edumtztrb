## Part A — Structural Composition Root

**Structural composition root — Mechanically Verified.** This part is accepted and is not being revisited; it is recorded here as the audit trail for the `DistrictShell` refactor.

### Phase 0 — Audit

1. **Existing shared district-shell infrastructure.** `src/components/shell/AppShell.tsx` (root shell: skip link, `GlobalNav`, persistent `WorldTrace`, single `#main-content` landmark) already exists and is unaffected by this task. `src/components/shell/DistrictNav.tsx` + `districtNavigation.ts` (M3.8) already implement the shared conceptual navigation order per district. No component named `DistrictShell` existed before this package (confirmed by exhaustive grep).
2. **Semantic scaffolding only.** None — every one of the nine conceptual layers M5.0 must support already has a real, tested implementation: `src/components/page-shells/PageShell.tsx` (`WorldThresholdShell`, `DistrictOverviewShell`, `CuratedViewShell`, `ComprehensiveViewShell`, `GroupingViewShell`, `UtilityPageShell`) and `CanonicalRecordShell.tsx` (M1.5); `Breadcrumb.tsx` / `orientation.ts` / `DirectEntryOrientation.tsx` (M3.9/M3.13); `RecordReturnControl.tsx`, `ThresholdLink.tsx`, `ThresholdIndicator.tsx`, `IndexPassageRestoration.tsx` (M4.6–M4.9, Return); `Trace.tsx` / `RecordTrace.tsx` (relationship passages).
3. **What was actually missing.** A single reusable composition root for district identity + district navigation. Before this package, `src/app/{work,research,lab,art,products,about}/layout.tsx` were six byte-for-byte identical bodies (`<div data-district="…"><DistrictNav district="…" />{children}</div>`), differing only by the district literal and page `<title>`.
4. **Composed, not replaced.** `DistrictNav` is reused unchanged. Every M1.5 page shell, `DirectEntryOrientation`, `Trace`, and every M4 Return/threshold component remain composed inside `children` at the page level, unchanged.
5. **Where naive duplication would occur.** Exactly the six duplicated `layout.tsx` files above — that fork is what this package removes.
6. **Smallest shared architecture.** One `DistrictShell({ district, children })` component, colocated with `AppShell`/`GlobalNav`/`DistrictNav` in `src/components/shell/`, owning only district identity (`data-district`) and district navigation. All other conceptual layers stay page-level, per source §5.4 ("standardizing the laws, not the expression").

**Contradiction check:** no conflict was found between any pair of governing documents on this topic — all agree on one shared shell/navigation logic, district variation by emphasis/density rather than structure, and no district-specific accent/token system. `docs/universes/*_UNIVERSE_v1.1.md` were individually checked; every district's homepage sequence maps onto the same threshold → curated → grouping → comprehensive → passage → return pattern (labels vary, order does not). Art's nested "Focused Encounter" state and Products' transactional page types are additive, page-level variations already anticipated by `CROSS_UNIVERSE_SYSTEM_REQUIREMENTS.md` (CUR-SPA-10, Products offer types) — neither requires a shell-level fork. About has no comprehensive-archive instance by design (`CUR-OWN-08`); the shell does not assume one exists (it never renders an archive slot itself, so nothing needed changing there).

One non-governing-document item was found and resolved rather than escalated: `tests/routes/district-navigation-wiring.test.ts` (M3.8) asserted literal source text in each `layout.tsx` pinning the pre-M5.0 duplicated implementation. Since M5.0's explicit objective is to replace that duplication, the test was updated to assert the equivalent guarantee (each layout hands `DistrictShell` its own correct district, and no layout hand-rolls its own nav/identity wrapper) against the new architecture, rather than treated as a frozen specification.

### Architectural Contract (Part A)

`DistrictShell` accepts exactly two things: `district: CanonicalOwnerDistrict` and `children: ReactNode`. It renders the `data-district` identity attribute and `DistrictNav`, then `children` unmodified. It introduces no new landmark, class, token, or district-conditional branching (no `if (district === "art")`), and it does not itself render or wrap threshold/curated/comprehensive/grouping/canonical/relationship/return/direct-entry content — those remain the page's own composition, using the already-approved M1.5/M3.9/M3.13/M4 components.

### Compositional Gap Audit

The question this audit answers is not "do the seven page-shell components exist" (they do — see Part A audit item 2) but whether they already share one coherent spatial grammar. They do not. Concretely:

- `.composition` (`src/styles/layout.css`, M2.3) is the platform's one shared 4/8/12 grid, but its own rule `.composition > * { grid-column: 1 / -1; }` makes **every** direct child span the full row — there is no mechanism anywhere in the repository for assigning a primary/peripheral role a different column span. `primitives.css`'s own comment confirms this was left open on purpose: "No content exists yet that needs a narrower span; a future component can opt into one explicitly... once real content requires it."
- `CanonicalRecordShell`'s optional regions (`context`, `evidence`, `metadata`, `relationships`, `credits`, `continuation`) are each rendered as a direct child of `.composition` — so today they all receive the same full-row `grid-column: 1 / -1`, with no shared-axis relationship, no dominant/peripheral distinction, and no density variation between them.
- `DistrictNav` (`src/styles/district-nav.css`, M3.8) used a fixed `padding: var(--space-2) var(--space-4)`, unrelated to `.composition`'s fluid `--margin-compact`/`--margin-medium`/`--margin-wide` tokens — so district navigation's left/right edge did not actually align with the content grid immediately below it. This is the one concrete "district navigation relationship to content" gap named in the compositional audit checklist.
- No mechanism existed for selective offset, density gradients, or peripheral latency anywhere in the codebase — these are DESIGN_SYSTEM.md v1.1 §11 concepts that, before this package, existed only in the Design System document, never in an implementable primitive.
- Semantic depth between foreground/relational/comprehensive layers is real (each page-shell type is a real, distinct component — see Part A), but nothing yet expresses the *spatial* relationship (shared axis, asymmetry, void) between a page's primary content and its own peripheral/relational content.

**Conclusion: not already implemented.** This is the actual remaining M5.0 scope, addressed below without duplicating any existing page shell.

### Compositional Contract

One new primitive, `DistrictField` (`src/components/composition/DistrictField.tsx`), plus one new stylesheet, `src/styles/district-composition.css`. Contract:

- Two semantic roles only: `primary` (required) and `peripheral` (optional). No district name, no per-district boolean (`isWork`/`isArt`/…) anywhere in the prop surface or the CSS.
- One shared, district-agnostic emphasis state: `density: "concentrated" | "moderate" | "dense"` — DESIGN_SYSTEM.md §11.7's own vocabulary (concentrated void / moderate information density / dense evidence), never a district identifier.
- `.district-field` is a **nested grid reusing the exact same column-count and gutter tokens as `.composition`**, at the same three breakpoints — this is what makes the primary/peripheral split share the platform's one architectural axis (§11.3) instead of inventing a second ratio system. No new breakpoint, margin, gutter, column-count, or color token is introduced anywhere in `district-composition.css` (mechanically enforced — see Validation).
- Below the 1024px breakpoint, both roles keep the inherited `grid-column: 1 / -1` and simply stack in DOM order — an ordinary consequence of the same grid mechanics, not a special compact-mode code path (§47 "lateral relationships may become vertical").
- At 1024px and above, each density value assigns a different dominant/peripheral column split and a different `row-gap` (using existing `--space-*` tokens only) — per §11.8, "No fixed dominant/peripheral ratio is approved," so the ratio is deliberately a function of the shared `density` state, not a single hardcoded constant. `density="dense"` additionally opens its peripheral zone one column early relative to `moderate`, a selective offset (§11.4 — "an ordinary part of the visual grammar... not automatically a Controlled Exception").
- `DistrictNav`'s horizontal padding (`src/styles/district-nav.css`) now reuses `--margin-compact`/`--margin-medium`/`--margin-wide` at the same breakpoints as `.composition`, closing the shared-axis gap named in the audit above.
- `DistrictField` never renders the CSS `order` property and never reorders its own children — `primary` is always the first DOM child, `peripheral` (an `<aside aria-label="Related">` complementary landmark) always the second, at every breakpoint and every density.

### Responsive Proof

Verified structurally (this repository has no browser test runner — see `tests/tokens/grid-contract.test.ts` for the same precedent on `.composition` itself):

- `district-composition.css` defines exactly two `min-width` breakpoints, 768px and 1024px — the same two already approved and used by `.composition`; no new breakpoint exists (mechanically enforced, see Validation).
- Below 1024px, `.district-field-primary`/`.district-field-peripheral` share one unconditional `grid-column: 1 / -1` rule (defined once, above every `@media` block) — both roles stack full-width, top to bottom, in the DOM order `DistrictField` always renders them in.
- At 1024px and above, the same two roles gain a partial `grid-column: span N` per density value — the *only* thing that changes between breakpoints is the column span, never the DOM order, never a swap between which role appears first.
- Fetched `/contact?composition-fixture=m5` from a locally running `next dev` server and confirmed via the raw HTML response that all three `data-density` values and all three `.district-field` instances render correctly server-side (mechanical confirmation that the route and markup are real, not a claim about rendered pixels at any specific viewport — that judgment is reserved for the human review below).

### Accessibility

- DOM order is primary-then-peripheral at every density and every breakpoint; `DistrictField` never sets the CSS `order` property (mechanically enforced, see Validation) — visual asymmetry can never diverge from reading/tab order.
- `peripheral`, when present, is a labeled `<aside aria-label="Related">` complementary landmark; when omitted, no peripheral element exists in the DOM at all (not merely hidden) — verified by `DistrictField.test.tsx`.
- No color, background, or Signal declaration exists anywhere in `district-composition.css` — density/role distinction is expressed structurally (grid position, landmark), never by color alone (mechanically enforced, see Validation).
- No motion, transition, animation, or transform exists anywhere in `district-composition.css` — the compositional grammar is static, so reduced-motion behavior is unaffected by construction, not by a separate reduced-motion rule (mechanically enforced, see Validation).
- No existing landmark, heading, or focus behavior was touched — `AppShell`, `GlobalNav`, `DistrictNav`'s DOM structure, `DistrictShell`, and every page shell remain byte-for-byte as Part A left them; only `DistrictNav`'s CSS padding changed (see Compositional Contract).

### Deferred to M5.1–M5.7

`DistrictField` establishes the shared spatial grammar's *mechanism* only — it does not itself decide which district page uses which density, what its real primary/peripheral content is, or the final dominant/peripheral ratio for any specific page type. Those are explicitly district-specific composition decisions, reserved for M5.1 (Home) through M5.7 (About), consistent with `DESIGN_SYSTEM.md` §69 ("Districts vary by degree rather than vocabulary") and this package's own instruction not to redesign any of the seven districts here. No page shell (`WorldThresholdShell`, `DistrictOverviewShell`, `CuratedViewShell`, `ComprehensiveViewShell`, `GroupingViewShell`, `CanonicalRecordShell`, `UtilityPageShell`) was modified to consume `DistrictField` in this package — that wiring, and the real content it would carry, belongs to the district packages that actually have real content to place.

2. Is there one coherent identity across the three states?
3. Are the states materially different without feeling like different websites?
4. Does the controlled asymmetry (primary vs. peripheral split) feel deliberate?
5. Is the void intentional rather than merely empty?
6. Are the shared axes (alignment between district navigation, primary content, and peripheral content) perceptible?
7. Does peripheral content feel secondary rather than arbitrarily displaced?
8. Are the density differences between the three states meaningful?
9. Does navigation remain clear at every state?
10. At ~390px, does the composition genuinely recompose (stack, reorder attention) rather than merely shrink?
11. With reduced motion enabled in the OS/browser, is the entire composition still meaningful? (Expected: unaffected — nothing here uses motion.)
12. Does anything look prematurely like a final Work/Research/Art design? (Expected: no — content is deliberately abstract fixture text.)

The user decides whether this shared spatial grammar is strong enough to become the basis for M5.1–M5.7. This document does not answer that question.
