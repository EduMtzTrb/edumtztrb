## Plane

**Implemented — established, not yet applied.** `.plane` in `primitives.css`: `background: var(--color-graphite-800)`, `border: var(--line-hairline) solid var(--color-graphite-700)`, `border-radius: var(--radius-control)`, `padding: var(--space-4)`. No shadow, no transparency — a restrained rectangle, not a card.

**Why `color-graphite-800`, not a new `surface-content` token:** §95's suggested name (`surface-content`) was already deliberately not added during Implementation-Readiness Reconciliation, and remains not added now — no current content needs it enough to justify guessing its exact hex value, and "do not create tokens merely because a concept has a name in prose" is this task's own explicit instruction. `color-graphite-800` is already an approved, already-resolved neutral (§10.2) one step lighter than the Dark Field (`color-void-1000`) — reusing it for local separation is a defensible composition of existing authority, not an invented value.

**Why not applied to any shell:** §17.4 itself: "Many compositions should remain field + content without intermediate panels." No current shell (all seven are still just a heading on the field) has evidence, comparison, or transaction content that needs local separation. Forcing `.plane` onto a heading-only page would be exactly the "card proliferation" §17.9 prohibits. Ready for the first component that genuinely needs it.

## Line

### Structural

**Implemented.** `.line-structural`: `border-block-end: var(--line-hairline) solid var(--color-graphite-700)`. §16.1 describes this family as "quiet, continuous, non-directional, subordinate" — the *lightest* available physical weight (`line-hairline`, 1px) fits that description directly, and matches the shell's own already-existing header-divider treatment.

### Hierarchy

**Implemented.** `.line-hierarchy`: `border-block-end: var(--line-emphasis) solid var(--color-graphite-500)`. §16.2: "stronger than ordinary structural separation... use sparingly, spacing should perform most grouping work." Shares the 2px `line-emphasis` weight with the shell's existing focus ring — deliberately not a new fourth physical weight — distinguished from focus by color (neutral gray here vs. `color-focus` there), which §94 explicitly permits ("implementation may alias physical values where testing shows two roles can share weight/color, but semantic distinction must remain").

No duplicate primitive was created.

## Frame

**Implemented — established, not yet applied.** `.frame`: `border: var(--line-structural) solid var(--color-graphite-700)`, `border-radius: var(--radius-control)`. Deliberately reuses `line-structural` (3px) — the Design System's own "rare role, 3px max" physical weight (§12.1 of the original v1.0 line-weight table, confirmed still resolved and unaffected by v1.1) — for a boundary decisive enough to mark real extent, distinct from the lighter Structural-*line* family above. This resolves a naming coincidence cleanly: the token `line-structural` (a *physical weight*) backs the **Frame** primitive, not the semantic **Structural line family** (which uses `line-hairline` instead, per its own "quiet/subordinate" character) — same token name, different primitive, justified by weight-to-character fit rather than name-matching alone.

Not applied to any current shell — none has media, evidence, or an inspection region with real extent to mark yet. Wrapping a whole `<main>` in `.frame` would be exactly the "universal card" §12/§18 prohibit.

## Void

**No new implementation — already complete via M2.3.** This task's own Step 13 anticipates exactly this outcome: "determine whether Void needs a semantic class, a compositional permission, or no new implementation at all because the existing Field + spacing system already expresses it." It does: `.composition`'s unforced column occupancy ("the grid provides alignment without requiring occupancy," §14.3 — unoccupied columns are latent/peripheral capacity by construction) and `.field-interval`'s fluid compositional breathing room (§13.3, §15.3) together already express architectural void completely. Nothing was added; nothing was duplicated.

## Signal

**Fully deferred — no token, no class, no visual instantiation.**

Reasoning, precisely: §8.2 leaves "exact chromatic values... implementation-calibrated" — but calibration requires *something real to calibrate against*, and Signal's own definition (§8: "meaningful connection, branching possibility, active/revealed authorship relationship/intervention," DS-111/112) requires real relational content to mean anything at all. No such content exists anywhere in this repository. §8.1/DS-113 explicitly prohibit Signal substituting for "ordinary hover, active navigation, selection, focus, CTA, purchase action, validation, success, warning, error, generic availability, disabled state" — every one of which is the *only* kind of interactive surface currently in this codebase (nav links, skip-link focus). Instantiating Signal anywhere right now would have nothing legitimate to attach to and would necessarily misuse it as exactly the kind of generic accent §8.1 forbids.

This task's own Step 15 anticipated this and gave explicit instructions for it: "If no real semantic Signal situation exists in the current application, do not fabricate one simply to visually test the token. In that case: define the semantic implementation contract, resolve only what can be resolved responsibly, document what awaits first real relational usage." That is exactly what happened — the semantic contract is the one already written in `DESIGN_SYSTEM.md` §8; nothing further was resolved; this document records what's awaited (real canonical-relationship data, Milestone 7+).

**This did not require stopping for a design-decision review** — no identity-level choice was made or needed to be made. The decision was to make *no* choice, which is not a convention-setting act; it is the same deferral pattern already applied to `color-disabled`, layer-order numerics, and opacity numerics.
