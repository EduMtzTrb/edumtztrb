## Frame

**Implemented, calibrated once after human visual review — established, not yet applied.**

**Initial treatment (rejected):** `border: var(--line-structural) solid var(--color-graphite-700)` — reusing `line-structural` (3px), the Design System's own "rare role, 3px max" physical weight (§12.1 of the original v1.0 line-weight table). The reasoning at the time was that Frame should read as more decisive than the Structural line family, and 3px was the heaviest approved weight available. Human visual review at desktop and ~390px mobile found this too strong: it read as a pronounced boxed container, and the effect became more apparent at mobile width; combined with Plane, it began to approach generic panel/card UI — exactly what §12/§18's "must not become universal card / decorative picture border / generic hero frame" prohibits.

**Calibrated treatment (current):** `border: var(--line-hairline) solid var(--color-graphite-700)` — the smallest approved physical weight, per the review's own explicit guidance ("prefer the smallest existing approved line/geometry treatment... if `line-hairline`... provides the appropriate restrained Frame behavior, reuse it"). Frame now shares its exact weight with the Structural line family, and stays visually distinct from a single Structural line not by being heavier, but by being a full four-sided boundary with radius, marking an actual extent, rather than one edge marking a region separation. `line-structural` (3px) was not deleted or altered — it remains fully resolved in `src/styles/tokens/geometry.css`, available for whatever future, separately-justified semantic use genuinely needs a heavier weight; it is simply no longer Frame's default.

Not applied to any current shell — none has media, evidence, or an inspection region with real extent to mark yet.

## Signal

**Fully deferred — no token, no class, no visual instantiation.**

Reasoning, precisely: §8.2 leaves "exact chromatic values... implementation-calibrated" — but calibration requires *something real to calibrate against*, and Signal's own definition (§8: "meaningful connection, branching possibility, active/revealed authorship relationship/intervention," DS-111/112) requires real relational content to mean anything at all. No such content exists anywhere in this repository. §8.1/DS-113 explicitly prohibit Signal substituting for "ordinary hover, active navigation, selection, focus, CTA, purchase action, validation, success, warning, error, generic availability, disabled state" — every one of which is the *only* kind of interactive surface currently in this codebase (nav links, skip-link focus). Instantiating Signal anywhere right now would have nothing legitimate to attach to and would necessarily misuse it as exactly the kind of generic accent §8.1 forbids.

This task's own Step 15 anticipated this and gave explicit instructions for it: "If no real semantic Signal situation exists in the current application, do not fabricate one simply to visually test the token. In that case: define the semantic implementation contract, resolve only what can be resolved responsibly, document what awaits first real relational usage." That is exactly what happened — the semantic contract is the one already written in `DESIGN_SYSTEM.md` §8; nothing further was resolved; this document records what's awaited (real canonical-relationship data, Milestone 7+).

**This did not require stopping for a design-decision review** — no identity-level choice was made or needed to be made. The decision was to make *no* choice, which is not a convention-setting act; it is the same deferral pattern already applied to `color-disabled`, layer-order numerics, and opacity numerics.
