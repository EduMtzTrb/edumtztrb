## Selection Semantic Model

Two independent concepts, per the Plan's own M2.5/M2.6 split and `DESIGN_SYSTEM.md v1.1` §21.1 ("Selection, active route, focus, and Signal are distinct concepts"):

- **Action** (M2.5) — performs an operation. A native `<button>` or a navigating `<a>`.
- **Selection** (M2.6) — expresses a current choice, active view mode, or filter criterion. Never a `.action-primary`/`.action-secondary` visual treatment; each primitive below has its own class family in `src/styles/selection.css`, independent of `controls.css`.

Pressed, selected, active-route, focus, disabled, and Signal remain six independent states — no primitive in this package collapses any two of them into one visual signal.

## Selected-State Redundancy

The Plan's own non-negotiable rule: **"Selected state must use more than color alone."** Applied per primitive (all in `src/styles/selection.css`, all protected by `tests/tokens/selection-contract.test.ts`'s "governing rule" test):

| Primitive | Color channel | Non-color channel(s) |
|---|---|---|
| Tab | text + border color | font-weight (600) |
| Segmented option | background fill | font-weight (600) |
| Filter toggle | border color | filled marker box (shape/presence) + font-weight |
| Checkbox | filled box | explicit checkmark shape (`::after`, rotated border) |
| Radio | border color | filled inner dot (`::after`) |

Select and StatusTag have no ambiguous "selected-but-same-shape" state to protect (native `<select>`'s chosen option is the browser's own affordance; StatusTag is never selectable). RemovableFilter isn't a toggle — it has no unselected variant to distinguish from.

## Tabs

`src/components/selection/Tabs.tsx` — a compound `Tabs`/`TabList`/`Tab`/`TabPanel` API (smallest coherent shape for a real tablist/tabpanel relationship): `Tabs` provides `{ value, onChange }` plus a `useId()`-derived id namespace via context; `TabList` renders `role="tablist"` with an `aria-label` and owns arrow-key roving focus; `Tab` renders `role="tab"` with `aria-selected`, `aria-controls`, and roving `tabIndex` (0 on the selected tab, -1 on the rest); `TabPanel` renders `role="tabpanel"` with `aria-labelledby` and the native `hidden` attribute on every panel but the selected one. Keyboard: ArrowLeft/ArrowRight/Home/End move focus and activate (automatic-activation model, ARIA APG tablist pattern) — implemented directly since no dependency exists in this repository to provide it. Selected tab is exposed via `aria-selected="true"` and is visually distinct through a bottom border plus `font-weight: 600` (see **Selected-State Redundancy**), not color alone. No production consumer exists — implemented and tested standalone (`Tabs.test.tsx`), the same posture M2.5 took for `Action`/`ActionLink` before any page needed them.

## Segmented Views

`src/components/selection/SegmentedView.tsx` — a mutually-exclusive view-mode selector built on a **native radio group** (`<fieldset role="radiogroup"><legend>` + visually-hidden `<input type="radio">` per option), not a hand-rolled ARIA composite widget — native keyboard behavior (arrow-key roving, space/click activation) comes free from the browser rather than being reimplemented, per this package's "native behavior first" instruction. No actual public view mode is invented to demonstrate it (e.g. no fake "visual/compact" toggle wired into a real page) — the primitive is implemented and tested standalone (`SegmentedView.test.tsx`). Distinguished from Tabs (no tabpanel relationship — a segmented view changes a mode, it doesn't switch between two rendered panels) and from Filter/CTA (no `aria-pressed`, no action-level styling).

## Filters

Two distinct primitives, matching the Plan's separate mentions of "filters" and "removable filters":

- **`FilterToggle.tsx`** — the selectable-criterion control: a native `<button type="button" aria-pressed>`, never an `Action`. Selected state is border color + a filled marker box + font-weight (see table above) — deliberately not `.action-primary`, so a selected filter never reads as a CTA (§31/§85). Owns the control only — no result-set recomposition, no URL/query state, no persistence (all M3.11).
- **`RemovableFilter.tsx`** — represents one *already-applied* criterion plus its removal affordance: a text label (`.removable-filter-label`) next to a real `Action` (`level="tertiary" iconOnly`) for the remove control. This is the one place in this package that legitimately reuses an M2.5 `Action` — the remove button is a genuine state-changing operation, and only that small control gets action styling, not the surrounding chip, so the token as a whole does not read as a CTA. The accessible name is `"Remove {criterion}"`, containing the criterion text itself, per this package's explicit accessibility requirement.

Neither implements reset, canonical-URL changes, or query-state persistence — all explicitly out of scope, owned by M3.11.

## Checkboxes

`src/components/selection/Checkbox.tsx` — a native `<input type="checkbox">` wrapped directly in its own `<label>` (implicit label association — no generated `id`/`htmlFor` bookkeeping needed). The input is visually hidden via `.visually-hidden-input` (the standard "clip-to-1px, never `display:none`" technique) so it stays in the accessibility tree, focusable and keyboard-operable exactly like an unstyled checkbox; a decorative `aria-hidden` sibling span draws the box, and checked state adds both a fill and an explicit rotated-border checkmark shape (see table above). Disabled reuses `--opacity-disabled` (M2.5's resolved token) on both the box and label text, plus the native `disabled` attribute.

## Radios

`src/components/selection/RadioGroup.tsx` — the same native-input-plus-decorative-sibling technique as Checkbox, applied to a real `<fieldset role="radiogroup"><legend>` group of same-`name` `<input type="radio">`s, so mutual exclusivity is a genuine native guarantee, not simulated. Checked state is a border-color change plus a filled inner dot (`::after`, using `--radius-circle` — see **Geometry**). Focus and disabled follow the same pattern as Checkbox.

## Selects

`src/components/selection/Select.tsx` — a plain native `<select>`, not a custom combobox (no genuine requirement here justifies reimplementing one). Provides a `<label htmlFor>` (generated `id` via `useId()` when the caller doesn't supply one), `.select` for geometry/border/focus-visible/disabled, and passes through all native `<select>` props/behavior/option semantics untouched. No validation, guidance, required-state, or confirmation UI — that's M2.10's Form family.

## Status Tags

`src/components/selection/StatusTag.tsx` — a plain, non-interactive `<span>` (no button/link semantics, no `onClick` prop in its type surface at all) rendering explicit text inside a single restrained neutral treatment (hairline border, `--radius-control`, `--color-mist-300` text). Deliberately **not** a hue-per-lifecycle-state system — no `tone`/`variant` enum exists yet, since building one now would preempt M2.11's full shared static-state model before this package has any real lifecycle content to apply it to. This is the minimal reusable primitive the Plan's M2.6 line asks for; the color taxonomy is explicitly M2.11's to design.

## Removable Filters

Covered under **Filters** above (`RemovableFilter.tsx`) — kept together there since the Plan's Filter/Removable-filter split is really "criterion selector" vs. "already-applied criterion representation," not two unrelated primitives.

## Filter vs Lens Boundary

`INFORMATION_ARCHITECTURE.md` §9.1/§9.3 and `DESIGN_SYSTEM.md v1.1` §31/§85 are explicit: a Filter narrows the current view and never creates a canonical record, content type, or curatorial judgment; a Lens is a stable named structural perspective (district/content-type/discipline/theme/year) with its own navigable route. `IMPLEMENTATION_PLAN.md`'s M2.6 line names only "filters," not lenses — so **no Lens component is added by this package**. `FilterToggle`/`RemovableFilter` are labeled and documented as Filter-family primitives only; nothing here presents a Lens as interchangeable with a filter, and nothing here gives a Filter route-like visual weight. A future Lens primitive (if ever built) may reuse the same underlying selection *mechanics* (a toggle/selected-state control), but per §31/§85 must carry its own distinct label/semantics, not this package's Filter labeling.

## M3.11 Filter Boundary

Not implemented, correctly: visible active-filter *result-set* state, reset architecture, canonical-URL/query persistence, or any Search/Index integration. `FilterToggle`/`RemovableFilter` are controlled components — the consumer owns `selected`/`value`/`onRemove`; no internal state model simulates real filtering. All of that is explicitly M3.11's, per this package's own instruction.

## M2.11 Status Boundary

Not implemented, correctly: loading/empty/sparse/no-result/unavailable/archived/error/success/confirmation/restricted-unpublished as distinct StatusTag variants. `StatusTag` is the single neutral primitive; the full static-state system (with whatever real visual differentiation each of those ten states eventually needs) is M2.11's to design against real content.

## Typography

No new typography role. Every primitive applies an existing M2.2 `.type-*` class (`.type-label` for Tab/segmented-option-label/FilterToggle-via-Action; `.type-body` for Checkbox/Radio label text and Select's `<select>` itself; `.type-caption` for StatusTag, Select's `<label>`, and both fieldset `<legend>` elements) — `selection.css` itself sets no `font-family`/`font-size`/`font-weight` base value, only the `font-weight: 600` selected-state emphasis noted above. No forced uppercase, no default Mono.

## Geometry

`--radius-control` (2px, already-resolved) on every rectilinear control surface (`.segmented-view-options`, `.filter-toggle`, `.select`, `.status-tag`, `.removable-filter`) — the same value M2.5's controls already use, no new radius introduced. The one deliberate exception is `.radio-dot`, which uses `--radius-circle` (already-resolved, geometry.css) for its genuinely circular marker — an expected native-radio affordance, not part of the pill/capsule language the Plan explicitly prohibits; `tests/tokens/selection-contract.test.ts` checks these two facts separately rather than banning `--radius-circle` outright. No `9999px` literal, no capsule tab/filter geometry anywhere.

## Focus

Every interactive family (`Tab`, segmented option, `FilterToggle`, `Checkbox`, `Radio`, `Select`) exposes `:focus-visible`. Five of the six reuse the shared shell outline **byte-for-byte** (verified by string-equality assertion in `selection-contract.test.ts`, the same technique `controls-contract.test.ts` uses for M2.5). The segmented option is the one calibrated exception: because segmented options sit flush against each other inside a shared bordered container with no external margin, an outward `2px` offset would clip against the neighboring option or the container edge, so it uses the identical outline weight and color with an inward `outline-offset: -2px` instead — same mechanism, offset direction adapted to this control's specific box model. Focus remains visually independent of selected/checked/pressed state in every rule (no selector combines `:focus-visible` with `:checked`/`[aria-selected]`/`[aria-pressed]`).

## Disabled State

Every primitive that supports it (`FilterToggle`, `Checkbox`, `Radio`, `Select`) reuses `--opacity-disabled` (M2.5's resolved token) plus the native `disabled` attribute — no second disabled model, no new opacity role resolved by this package. `Tab` does not expose a `disabled` prop (no real consumer needs a disabled tab yet, and the Plan doesn't require one); adding it speculatively would be exactly the "build ahead of a real consumer" pattern this project has consistently avoided.

## Signal Exclusion

`src/styles/selection.css` contains no `.signal`, `--signal`, or `--color-signal` reference anywhere — asserted by `selection-contract.test.ts`. No selected/checked/pressed/hover/focus state in this package uses an accent color; every one uses the tonal/structural channels in the **Selected-State Redundancy** table.

## Component Architecture

Eight small, independently-testable modules under `src/components/selection/`: `Tabs.tsx`, `SegmentedView.tsx`, `FilterToggle.tsx`, `Checkbox.tsx`, `RadioGroup.tsx`, `Select.tsx`, `StatusTag.tsx`, `RemovableFilter.tsx` — plus one shared stylesheet, `src/styles/selection.css`. No shared base "SelectionControl" abstraction was introduced: each primitive's DOM/ARIA shape is different enough (compound-context Tabs vs. plain-props everything else) that a forced common wrapper would cost more than it would save, consistent with this project's standing "no premature abstraction" instruction. No new dependency was added.

## Controlled vs Uncontrolled State

Every primitive with a meaningful "current selection" (`Tabs`, `SegmentedView`, `FilterToggle`, `RadioGroup`) is a fully controlled component (`value`/`selected` + `onChange`/`onClick`) — the consumer owns the state, matching the instruction that components expected to eventually reflect external filter/view state should be controlled rather than managing hidden internal state now. `Checkbox` and `Select` accept the same native controlled/uncontrolled duality any plain `<input>`/`<select>` would (no extra behavior added). No Redux/Zustand/context-based global state, no URL-state infrastructure — `Tabs`'s only internal context is the id-namespace plumbing a compound component needs to wire `aria-controls`/`aria-labelledby` together, not application state.

## Accessibility

- **Native semantics first:** real `<button>`, `<input type="checkbox">`, `<input type="radio">`, `<select>`, `<fieldset>`/`<legend>` everywhere one applies — no decorative div pretends to be a form control.
- **Programmatic state:** `aria-selected` (Tab), native `checked` (segmented radio, Checkbox, Radio), `aria-pressed` (FilterToggle) — all exposed per §65, all asserted in each component's tests.
- **Keyboard:** native for Checkbox/Radio/Select/segmented-radiogroup; explicit ArrowLeft/ArrowRight/Home/End roving-focus implementation for Tabs (tested in `Tabs.test.tsx`).
- **Labeling:** `TabList`'s `aria-label`, `RadioGroup`/`SegmentedView`'s `<legend>`, `Checkbox`/`Radio`'s wrapping `<label>`, `Select`'s `<label htmlFor>`, `RemovableFilter`'s `"Remove {criterion}"` accessible name.
- **Disabled:** native `disabled` attribute throughout (never `aria-disabled` alone, since every disabled-capable primitive here has a real native disabled state available).
- **44×44 target:** `Tab`, `FilterToggle`, `Checkbox`, `Radio`, `Select` all carry `min-height: 44px` (asserted in `selection-contract.test.ts`); `Checkbox`/`Radio`'s clickable region is the entire label (text + visual box), not just the small decorative marker.
- **Selection not color-dependent:** see **Selected-State Redundancy** table.
- **No hover dependency:** every state (selected/checked/pressed/disabled) is fully legible and operable with hover never touched — hover only adds a restrained opacity dim, same as M2.5.
- **Zoom/reflow:** no fixed-width container, no viewport-dependent rule anywhere in `selection.css` (same posture as `controls.css`).
