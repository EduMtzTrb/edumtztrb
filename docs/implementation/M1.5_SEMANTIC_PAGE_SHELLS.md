## M1.4 Accessibility Correction

Per this task's explicit instruction to verify M1.4's active-context semantics before starting M1.5: `GlobalNav.tsx` previously used `useSelectedLayoutSegment()`, which only returns the *first* route segment under root. On a deep route like `/work/selected`, this made the "Work" link receive `aria-current="page"` — which is semantically wrong per WAI-ARIA: `aria-current="page"` means "this link's href is the current document," and `/work` is not the current document when the visitor is actually on `/work/selected`. This falsely told assistive technology the visitor was on the district overview when they were actually on a curated sub-view.

**Fix:** switched to `usePathname()` (still the one Client Component boundary; no new boundary was introduced) and a small two-tier comparison:

```ts
function currentState(pathname: string, href: string): "page" | "true" | undefined {
  if (pathname === href) return "page";
  if (href !== "/" && pathname.startsWith(`${href}/`)) return "true";
  return undefined;
}
```

- **Exact match** (`pathname === href`, e.g. on `/work` itself) → `aria-current="page"` — the correct ARIA 1.2 token for "this is the current document."
- **Containing section, not the exact page** (e.g. on `/work/selected`, `/work/some-entry`, or any route nested under `/work/`) → `aria-current="true"` — ARIA 1.2 §6.9's own generic token for "current item... when no more specific value applies," which is exactly this case (there is no ARIA-current token for "ancestor section").
- Neither → `aria-current` omitted entirely, same as before.

The existing non-color visual cue (underline + font-weight, `.global-nav-list a[aria-current="page"], … a[aria-current="true"]` in `src/styles/shell.css`) was extended to fire on both values, so the visitor still sees the same "you are in Work" indication at any depth — this is a semantic correction, not a visual redesign. Verified directly in built HTML: `/work` → `aria-current="page"`; `/work/selected` and a live-rendered `/work/some-project` (dynamic) → `aria-current="true"`; `/index/theme/architecture` (a deep Index lens) → `aria-current="true"` on "Index," not "page." No other part of M1.4 was touched.

## Semantic Shell Architecture

Two files under `src/components/page-shells/`:

- **`PageShell.tsx`** — one small internal primitive (`pageType`, `heading`, optional `district` for Home's special case) plus six thin, individually-named exported wrappers: `WorldThresholdShell`, `DistrictOverviewShell`, `CuratedViewShell`, `ComprehensiveViewShell`, `GroupingViewShell`, `UtilityPageShell`. Each renders `<main data-page-type="...">` containing a `<header><h1>{heading}</h1></header>` — nothing more, because nothing more is structurally justified yet for these six types (their §6 purposes describe regions — curated foreground, archive listing, grouping explanation — that don't exist until real content does; adding empty containers for them now would violate this task's explicit "no empty decorative containers" instruction).
- **`CanonicalRecordShell.tsx`** — kept separate because its structural obligation is explicitly larger: this task requires it to "structurally allow future representation of: identity, public state, context, authorship/role, primary content/evidence, metadata, credits, relationships, continuation/open edge." It accepts `heading` (required) plus eight optional `ReactNode` props matching that exact list — `publicState`, `authorship` (rendered inside `<header>`, alongside the identity they qualify), and `context`/`evidence`/`metadata`/`relationships`/`credits`/`continuation` (each its own `<section aria-label="…">`, or `<nav aria-label="Continuation">` for the last, matching CUR-NAV-08's framing of Previous/Next as navigation). Every optional region is conditionally rendered — omitted entirely, not rendered empty — so today, with no district content model wired up, every canonical-record page renders exactly `<main><header><h1>…</h1></header></main>`, identical in weight to the other six shells, while the component's own type signature already documents the full future obligation.

Both files were composed, not duplicated, into "a small set of meaningful structural families" (7 exported components, 1 shared internal primitive) rather than one generic component with many props (rejected: would have hidden which regions apply to which type) or one component per route (rejected: 53 near-identical files would have obscured the 7 real structural families this task asked for).
