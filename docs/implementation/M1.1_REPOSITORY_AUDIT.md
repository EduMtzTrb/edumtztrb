## Contradictions or Specification Gaps

This task's own instructions state that `IMPLEMENTATION_PLAN.md v1.0` and `PLATFORM_SPECIFICATION.md v1.0` are part of the "Mandatory Source-of-Truth Reading" and are "complete and Approved," and that `DESIGN_SYSTEM.md v1.0` and `ANIMATION_SYSTEM.md v1.0` are approved documents.

At the point this audit began, none of the four documents existed under those names anywhere in the repository (root, `docs/`, or `PLATFORM.zip`) — only `DESIGN_SYSTEM.md` and `ANIMATION_SYSTEM.md` existed, and both were self-declared `Proposal` status at version `0.1`. Partway through the audit, four new, differently-named files appeared in the repository root: `IMPLEMENTATION_PLAN_v1.0.md`, `PLATFORM_SPECIFICATION_v1.0.md`, `DESIGN_SYSTEM_v1.0.md`, and `ANIMATION_SYSTEM_v1.0.md`, each self-declaring `Status: Approved`, `Version: 1.0`. This resolves the original "document does not exist" gap, but introduces new, unresolved gaps that this audit is reporting rather than resolving:

1. **Filename mismatch with no archival step.** The canonical filenames `DESIGN_SYSTEM.md` and `ANIMATION_SYSTEM.md` still point at the old `Proposal`/`0.1` content. The new `Approved`/`1.0` content lives at different filenames (`DESIGN_SYSTEM_v1.0.md`, `ANIMATION_SYSTEM_v1.0.md`) instead of replacing the canonical file, with the old version moved to an archive — which is the pattern this same repository already used for the Universe documents (old versions moved to `docs/archive/universes/`, current version at `docs/universes/*_v1.1.md`, with a README pointer). No such archival or pointer exists yet for `DESIGN_SYSTEM.md`/`ANIMATION_SYSTEM.md`, so two documents with the same title and materially different approval status now coexist at the root, and nothing in the repository states which filename implementation should treat as authoritative going forward.
2. **The new documents are untracked in Git.** `IMPLEMENTATION_PLAN_v1.0.md`, `PLATFORM_SPECIFICATION_v1.0.md`, `DESIGN_SYSTEM_v1.0.md`, and `ANIMATION_SYSTEM_v1.0.md` are all outside version control as of this audit. An "Approved" governing document that exists only as an untracked working-tree file is not yet a durable part of the project history.
3. **`IMPLEMENTATION_PLAN_v1.0.md` §2.1 ("Governing source set") itself lists `PLATFORM_VISION.md v1.0` and `INFORMATION_ARCHITECTURE.md v1.0` as governing documents, but no `v1.0` file exists for either — only the root `PLATFORM_VISION.md` and `INFORMATION_ARCHITECTURE.md`, both still self-declared `Proposal` status at version `0.1`, were found** (verified by searching the full repository for any `PLATFORM_VISION*` or `INFORMATION_ARCHITECTURE*` filename). This is a contradiction inside the newly-arrived governing document set itself, not just between the task prompt and the repository, and it was not resolved by this audit.
4. `ANIMATION_SYSTEM_v1.0.md`'s header states `Status: Approved`, `Version: 1.0`, but — unlike `DESIGN_SYSTEM_v1.0.md`, `PLATFORM_SPECIFICATION_v1.0.md`, and `IMPLEMENTATION_PLAN_v1.0.md` — it does not include an explicit `Approved:` date in its header.

Per `AGENTS.md`'s "Handling Ambiguity" rule (implementation must stop rather than silently resolve an incomplete or contradictory specification) and this task's own Stop Conditions, these gaps are reported here rather than resolved unilaterally. In particular, this audit did **not**:
- delete, rename, move, or archive `DESIGN_SYSTEM.md`/`ANIMATION_SYSTEM.md` in favor of the `_v1.0` files, even though that appears to be the intended outcome;
- stage or commit the four new files on the repository's behalf;
- guess at, or invent, `PLATFORM_VISION_v1.0.md` / `INFORMATION_ARCHITECTURE_v1.0.md` content to resolve gap #3 above.

The Routing Baseline and Approved-Plan Mapping sections above were, however, updated to use `PLATFORM_SPECIFICATION_v1.0.md` and `IMPLEMENTATION_PLAN_v1.0.md`'s actual content once those files appeared, since reading an existing document to describe verified repository state is inspection, not a design decision.

## Risks for M1.2

- `IMPLEMENTATION_PLAN_v1.0.md` §6 defines **M1.2 — "Environment baseline"** explicitly: runtime declaration, lockfile consistency, an environment-variable example, local setup instructions, and deterministic build scripts — "do not add speculative services." That work package does not itself depend on `DESIGN_SYSTEM.md`/`ANIMATION_SYSTEM.md` content, so the filename/archival ambiguity around those two documents (**Existing Issues** #1) does not need to block M1.2 starting.

M1.2 as scoped above is not the work package affected by issues #1–#3 in **Existing Issues**, but Milestones 2 and 5 (System Primitives; District Framework), which do depend on Design/Animation System content, are.
- The four newly-arrived governing documents being untracked in Git (**Existing Issues** #2) is a risk regardless of which task comes next: any implementation work that cites them as "approved" is citing files that are not yet part of the project's committed history and could be altered or lost before being committed.
- The uncommitted documentation reorganization (deleted root `*_UNIVERSE.md` files, new `docs/` tree, modified `PROJECT_STATE.md`) should be resolved (committed or explicitly reviewed) before more untracked change accumulates on top of it.
