## Root Cause

Determined by direct code audit — Claude did not have live-browser access for this diagnosis either, but the mechanism is deterministic and does not require one to confirm.

`ThresholdIndicator` was a **conditionally mounted** component: it returned `null` whenever no genuine passage was detected, and mounted a brand-new `<p data-threshold-state="first-entry">…</p>` node only once a passage was detected. A freshly inserted DOM node has no prior computed value for any of its own CSS properties — a `transition: opacity …` rule declared on it therefore has nothing to transition *from*. The browser paints the node directly at its final, resting value (`opacity: 1`) in a single frame. The declared transition was real, was correctly token-driven, and was mechanically testable (source contract) — and still never visually fired, in any real browser, because the element it was attached to never existed in an intermediate state. (This repository does not use the newer `@starting-style` CSS feature that exists specifically to give a freshly-inserted node a "before" value — a deliberate choice carried over from M4.5's own documented reasoning — so that escape hatch was never available here.)

Two compounding factors made the failure total rather than partial:

1. **No shared geometry.** The only visual channel was `opacity` on a small block of explanatory text. Nothing about Home's layout and nothing about Work's layout was visually connected — there was no shared element for a viewer's eye to track across the navigation, so even a working opacity fade would only have faded *in new, unrelated text*, not communicated "this is the same world."
2. **No persistence across the route change.** `ThresholdIndicator` lived inside each page's own component tree. `/` and `/work` share no layout beyond the root `AppShell` — React (via Next's App Router) fully unmounts one page's tree and mounts the other's on navigation. Even if `@starting-style` had been used, there would still have been a genuinely *different* DOM node on each side of the navigation, not one continuous element.

The prior report's "Reduced motion: not applicable" framing for M4.8 and this package's own original "declared but not exercised" transition were, in hindsight, the same class of risk this review has now confirmed as an actual defect for M4.9 specifically: a token-correct, source-contract-passing transition that a real browser never plays.

## Calibration Architecture

The fix is **persistence, not a new effect or a richer animation**. A single new component, `WorldTrace` (`src/components/threshold/WorldTrace.tsx`), is mounted once inside `AppShell` (`src/components/shell/AppShell.tsx`) — the one layout level that genuinely survives every Home ↔ Work navigation, since `/` and `/work` share no other common layout. `WorldTrace` is never conditionally mounted or unmounted; it always renders the same wrapper and segment, and only its own `data-trace-position`/`data-trace-mode` attribute values change in response to the real, current pathname. Because the element itself never disappears, a CSS `transition` on it has a real prior value to animate from on every route change — the exact property whose absence caused the original failure.

`WorldTrace` reads `usePathname()` (the same hook `GlobalNav` already uses for its own active-state detection) to resolve one of three positions — `"home"`, `"work"`, or `"elsewhere"` — via a small, deliberately narrow `resolveTracePosition` function that recognizes only the Home ↔ Work boundary. It is **not** a general route-transition manager: it intercepts no navigation, delays nothing, creates no history stack, and has no awareness of any route beyond `/` and `/work` (every other route simply recedes to the same subdued "elsewhere" presentation). It can be generalized or replaced entirely during Milestone 5 without touching any M4 authority.

First/repeated mode is derived the same way `ThresholdIndicator` already derives its own state: `useSyncExternalStore` reading `hasTraversedThreshold(HOME_WORK_THRESHOLD_KEY)`, a **pure, read-only** call — `WorldTrace` never writes this flag; the write remains `ThresholdIndicator`'s own unchanged responsibility, in its own effect, after commit. Because `hasTraversedThreshold` is monotonic for the session, no separate "did a crossing just happen" bookkeeping is required: on the render that first paints `position="work"`, the previous crossing's mark has not yet been written (that write happens in a sibling component's effect, after this same commit), so the snapshot correctly still reads "first"; on any later crossing, the prior effect has already run, so it correctly reads "repeated."

A first implementation attempt tracked "did a genuine crossing just happen" with two `useRef`s mutated directly in the render body, on the understanding that ref mutation (unlike `setState`) is React's own documented exception to "don't do this during render." Running `npx eslint` against the new file proved that assumption wrong for this specific repository: the `react-hooks/refs` rule in this project's ESLint config forbids reading **or** writing `ref.current` during render outright, with no carve-out for this pattern. Rather than fight the rule, `WorldTrace` was rewritten to avoid refs entirely — the `useSyncExternalStore` design above needs no ref, no `useState`, and no `useEffect` at all, and passes `npx eslint` with zero errors or warnings.

## Shared Spatial Trace

`WorldTrace` renders one architectural, rectilinear structural element — a thin horizontal segment (`.world-trace-segment`, height `var(--line-emphasis)`, the same hairline-emphasis token already used elsewhere in the design system) positioned along one edge of the shell, between the global header and the page content. It is **not** a decorative graphic, not a district logo, palette shift, portal, or particle system, and does not depict a literal doorway — it is a stable, rectilinear boundary marker, one of this task's own explicitly preferred forms ("shared structural axis … persistent line … restrained field edge … other already-approved rectilinear structural cue"). Signal (M4.4) is not reused or referenced — this is new, narrowly scoped structure, not an existing system repurposed outside its own meaning.

At Home, the segment sits flush left (`translateX(0)`); at Work, it translates to the opposite edge (`translateX(calc(100% - 96px))`); at any other district, it simply recedes in opacity (`var(--motion-recession-subtle)`, the same subdued-but-present token M4.1 already defines) without any positional claim. The same physical DOM node carries all three states — the segment does not know it is "arriving" or "leaving," only where it currently belongs, which is exactly what makes it capable of animating between two real, different values instead of only ever appearing at one.

## Persistence Strategy

`AppShell` was audited as the smallest existing persistent shell level, per this task's own explicit Phase 4 preference, and found sufficient — no new persistent transition coordinator, no session-scoped departure/arrival intent tracking, and no new history stack were needed beyond what `WorldTrace` itself does by simply reading `usePathname()` on every render. `WorldTrace`'s own doc comment records this reasoning in full for future maintainers. This deliberately stops short of the task's own offered "example architecture" (a departure-intent → session-state → shell-reaction pipeline) because the offered example was explicitly framed as "only an example," and the pathname itself already supplies everything `WorldTrace` needs synchronously, with no intermediate state to track or lose.

## WorldTrace Scope

**Found and corrected during a pre-M4-C-re-review integrity audit, narrower than the calibration itself.** The initial calibration derived `data-trace-position` purely from `usePathname()` — correct for *structural presence* (Home shows at the Home edge, Work at the Work edge, everything else recedes), but this alone does not distinguish a *genuine* Home ↔ Work threshold crossing from any other arrival at `/work`. Since the CSS `transition` was originally attached unconditionally to `.world-trace-segment`, a Research → Work or About → Work navigation — or a cold `/work` load, or browser Back into `/work` from an unrelated route — would have played the *identical* animated choreography as a real Home → Work passage, merely because the destination pathname happened to be `/work`. That would have misrepresented every arrival at Work as a Home-threshold event, which is not this prototype's claim.

**The fix reuses the existing departure/arrival infrastructure, adds no new mechanism.** `WorldTrace` now also reads `peekThresholdArrival(HOME_TO_WORK_ARRIVAL_KEY)` / `peekThresholdArrival(WORK_TO_HOME_ARRIVAL_KEY)` — the exact same non-mutating, session-scoped reads `ThresholdIndicator` already performs to tell a genuine arrival from a cold one — and sets `data-trace-active="true"` only when the current position corresponds to a real, pending arrival flag genuinely set by the representative `ThresholdLink`s (`Enter Work` on Home, `Return to Home` on Work). In `threshold.css`, the `transition` itself is now declared only under `[data-trace-active="true"] .world-trace-segment` — `data-trace-position` (structural presence) and `data-trace-active` (active choreography) are deliberately two separate concerns: the trace always renders at the structurally correct edge, but only *animates* into place for a genuine crossing. No new route, no new history mechanism, no Link interception, no delay, and no general route-transition manager were introduced — `resolveTracePosition` and the arrival-key check both remain synchronous, pure functions of already-existing state.

Verified directly (`WorldTrace.test.tsx`'s "WorldTrace scope" describe block, `m4c-world-trace-journey.test.tsx`'s "real genuine crossing vs. real fabricated crossing" describe block):

- **Home → Work** (real `Enter Work` click) — `data-trace-active="true"`, passage plays.
- **Work → Home** (real `Return to Home` click) — `data-trace-active="true"`, passage plays.
- **Research → Work** / **About → Work** (no Home departure ever marked) — `data-trace-position="work"` (correct structure), `data-trace-active` absent — no fabricated passage.
- **Work → Research** / **Work → About** (no Return-to-Home departure marked) — position resolves correctly, no fabricated passage.
- **Cold, direct `/work`** — position resolves to `work`, `data-trace-active` absent (consistent with the pre-existing "no animation on first paint" behavior, now also true for a client-side arrival).
- **Browser Back into `/work` from an unrelated route** — same as any other non-genuine arrival: correct structure, no fabricated Home origin.
- A stale departure flag left over in an unrelated district does not leak into a later, unrelated position.

## Passage architecture

Two small, session-scoped primitives, deliberately separate from M4.6's Return memory (see next section):

- **`ThresholdLink.tsx`** (`src/components/threshold/`) — a real `next/link` that marks genuine departure intent (`markThresholdDeparture`) synchronously on click, before the real navigation proceeds — never delaying or gating access, the same discipline `PassageIndexRecord` (M4.8) already established.

## First entry

On the first Home → Work passage this session, two independent, non-textual things happen alongside `ThresholdIndicator`'s existing richer message: `WorldTrace` transitions its segment from the Home edge to the Work edge over `var(--motion-duration-spatial)` (the richest already-approved duration, District Passage/World Threshold's stand-in — see **No new duration tier invented**), traveling the *full* distance between edges. Content remains immediately accessible throughout (it is not gated behind the transition) — there is no mandatory wait, no cinematic sequence, and nothing blocks interaction with the rest of the page.

## Repeated-entry efficiency

Core acceptance requirement — now satisfied through **two independent, mechanically different, non-textual channels**, directly addressing the calibration review's finding that varying only text length is not sufficient evidence of repeated-entry efficiency. Once `hasTraversedThreshold("home-work")` is true (set after the first arrival, regardless of direction):

1. `WorldTrace`'s transition **duration** drops from `var(--motion-duration-spatial)` to `var(--motion-duration-standard)` — a real, shorter, token-driven value, confirmed by source contract.
2. `WorldTrace`'s transition **distance** also shortens — the segment travels only to `calc(75% - 72px)` instead of the full `calc(100% - 96px)`, one of this task's own explicitly acceptable forms ("less spatial displacement"). At the compact breakpoint this shortens further still (`calc(45% - 43px)` vs. `calc(60% - 58px)`), never lengthens.
3. `ThresholdIndicator`'s message is *also* still shorter on repeated entry ("Arriving from Home." vs. "Arriving from Home — Work is part of the same platform."), unchanged from the original implementation — but this text difference is no longer the *primary* evidence; it is now one of three real, independently verifiable presentation differences, alongside two non-textual ones.

Mechanically proven: `tests/tokens/threshold-contract.test.ts`'s `.world-trace` describe block asserts first/repeated resolve to genuinely different CSS duration *and* distance values; `tests/integration/m4c-world-trace-journey.test.tsx` walks a real Home→Work→Home→Work sequence through `AppShell` and confirms `data-trace-mode` transitions from `"first"` to `"repeated"`; the pre-existing `m4c-home-threshold-journey.test.tsx` continues to confirm the text-side difference unchanged. Orientation is not removed on repeated entry — the indicator, though shorter, is still present and still states what's happening, and the trace itself never becomes fully invisible.

## No new duration tier invented

`ANIMATION_SYSTEM.md`'s full hierarchy names "District Passage"/"World Threshold" as tiers above Record Passage, but M4.1's already-locked token set has no dedicated value there — only `--motion-duration-spatial` (the largest non-ambient value) exists below `--motion-duration-ambient`. M4.1's own original doc comment (`docs/implementation/M4.1_MOTION_TOKENS.md`) provisionally mapped `spatial` to "Sequence/Record Passage," but M4.8's own later, narrow reconciliation deliberately chose `--motion-duration-deliberate` for Record Passage instead (distinguishing it from Focus by an added translation channel, not a longer duration) — see `M4.8_RECORD_PASSAGE_PROTOTYPE.md`'s own "Reduced motion" / motion-token section. That decision, not this document, is Record Passage's authoritative token assignment; M4.1's earlier provisional mapping is superseded and is not corrected retroactively here, since M4.1 itself is a separate, closed milestone this task does not reopen. With Record Passage settled on `deliberate`, `spatial` remained available, unconsumed, for M4.9's own District Passage/World Threshold tier — introducing a new token tier now would be exactly the kind of unilateral new convention this task's own governing instructions repeatedly warn against establishing without explicit authorization. `threshold.css` therefore reuses `--motion-duration-spatial` for first entry (the richest already-approved value still unconsumed by any other package) and drops to `--motion-duration-standard` (State-Change tier) for repeated entry — both already fully resolved, tested, and approved since M4.1; zero new tokens anywhere (confirmed by source contract).

**Hierarchy recheck (post-calibration):** the ordering Feedback < State Change < Focus < Record Passage < District Passage/Home Threshold still holds, and now with the correct token assignment per package: Record Passage (M4.8) uses `--motion-duration-deliberate` — the same tier Focus (M4.4) uses, distinguished by an added translation channel, never `spatial`. `WorldTrace`'s first-entry state is the *only* place in Milestone 4 that consumes `--motion-duration-spatial` — confirmed by source contract (`record-passage-contract.test.ts` explicitly asserts `record-passage.css` never contains `--motion-duration-spatial`). M4.9 is therefore the strongest representative passage in Milestone 4 both by token tier and by scope (it is the one that crosses a shell-level boundary and reorganizes a persistent, shared structural element, where M4.8 animates a single record's own local arrival) — while remaining restrained: one segment, one axis of movement, `translateX` only, no cinematic sequence, no route wipe, no portal, no loading scene.

## Familiarity / session model — deliberately separate from M4.6

`src/lib/threshold/familiarity.ts` is a new, small, entirely separate module from `src/lib/return/returnMemory.ts`, per this task's own explicit §B7 instruction to document the distinction rather than conflate the two. Return answers "what specific context should be restored" (a rich, capture-then-consume snapshot, cleared after one use); Familiarity answers a smaller, different question — "has this one threshold already been crossed this session" (a single, session-persistent boolean that stays `true` for the rest of the session once set). Reusing Return's storage would have merged two genuinely different lifecycles. Familiarity uses its own `sessionStorage` key namespace (`m4-threshold-`, never `m4-return-memory:`), confirmed disjoint by test. Session-scoped only — `sessionStorage`, never `localStorage` (confirmed by a spy-based test, the same technique M4.6 used) — never a permanent profile, analytics record, or browsing-history dashboard.

## District → Home

Returning to Home shows one temporary, subordinate trace line ("Common ground restored — you were just in Work." on first return, "Common ground restored." on repeat) — never a "recently visited" dashboard, never more than one line, and consumed (cleared) immediately after display so it cannot linger or reappear on an unrelated later visit to Home. This is not a mechanical replay of Home→Work in reverse: `WorldTrace` reads the *current* pathname on every render, so Work → Home simply resolves `data-trace-position` back to `"home"` and the segment reorganizes back to the Home edge — the same shared structural element, communicating "common ground restored" spatially as well as textually, settling quickly (within the same `spatial`/`standard` duration already governing the rest of the passage) rather than lingering as a "recently visited Work" marker.

## Navigation-Immediacy Contract

`WorldTrace` and `ThresholdLink` together guarantee navigation is never delayed. `ThresholdLink` remains a real, unmodified `next/link` — marking departure intent is a synchronous, side-effect-only `onClick` handler that never calls `preventDefault`, never gates the click on a promise, and never waits for the trace to "finish." There is no preloader, no blocking curtain, no mandatory wait, no route interception, no `setTimeout` before navigation, and no intermediate fake transition page/route. The destination page's real content is present in the very first render after navigation — `tests/integration/m4c-world-trace-journey.test.tsx`'s "destination content is immediately present" test asserts the Work heading and the trace both exist in the same render, with no waiting/polling required to find either.

## Copy / Status Boundary

No new final Home/Work editorial copy was invented, and no M5 content decisions were made — the existing sentences are unchanged verbatim.

## Cancellation / Interruption

Audited against M4.2's cancellation primitive and deliberately not consumed, for the same reason M4.8 reached, extended to cover `WorldTrace`: every operation in this package is synchronous (a `sessionStorage` read/write, or a `usePathname()` read — no timer, no network, no async settle to race). `usePathname()` always reflects the current, real route; there is no intermediate "navigating" state for a rapid Home→Work→Back, Home→Work→other-nav, or Work→Home→other-nav sequence to catch mid-flight — each render simply reflects whatever the location genuinely is at that instant, and the browser's own CSS transition engine natively redirects an in-flight `transform`/`opacity` transition smoothly toward a newly changed target value without any component-level logic. There is no persistent async layer that could finish late on the wrong route, reopen Work, restore Home, steal focus, move scroll, cover later content, or leave an incorrect active trace — `WorldTrace` has no state that outlives a single synchronous render. "Rapid navigation" for `ThresholdIndicator`'s own text side reduces to the same case already covered before this calibration: does marking departure twice in a row before the destination mounts still resolve to exactly one clean indicator? Yes — tested directly (`m4c-home-threshold-journey.test.tsx`, "Rapid navigation" describe block).

## Reduced-Motion Equivalent

No JavaScript branches on `useReducedMotion()` anywhere in this package — none is needed, the same conclusion M4.4/M4.5 already reached for their own local mechanics, now also confirmed sufficient for `WorldTrace`. Both `threshold.css`'s `transition: opacity` (per `[data-threshold-state]`) and `WorldTrace`'s `transition: transform, opacity` (per `.world-trace-segment`) are pure CSS `transition` declarations, already collapsed to an imperceptible, still-real state change by the pre-existing, M4.2-reconciled `prefers-reduced-motion` rule in `globals.css` — no component-local second reduced-motion system was created. With motion collapsed, the spatial *relationship* survives structurally, not just the transition: Home is still `data-trace-position="home"`, Work is still `data-trace-position="work"`, the segment is still at a different, correct edge in each case, first/repeated is still a different real duration/distance value (imperceptibly fast, but still genuinely different, satisfying "may remain subtle, must not be imperceptible" for the *state*, as distinct from the *animation*), and Work→Home still restores the Home-edge state. The trace is never removed entirely under reduced motion — removing it would remove the spatial relationship itself, not merely the animation of it, which this task's own instructions explicitly warn against.

## Responsive

`.world-trace-segment`'s travel distance is defined with `calc()` against the parent's own `100%` width plus a fixed pixel offset — never an absolute desktop-only coordinate — so it scales correctly at any viewport width without overflow. The existing 767px breakpoint (M3.7's own convention, reused rather than inventing a new one) shortens travel distance in compact layouts (`calc(60% - 58px)` first-entry, `calc(45% - 43px)` repeated-entry) rather than lengthening or increasing motion on a smaller screen — the opposite of what this task's own instructions warn against. The segment's `max-width: 33%` and fixed `96px` base width keep it well within a 390px viewport with room to spare; it carries no interactive affordance of its own (no button, no link, no focus target), so there is no focus ring to clip and no control to become inaccessible at any width. `GlobalNav`'s own real links remain the only interactive elements in the header region, unaffected by `WorldTrace`'s presence.

## Performance

No blur, no layout-affecting property is animated anywhere in `threshold.css` — confirmed by source contract: `ThresholdIndicator`'s own rules animate only `opacity`, and `WorldTrace`'s rules animate only `transform`/`opacity` (both cheap, GPU-composited properties), with `transform` restricted to `translateX` alone (no `scale`/`zoom`/`blur`/`perspective`/`rotate`/`skew` anywhere in the file, confirmed by the updated source contract). No expensive repaint area, no main-thread-blocking work, no animation loop (`@keyframes` confirmed absent — the trace settles and stops once a passage completes; it does not run continuously). No canvas, no WebGL, no environmental/ambient loop. No performance-monitoring framework was added — out of proportion for a two-line text indicator plus one structural segment; genuine felt-performance review is reserved for the M4-C human review.

## Human Re-review Procedure

A human reviewer should verify, in a real browser, against the running app (`npm run dev`, then `/` and `/work`):

- **First entry** — from `/`, click `Enter Work`. Expect: a visible structural segment near the top of the page moves from the left edge toward the right edge over roughly half a second, alongside the existing "Arriving from Home — Work is part of the same platform." text.
- **Return** — from `/work`, click `Return to Home`. Expect: the same segment moves back to the left edge; the existing "Common ground restored…" text still appears.
- **Repeated entry** — click `Enter Work` again. Expect: the segment's movement is visibly quicker and travels a visibly shorter distance than the first time; the text now reads the shorter "Arriving from Home." / "Common ground restored."
- **Reduced motion** — enable "prefers reduced motion" at the OS level, reload, and repeat the same journey. Expect: no visible animation, but the segment still appears at the correct edge for each page (left at Home, right at Work) immediately, and all text remains correct.
- **Direct entry** — with a fresh session (no prior visit to `/`), navigate directly to `/work`. Expect: no arrival text, and the segment should simply be at the Work-side edge with no prior animation implied.
- **Interruption** — from `/`, click `Enter Work`, then immediately click `Return to Home` before the first transition visually settles. Expect: the segment smoothly redirects toward the Home edge rather than snapping, finishing, or getting stuck mid-transition; no duplicate or stale indicator text appears.
- **390px** — resize the viewport (or use device emulation) to ~390px wide and repeat the first-entry/repeated-entry checks. Expect: no horizontal scrollbar, the segment remains fully visible with no clipping, and its travel distance is visibly shorter than at desktop width.
- **Unrelated-district scope** (added by the pre-review integrity audit) — from `/`, navigate to Research (or any non-Work district) via `GlobalNav`, then navigate onward to `/work` via `GlobalNav`, not the `Enter Work` threshold link. Expect: Work's content renders normally and the structural segment is present at the Work-side edge, but with no visible motion into place — it should simply already be there, the same as a cold direct visit. Then, from Work, leave via `GlobalNav` to a district other than Home. Expect: no "Return to Home"-style movement plays.
