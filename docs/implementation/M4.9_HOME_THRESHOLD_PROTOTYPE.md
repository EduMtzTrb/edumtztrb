## Starting-state audit

No threshold/passage mechanism existed anywhere. `src/app/page.tsx` (Home) and `src/app/work/page.tsx` (Work) each rendered only their `WorldThresholdShell`/`DistrictOverviewShell` heading — no body content, no district links beyond `GlobalNav`. `WorldThresholdShell` did not accept `children` at all (`DistrictOverviewShell` already did, from M3.10's earlier extension).

## Home authority audit

Home remains exactly what `PLATFORM_SPECIFICATION.md`/M1.5 already established: shared entrance, orientation space, connective territory — not a mandatory transit hub, cinematic intro, portfolio index, or loading ritual. This prototype does not redesign Home's composition (§B2) — it adds two small, real pieces of content (one departure link, one arrival indicator) to the *existing* `WorldThresholdShell`, nothing more. No environmental system, no district spatial map, no final atmosphere was built.

## Representative district

**Work**, reused directly from M4.8 — per this task's own explicit preference ("using the same district isolates the threshold behavior instead of changing content variables between prototypes"). No new fixture, canonical record, or route was introduced for this package.

## Threshold vs. passage semantics

- **Home → Work** communicates continuity, not disappearance: the arrival indicator on Work explicitly states "Work is part of the same platform" on first entry — Work never looks like an unrelated site suddenly loading.
- **Work → Home** uses Return-shaped language ("Common ground restored") — the shared field returning as common reference, exactly as the Home movement law states.

## Passage architecture

Two small, session-scoped primitives, deliberately separate from M4.6's Return memory (see next section):

- **`ThresholdLink.tsx`** (`src/components/threshold/`) — a real `next/link` that marks genuine departure intent (`markThresholdDeparture`) synchronously on click, before the real navigation proceeds — never delaying or gating access, the same discipline `PassageIndexRecord` (M4.8) already established.
- **`ThresholdIndicator.tsx`** — the arrival side. Built on `useSyncExternalStore` (the same SSR-safe pattern `useReducedMotion` (M4.2) and `RecordReturnControl` (M4.8) already established) with a side-effect-free snapshot function; the actual state mutation (consuming the arrival flag, marking the threshold traversed) happens in a plain `useEffect` that calls no React state setter, avoiding this repository's `react-hooks/set-state-in-effect` rule the same way M4.8 already had to.

## Spatial trace / continuity

At least one concrete, persistent structural trace survives each passage (§B1): Work's arrival indicator (a real, readable sentence, not merely a CSS effect) and Home's return indicator (likewise). Motion may reinforce this — see **Reduced motion**, below — but the meaning itself is carried entirely by real DOM text, never by animation alone.

## First entry

On the first Home → Work passage this session, `ThresholdIndicator` renders the richer, two-clause message ("Arriving from Home — Work is part of the same platform.") — content remains immediately accessible (it *is* the content), there is no mandatory wait, no cinematic sequence, and nothing blocks interaction with the rest of the page (the district heading and the Return-to-Home link are both present and usable in the same render).

## Repeated-entry efficiency

Core acceptance requirement, satisfied via **reduced assembly** — one of this task's own explicitly acceptable forms (§B6: "shorter duration; reduced assembly; less spatial displacement; fewer secondary transition layers"). Once `hasTraversedThreshold("home-work")` is true (set after the first arrival, regardless of direction), the indicator shows a shorter, single-clause message ("Arriving from Home.") — genuinely less content, not merely restyled, and never a verbatim replay of the first-entry message. Mechanically proven: the real journey test (`m4c-home-threshold-journey.test.tsx`) walks Home→Work (first) → Work→Home → Home→Work (second) and confirms the second passage is classified `repeated-entry` with the shorter text, never the richer one. Orientation is not removed on repeated entry — the indicator, though shorter, is still present and still states what's happening.

## No new duration tier invented

`ANIMATION_SYSTEM.md`'s full hierarchy names "District Passage"/"World Threshold" as tiers above Record Passage, but M4.1's already-locked token set has no dedicated value there — only `--motion-duration-spatial` (the largest non-ambient value, Sequence/Record-Passage tier) exists below `--motion-duration-ambient`. Introducing a new tier now would be exactly the kind of unilateral new convention this task's own governing instructions repeatedly warn against establishing without explicit authorization. `threshold.css` therefore reuses `--motion-duration-spatial` for first entry (the richest already-approved value) and drops to `--motion-duration-standard` (State-Change tier) for repeated entry — both already fully resolved, tested, and approved since M4.1; zero new tokens anywhere (confirmed by source contract). This is documented transparently as a deliberate scope boundary, not an oversight — a future, explicitly authorized token package may add a dedicated tier if a reviewer wants one.

## Familiarity / session model — deliberately separate from M4.6

`src/lib/threshold/familiarity.ts` is a new, small, entirely separate module from `src/lib/return/returnMemory.ts`, per this task's own explicit §B7 instruction to document the distinction rather than conflate the two. Return answers "what specific context should be restored" (a rich, capture-then-consume snapshot, cleared after one use); Familiarity answers a smaller, different question — "has this one threshold already been crossed this session" (a single, session-persistent boolean that stays `true` for the rest of the session once set). Reusing Return's storage would have merged two genuinely different lifecycles. Familiarity uses its own `sessionStorage` key namespace (`m4-threshold-`, never `m4-return-memory:`), confirmed disjoint by test. Session-scoped only — `sessionStorage`, never `localStorage` (confirmed by a spy-based test, the same technique M4.6 used) — never a permanent profile, analytics record, or browsing-history dashboard.

## District → Home

Returning to Home shows one temporary, subordinate trace line ("Common ground restored — you were just in Work." on first return, "Common ground restored." on repeat) — never a "recently visited" dashboard, never more than one line, and consumed (cleared) immediately after display so it cannot linger or reappear on an unrelated later visit to Home.

## Orientation preservation

`GlobalNav` (M1.4, untouched) remains fully valid throughout — every check in the real journey test still finds the district heading, the district's own content, and (in the direct-access test) the Return-to-Home link all present and reachable regardless of threshold state.

## Direct-entry boundary

A cold visit to `/work` (no prior Home departure this session) renders no threshold indicator at all — tested directly — while the district remains completely usable (heading present, Return-to-Home link present). No Home passage is ever fabricated for a visitor who bypassed Home entirely via `GlobalNav` or a direct URL, satisfying §B9 exactly.

## Cancellation

Audited against M4.2's cancellation primitive and deliberately not consumed, for the same reason M4.8 reached: every operation here is synchronous (a `sessionStorage` read/write, no timer, no network). "Rapid navigation" therefore reduces to: does marking departure twice in a row before the destination mounts still resolve to exactly one clean indicator? Yes — tested directly (`m4c-home-threshold-journey.test.tsx`, "Rapid navigation" describe block) — the second `markThresholdDeparture` call simply overwrites the same flag; no stale duplicate state or double-rendering occurs.

## Reduced motion

No JavaScript branches on `useReducedMotion()` in this package — none is needed, the same conclusion M4.4/M4.5 already reached for their own local mechanics. `threshold.css`'s one `transition: opacity` per state is already collapsed to an imperceptible, still-real state change by the pre-existing, M4.2-reconciled `prefers-reduced-motion` rule in `globals.css`. Meaning is carried entirely by the indicator's real text content, unconditional on any motion preference — orientation, first/repeated distinction, and Return availability are all structural, not motion-dependent.

## Performance

No blur, no layout-affecting property is animated anywhere in `threshold.css` — the only transition is `opacity`, confirmed by source contract (no `transform`/`scale`/`zoom`/`blur`/`perspective` anywhere in the file). No expensive repaint area, no main-thread-blocking work, no animation loop (`@keyframes` confirmed absent). No performance-monitoring framework was added — out of proportion for a two-line text indicator; genuine felt-performance review is reserved for the M4-C human review.

## No environmental animation

Confirmed directly — `threshold.css` contains no `@keyframes`, no named `animation`, no ambient/looping treatment of any kind.

## M5.1 boundary

This package does not implement the final Home Universe shell, a district spatial map, environmental atmosphere, or any district's real composition — `WorldThresholdShell`/`DistrictOverviewShell` remain exactly the M1.5 structural shells they always were, now with two small, real, additive pieces of content. Milestone 5 owns everything beyond proving this mechanic.

## Fixture / review mode

None was added — no `/contact` fixture, no new query flag. The real `/` → `/work` → `/` journey, using the actual page components, *is* the review surface (mirroring M4.8's own choice not to duplicate a simulation elsewhere).
