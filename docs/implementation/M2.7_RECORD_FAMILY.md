## Architecture Decision

Five standalone components under `src/components/records/` (`PortalRecord.tsx`, `MediaRecord.tsx`, `IndexRecord.tsx`, `EditorialRecord.tsx`, `ProductRecord.tsx`), each independently testable, plus one shared stylesheet (`src/styles/records.css`). No shared low-level `Record`/`Card` primitive was introduced: the five families differ enough in DOM shape (whole-surface link vs. title-only link, media slot vs. none, row vs. block) that a forced common wrapper would either leak the wrong shape into at least one family or become a prop-driven variant switch — exactly the two anti-patterns this task warned against (`<Card variant="portal|media|...">` misuse risk, and five unrelated mini design systems). What they share instead is real: typography roles (M2.2), spacing tokens (M2.3), the focus-visible mechanism, and — where genuinely applicable — `StatusTag` (M2.6). This mirrors M2.6's own architecture decision (no forced base "SelectionControl" wrapper) for the same reason.

## Shared Record Invariants

Every family:

- has a mandatory `title: ReactNode` prop and a mandatory `href: string` prop — no record renders without an identity or a route cue.
- resolves to a real `<a>` (via `next/link`) for its route — never an `onClick`-driven `<div>`.
- renders `<article>` at its root (a record is a discrete, independently meaningful piece of content — the correct semantic element per this task's own guidance); whether that `<article>` is further wrapped in `<li>` is left to the consumer (a list context isn't assumed here since no real listing page exists yet).
- exposes every essential piece of information (title, and — where applicable — price/availability/status) unconditionally in the DOM; hover changes only `opacity: 0.85` (the same restrained value M2.5/M2.6 already use) and never gates content.
- has no dramatic hover/focus scale — no `transform`, no `box-shadow`, no blur, anywhere in `records.css` (asserted by `records-contract.test.ts`).
- carries a `:focus-visible` rule (see **Focus** below).
- uses only already-approved typography roles (`.type-h2`/`.type-h3`/`.type-label`/`.type-body`/`.type-body-small`/`.type-metadata`/`.type-caption`) — no new role, no forced uppercase, no default Mono.
- uses only already-resolved spacing/color/geometry tokens — no new token minted, no hard-coded color.
- is not a district-specific component — no `WorkRecord`/`ResearchCard`/etc. exists; district expression is deferred to later composition/content, per this task's own instruction.
- applies no Signal, no `.action-*`/`.filter-toggle`/`.segmented-*`/`.tab*` class from M2.5/M2.6 (those are action/selection vocabularies, not record vocabulary — asserted by `records-contract.test.ts`).

Every family remains fully comprehensible with motion disabled (none exists), hover unavailable (nothing is hover-gated), and direct keyboard navigation (every link is a real, focusable anchor).

## Portal Record

`src/components/records/PortalRecord.tsx` — entry into a district or major collection (§34.1). Minimal props (`title`, `href`, optional `orientation`, optional `identifier`) — deliberately the smallest information model of the five families, matching §34.1's "minimal essential information, concentrated void, clear route cue." Generous vertical padding (`--space-8`) stands in for "more void than other records" rather than any border/fill — no `.plane`/`.frame`, no background, nothing that would make it read as a hero card or dashboard tile. No Signal is used to make it feel special (§11 of the task's own instruction).

**Interaction rule:** the whole surface is one `<a>` — a Portal has exactly one purpose (enter) and no competing interactive content, so nesting the identifier/title/orientation inside a single link is correct and produces no nested-interactive-element violation.

## Media Record

`src/components/records/MediaRecord.tsx` — preview of a visual Work/Art/Lab/Product/other media-led record (§34.1). Owns a semantic `media` slot (a `ReactNode` prop, required) plus `title` (required), and optional `primaryMetadata`/`description`. The slot (`.record-media-slot`) sets no `aspect-ratio` and no `object-fit` — it renders `media` through a plain `<div>` with `width: 100%; height: auto` on its direct child, so whatever intrinsic ratio the eventual M2.8 media primitive has survives untouched. No universal image/text ratio is imposed, per §34.1/§15.2 ("no universal image/text ratio is approved").

**Interaction rule:** same as Portal — the whole surface is one link, since a Media Record (in this package) has no competing interactive content of its own.

## Index Record

`src/components/records/IndexRecord.tsx` — the dense, scannable row representation for archives, catalogues, and (later) Search/Index result lists (§34.1). Props: `title`, `href`, and optional `type`/`date`/`supporting`/`status`. Deliberately the *densest* family: a single flex row (`.record-index-link`), `padding-block: var(--space-2)` only (no per-side padding-inline beyond what the flex gap provides), no background, no border on the row itself. Containment comes from a **shared divider** between adjacent rows (`.record-index + .record-index { border-block-start: ... }`, §16.7's "shared dividers instead of repeated boxes") rather than each row owning its own box — the first row in any sequence has no divider at all, which falls out naturally from the adjacent-sibling selector rather than needing a `:first-child` override.

**Interaction rule:** the whole row is one link — an Index Record has no competing interactive content; the optional `status` renders as the non-interactive M2.6 `StatusTag` (§22, "use status only where the record family semantically needs it" — an archive/index row status is exactly that case), which is safe to nest inside an anchor since it carries no button/link semantics of its own.

## Editorial Record

`src/components/records/EditorialRecord.tsx` — text-led preview for Research papers, essays, questions, notes, and publications (§34.1). Props: `title`, `href`, optional `excerpt`/`date`/`source`/`status`. Uses Reading Voice (`.type-body` for the excerpt) — no separate Research-only typeface is introduced, satisfying "Editorial Record must remain useful in Research while still being shared platform vocabulary." `max-width: 65ch` keeps the excerpt at a controlled reading measure without inventing a new spacing/typography role.

**Interaction rule — the one place this package deliberately diverges from Portal/Media/Index's whole-surface-link pattern:** only the title is the link. An Editorial Record's excerpt is real prose a reader may want to select; wrapping the entire block in one `<a>` would make ordinary text selection fight navigation, and a large all-prose link is also a poor "essential information" boundary compared to a title-scoped one. This is the explicit, documented interaction-rule choice this task's §10 asked for.

## Product Record

`src/components/records/ProductRecord.tsx` — commercial object/offer preview (§34.1). Props: `title`, `href`, optional `media`, `family`, `descriptor`, `price`, `availability`, `edition`. Commercially material information — `price`, `availability`, `family` — always renders unconditionally (never behind hover), per §24's explicit requirement. No sale badges, no crossed-out pricing, no promotional ribbon, no ecommerce-specific accent color: `.record-product-commercial` uses the same neutral `--color-light-text` every other record family's body text uses, nothing new.

**Interaction rule:** only the title is the link, same reasoning family as Editorial but for a different, forward-looking reason — this record does not yet have a purchase/transaction control (out of scope per this task and per M2.7's Product boundary), but when one is eventually added, keeping the route link scoped to the title now means that future control never has to nest inside (or compete with) an already-existing whole-surface link. The Product Record is not a miniature Product detail page: no cart, checkout, payment, quantity, inventory, license workflow, fulfilment, purchase confirmation, account, or seller/legal information is present.

## Record/Link Semantics

Every family resolves its route through `next/link`'s `Link` (real `<a>`, no client-only `onClick` div). `ActionLink` (M2.5) was deliberately **not** reused for any record title link: `ActionLink`'s `kind="route"` always applies `.link` + `.type-label`, and `.type-label` is a fixed, small (13–15px) typographic size appropriate for a standalone navigational link or button — applying it to a record title would override that title's own heading-scale role (`.type-h2`/`.type-h3`) with label-scale text, which is exactly wrong for something that needs to read as a title. Each family's own local class (`.record-*-link`) instead sets only color/text-decoration/hover/focus directly, letting the wrapping heading element's typography role (or, for Portal/Media/Index's whole-surface links, the title's own inner `<h3>`) determine size. This is real, judged reuse discipline, not a missed opportunity — the "shared platform vocabulary" this task asks for is typography roles, spacing, geometry, and the focus mechanism (§16), not literally reusing one fixed-size link component everywhere a link exists.

Only two DOM shapes are used, and each is documented per-family above: **whole-surface link** (Portal, Media, Index — single purpose, no competing interactive content) and **title-only link** (Editorial, Product — real prose or a future subordinate control makes a whole-surface link the wrong choice). No family wraps a nested interactive element inside its own link (`StatusTag` is the only thing ever nested inside a record link, and it is non-interactive by construction).

## Fields / Planes / Frames

No family applies `.plane` or `.frame` (M2.4) by default — `records-contract.test.ts` asserts neither class appears anywhere in `records.css`. Per §16.7's border rule ("prefer spacing before containment") and this task's own §17 ("choose per family only when semantically justified"), the first pass for every family uses spacing/void/dividers instead of a box: Portal uses void (padding only), Media uses no containment around its slot, Index uses a shared hairline divider between rows (not a box per row), Editorial uses no containment at all (pure text hierarchy), and Product uses no containment either. This mirrors M2.4's and M2.5's own precedent of building an available capability (`Plane`/`Frame` remain fully usable) without forcing it onto content that doesn't yet need it — a real Product/Media consumer that later needs a marked extent can add `.frame` without this package needing to change.

## Typography / Spacing / Grid Integration

Every title uses an existing heading-scale role (`.type-h2` for Portal, `.type-h3` for Media/Editorial/Product); `IndexRecord`'s title uses `.type-label` (dense/compact, matching its row-based density). Supporting text uses `.type-body`/`.type-body-small`/`.type-metadata`/`.type-caption` per M2.2's existing role definitions — no new role, no default Mono anywhere. Spacing exclusively composes M2.3's `--space-*` scale (no literal pixel gap value anywhere in `records.css`). No grid-specific rule was added — records are presentation units meant to be placed inside the existing `.composition`/grid system by a future consumer, not a competing layout system.

## Status / Metadata Usage

`StatusTag` (M2.6) is reused only where a record family genuinely has a status concept: `IndexRecord` (archive/catalogue rows routinely carry a lifecycle status) and `EditorialRecord` (a paper/note plausibly has a draft/published state). `PortalRecord`, `MediaRecord`, and `ProductRecord` have no `status` prop at all — not merely "unused," genuinely absent, since a badge on every family regardless of relevance would be exactly the "badge wall" this task and M2.6's own report warned against. No lifecycle color taxonomy exists (StatusTag itself is still the single neutral treatment established by M2.6 — this package doesn't add one).

## Responsive Behavior

No fixed pixel width, no viewport-specific rule, and no forced desktop-row-on-mobile layout exists in `records.css` — every family is built from flex layouts (`display: flex`, `flex-wrap: wrap` where multiple inline fields exist) that recompose naturally at narrow widths rather than needing a breakpoint override:

- **Portal** — a single-column flex stack at every width; its generous padding is fixed-token-based (`--space-8`), not viewport-scaled, so authority/void is preserved rather than shrinking away on mobile.
- **Media** — slot and body already stack vertically (`flex-direction: column`) at every width; no row-based desktop layout exists to break.
- **Index** — `.record-index-link` uses `flex-wrap: wrap`, so its type/date/supporting/status fields wrap onto additional lines under the title at narrow widths instead of clipping or forcing horizontal scroll.
- **Editorial** — `max-width: 65ch` already caps the reading measure; narrower viewports simply reduce the realized width further, preserving the same proportional reading experience at every size.
- **Product** — `.record-product-commercial` also uses `flex-wrap: wrap`, so price/availability/edition remain simultaneously visible (never hidden behind a "see more" or forced into an unreadable single row) at any width.

Full breakpoint-by-breakpoint (`~390`/`~768`/`~1024`/`~1440–1600px`) verification against real rendered content is deferred to the human visual round (no browser tool available) and, eventually, M2.12's full responsive-system verification — this package only establishes a defensible responsive foundation, per this task's own instruction not to implement that verification early.

## Accessibility

- **Real anchors:** every record's route is a genuine `<a>` (`next/link`), never an `onClick` div — asserted per-component (`link.tagName === "A"`, real `href`).
- **Meaningful headings:** `PortalRecord`/`MediaRecord`/`EditorialRecord`/`ProductRecord` all expose their title as an `<h3>` (Portal uses `.type-h2` sizing on that same `<h3>` — visual size is independent of heading level, consistent with this project's established pattern); `IndexRecord`'s title is a plain `<span>`, matching its row/list semantics rather than a heading (a scanning list of many rows is not a sequence of document sections).
- **Keyboard access:** every link is natively focusable; tested directly (`link.focus(); expect(link).toHaveFocus()`).
- **Focus-visible:** every family exposes `:focus-visible`; four of five reuse the shared shell outline byte-for-byte (verified by string-equality assertion, same technique M2.5/M2.6 use); `IndexRecord` is the one documented, deliberate exception (inward `-2px` offset, since rows sit flush against shared dividers with no external margin — identical reasoning to M2.6's segmented-option exception).
- **No hover-only information:** every essential prop renders unconditionally; hover only dims opacity.
- **No color-only state:** the only stateful element reused here is `StatusTag`, which already carries M2.6's non-color-alone guarantees; nothing in this package introduces a new color-only state.
- **No nested-interactive violations:** confirmed per family — whole-surface-link families have no other interactive content inside their link; title-only-link families keep their link scoped to text only.
- **No duplicate link-name ambiguity:** each record has exactly one link (whole-surface families) or exactly one link (title-only families) — never two links with the same or colliding accessible names within one record.
- **Zoom/reflow:** no fixed-width container anywhere in `records.css` (see **Responsive Behavior**).
- **Fixtures clearly marked:** every test and the preview snippet below use unmistakable fixture strings ("Fixture …", "€000 — fixture only") — never anything resembling real portfolio content.
