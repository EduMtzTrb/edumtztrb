## Architecture

One component, `MetadataRail`, plus one internal (unexported) rendering helper, `MetadataItemRow`. Data-driven, not a compound component: unlike `Tabs` (M2.6), metadata entries need no individual keyboard coordination or parent-managed selection state, so the smallest sufficient API is a flat `items: MetadataEntry[]` prop — the same shape `RadioGroup`/`SegmentedView` (M2.6) already established for "a list of related things" primitives. No `MetadataItem` public component was exported (the task's own suggested name list explicitly permitted deviating where repository convention suggests a better shape); no canonical field schema, enum, or universal metadata list was created — `MetadataEntry.label` is a plain `string`, so any secondary fact a future consumer needs can be expressed without this package needing to change.

## Metadata Item Model

```ts
interface MetadataEntry {
  label: string;
  value: ReactNode;
  tier?: "primary" | "secondary" | "latent"; // defaults to "secondary"
  clarification?: string;
  group?: string;
}
```

`label`/`value` are the required anatomy (§B8). `tier`, `clarification`, and `group` are the task's own three named optional enhancements ("accessible clarification," "structured/linkable value via ReactNode" — `value: ReactNode` covers this directly, "group label"). No icon decoration, no per-type color coding, no district-specific field rendering exists anywhere in the type or the component.

## Semantic HTML

A real `<dl aria-label>` of `<dt>`/`<dd>` pairs — label/value is exactly what a description list represents, and this task's own audit step (§B6) confirmed no other native structure fits better. Each pair is wrapped in a `.metadata-item` `<div>` (valid per the HTML5 `<dl>` content model, which explicitly permits `<div>` wrappers grouping `dt`+`dd`) given `display: contents` so the wrapper generates no box of its own and its `dt`/`dd` children flatten directly into the shared CSS Grid — the standard technique for keeping label/value columns aligned across many wrapped pairs. `display: contents` is applied only to this presentational wrapper, which carries no ARIA role of its own to lose; `.metadata-group` (which does carry `role="group"`/`aria-label`) is deliberately kept as a real box instead, avoiding the known cross-browser risk of `display: contents` dropping an element's accessible name/role (see **Ordering** and **Wide/Compact Layout** for why this two-level structure exists).

## Ordering

`items` renders in exactly the order supplied — `partitionIntoRuns` (a pure grouping pass, not a sort) only merges *consecutive* entries sharing the same `group` value into one run; it never reorders, alphabetizes, or re-prioritizes. Protected by test (`"preserves supplied order — never reorders or alphabetizes"`).

## Typography

Both `<dt>` (`.metadata-label`) and `<dd>` (`.metadata-value`) apply `.type-metadata` (M2.2) verbatim — `metadata.css` sets no `font-family`/`font-size` anywhere (asserted by contract test). No Functional Mono default: §22/§23 of this task's own scope permit Mono only "where notation benefits from it," and no current `MetadataEntry` content is genuinely technical/coordinate notation, so it is not applied — exactly the same restraint M2.8 already documented for its own captions.

## Metadata Tiers

`DESIGN_SYSTEM.md v1.1` §22.1–§22.3 defines Primary/Secondary/Latent metadata tiers, and §34.2 says a metadata rail "uses" this hierarchy — so `MetadataEntry.tier` exists as a real, tested API concept, not merely documented intent. Visual differentiation, per §97's explicit permission to alias existing tokens rather than invent new colors:

- **Primary** — `.metadata-item[data-tier="primary"] .metadata-value` aliases `--color-light-text` directly (already-resolved, the same color used for body text everywhere) plus `font-weight: 500` (a layered addition on top of `.type-metadata`'s inherited weight, the same compositional technique M2.6's selected-tab `font-weight: 600` already used — not a recalibration of `.type-metadata` itself).
- **Secondary** (the default, no `data-tier` styling needed) — `.metadata-label`/`.metadata-value` alias `--color-mist-300` directly, the same "quiet/supporting" neutral M2.5–M2.8 already established throughout this repository.
- **Latent** — the one tier with no already-resolved token that fit: `--color-mist-300` alone (Secondary's color) doesn't clear the "one step more recessed" distinction §22.3 asks for, and the next-darker existing neutral, `--color-graphite-500`, was already computed (during M2.5's own disabled-state work) to fail WCAG AA text contrast (3.98:1 against the field). This package therefore resolves `--opacity-latent` (`src/styles/tokens/opacity.css`), applied to `--color-mist-300` rather than alone: WCAG relative-luminance contrast math (same method as M2.5's `--opacity-disabled` derivation) puts `--opacity-latent: 0.65` at approximately 4.88:1 against the field — above the 4.5:1 AA floor for `.type-metadata`'s 12–13px text, with real margin, while remaining visibly more muted than full-opacity Secondary. Full derivation is in `opacity.css`'s own header comment. This is the single new value this package introduces; Primary and Secondary needed no new token at all.

This is a narrow, WCAG-constrained numeric calibration — the same category of decision M2.5's `--opacity-disabled` resolution already established as acceptable non-identity-defining implementation work, not a guess among "materially different valid directions." No STOP was required.

## Density

No box, border, shadow, or pill wraps any individual metadata item — `metadata.css` contains no `box-shadow`, `border-radius`, or `.plane`/`.frame` reference (asserted by contract test). Shared axes (the grid's own `max-content 1fr` columns) and restrained `--space-3`/`--space-2` gaps carry the structure, per §22.4's "avoid badge-wall or spreadsheet-dashboard appearance" and this task's own "shared axes... avoid boxes around every item."

## Wide / Compact Layout (Compact-Screen Reflow)

`.metadata-rail` is `display: grid; grid-template-columns: 1fr` by default (compact-first, one column: label stacked above value) and switches to `grid-template-columns: max-content 1fr` (label | value, aligned) at `@media (min-width: 768px)` — the exact same breakpoint `layout.css`'s `.composition` already uses for its own compact→medium transition, reused rather than a newly invented number. This is real recomposition via CSS Grid auto-placement (each `dt`/`dd` pair becomes two grid items in a one- or two-column track), not a font-size reduction — satisfying the Implementation Plan's own explicit "compact-screen reflow" requirement. `.metadata-group` mirrors the identical one-column/two-column behavior at the same breakpoint, so grouped and ungrouped entries reflow identically. `MetadataRail` makes no claim about *where* the rail sits relative to primary content (§34.2: "a role rather than a fixed sidebar") — no page-shell or district layout was touched to demonstrate beside-content placement, per this task's own instruction not to redesign page shells for this.

## Long Values

No `text-overflow`, `white-space: nowrap`, or `overflow: hidden` exists anywhere in `metadata.css` (asserted by contract test) — a long collaborator list, source name, or multi-word role simply wraps within its grid cell. No truncation, no hover-tooltip-only reveal.

## Link Behavior

`value: ReactNode` accepts a real `<a>` (or an `ActionLink kind="inline"`, M2.5's exact "embedded in prose" link treatment) directly — `MetadataRail` itself renders no link/button of its own (asserted by test: `queryByRole("link")`/`queryByRole("button")` both absent when no value supplies one). The whole metadata row is never made clickable; only the value's own real link, if present, is interactive — consistent with every prior package's "no fake action semantics, no nested-interactive violations" posture.

## M2.8 Boundary

Media-intrinsic information — what a photograph depicts, who made it, a document's plate identifier, a video's accessible label — stays entirely inside M2.8's `Figure`/`Caption`/`DocumentPlate`/`VideoFrame` components; none of it was moved into `MetadataRail`. `RecordIntegration.test.tsx` renders a `Figure` (with its own `caption`/`credit`) alongside a separate `MetadataRail` (with record-level facts like "Medium") to confirm both coexist as genuinely distinct systems, not that one absorbs the other.

## Milestone 3 Boundary

## Annotation / Signal Boundary

Not implemented, correctly: no leader lines, measurements, coordinates, or trace relationships were added, and Signal does not appear anywhere in `metadata.css` or the component (asserted by contract test). Metadata (structured descriptive facts) and Annotation (contextual notation attached to a location/relationship/reference) remain distinct systems; nothing in this package's scope forced Annotation's resolution, so it stays deferred exactly as M2.4 originally left it.

## Metadata vs. Status

`MetadataEntry.value` may itself be a `StatusTag` (M2.6) where a fact genuinely is a status ("Publication state: [StatusTag]Draft[/StatusTag]") — `MetadataRail` does not wrap every value in `StatusTag` automatically, and most values remain plain text, avoiding the badge-wall this task explicitly warns against.

## Accessibility

- **Label/value association:** native `<dt>`/`<dd>` semantics — a screen reader's definition-list navigation already understands the relationship without any additional ARIA.
- **Reading order:** DOM order matches visual order at every viewport; the compact-mode single-column grid doesn't reorder `dt` before/after `dd` relative to the two-column mode, it only changes which track each occupies.
- **Group naming:** `.metadata-group` carries a real `role="group"` and `aria-label`, verified by test (`getByRole("group", { name: ... })`).
- **No color-only meaning:** the Primary tier pairs its color change with `font-weight: 500` (a non-color channel); Secondary/Latent differ only by intended visual weight, not by conveying distinct *meaning* through color alone (both are still plain "secondary information" — there is no error/warning-style semantic riding on color here).
- **No hover-only content:** `metadata.css` contains no `:hover` rule at all.
- **Keyboard access to links:** whatever real link a `value` supplies remains natively focusable; `MetadataRail` adds no interception.
- **Focus-visible:** not newly needed — `MetadataRail` introduces no new interactive element of its own; any link a consumer places in `value` already carries its own focus-visible treatment from M2.5.
- **200% zoom:** no fixed-width container, `ch`-based measure, or viewport-locked value anywhere in `metadata.css`.
- **No automatic placeholder:** missing/omitted entries simply don't exist in the `items` array — `MetadataRail` never renders `"N/A"` or a dash for an absent fact (asserted by test).

## Responsive Behavior

Tested at the conceptual widths this task named (~390/768/1024/1440–1600px) via the CSS breakpoint itself: below 768px, `.metadata-rail`/`.metadata-group` are single-column (stacked label/value); at and above 768px, both switch to the aligned `max-content 1fr` two-column layout. No horizontal scrolling is required at any width — grid columns never exceed the rail's own container width, and long values wrap rather than overflow. Full real-browser breakpoint verification is deferred to the human visual round (no browser tool available), same posture as every prior M2 package.
