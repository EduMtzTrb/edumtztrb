## Starting-state audit

Before writing any code, the repository was audited for anything M3.1 could reuse, conflict with, or accidentally duplicate.

- **No `src/domain`, `src/lib`, or `src/types` directory existed.** There was no prior canonical-record data model anywhere in the repository — only presentation components that render *shapes of data passed in as props*, never a data contract of their own.
- **`src/components/page-shells/CanonicalRecordShell.tsx`** (M1.5) — a presentation shell with optional *regions* (public state, authorship, context, evidence, metadata, relationships, credits, continuation) that currently render nothing. It has no typed record prop; it accepts pre-rendered `ReactNode` region content. **Classification: presentation-only, reusable later as a consumer of this contract, not itself part of the contract. Not modified.**
- **`src/components/records/*.tsx`** (M2.7 — Portal/Media/Index/Editorial/Product records) — accept individual typed props (`title`, `summary`, etc.) chosen for presentation composition, not a canonical record object. **Classification: presentation-only. Not modified; no import of this package's types was added to them, preserving the M2.7 boundary this task requires be respected.**
- **`src/components/media/*.tsx`** (M2.8) — render pre-supplied media props (`src`, `alt`, `caption`, etc.), never given a `MediaReference` object. **Classification: presentation-only, future consumer. Not modified.**
- **`src/components/metadata/MetadataRail.tsx`** (M2.9) — accepts a `tier` prop (`"primary" | "secondary" | "latent"`), an explicitly presentation-only concept per that package's own report. **Classification: confirms the "metadata boundary" this task calls out — `tier` is deliberately excluded from this contract (see "Metadata boundary" below). Not modified.**
- **No `zod` (or any runtime-validation library) dependency exists** in `package.json`. No prior implementation report references one. **Decision: TypeScript types only for M3.1 — see "Validation strategy" below.**
- **No test directory existed for a "domain" layer.** `tests/tokens/*-contract.test.ts` was the closest existing pattern (source-text contract tests against a stylesheet); it was reused conceptually for `tests/domain/records-source-contract.test.ts`, adapted to a TypeScript module instead of CSS.

Conclusion: nothing in the repository needed to change to accommodate this package. M3.1 is additive only — a new `src/domain/records/` module with zero imports from `src/components` and zero imports into it from existing code.

## Architecture decision

`CanonicalRecordBase` is one flat, strongly-typed interface — not a discriminated union with per-district optional fields, and not implemented as five near-duplicate district-specific interfaces. This task's own guidance (§6) explicitly rules out "one giant type with every district's fields as optional" (e.g. `price?`, `experimentResult?`, `paperAbstract?` all living on one shape); the chosen design avoids that failure mode by containing **only the fields `IMPLEMENTATION_PLAN.md` §7 actually lists** — no district-only field exists anywhere on `CanonicalRecordBase`.

District-specific extension (Work's deliverables, Art's medium, Lab's hypothesis, etc.) is **out of scope for M3.1 by definition** — it is M3.2's "District extensions" package, and is deliberately not modeled here even as a placeholder field. The extension mechanism is ordinary TypeScript interface extension (`interface WorkRecord extends CanonicalRecordBase { ... }`), which M3.2 will use; no "extension slot" field exists on this contract because the mechanism is the language's own `extends`, not a data field.

This keeps M3.1 to what the Implementation Plan actually asked for: a **minimal, universal, strongly-typed shared contract**, not a speculative all-encompassing schema.

## Canonical identity

- `CanonicalRecordId` and `CanonicalSlug` are both branded (nominal) string types: `type CanonicalRecordId = string & { readonly __brand: "CanonicalRecordId" }` (and the analogous `CanonicalSlug`). This makes it a **compile-time error** to pass a slug where an ID is expected, or vice versa — directly encoding IA §14.1's distinction between "stable ID... independent of title or route presentation" and "slug... public route identifier" as a type-system guarantee, not a naming convention.
- `id` is never the title and never an array index — fixtures construct IDs independently of both (`fixture-work-001`, distinct from the title `"Fixture work outcome"` and from array position).
- `createRecordId(value: string)` / `createSlug(value: string)` are the only construction functions — no format is prescribed upstream (no UUID requirement), matching this task's own guidance that a canonical ID need not necessarily be a UUID.

## Ownership model

`CanonicalOwnerDistrict = "work" | "research" | "lab" | "art" | "products" | "about"` — exactly the six IA §4.2 approved canonical-owner districts. **Home is deliberately excluded** — IA §4.2: "Home does not own canonical Work, Research, Lab, Art, Product, or About records merely because it surfaces them." No discipline (Architecture, AI, BIM, Software, etc.) appears as an owner; IA §1's "a new discipline... does not by itself justify a new district" is enforced both by the type (compile-time) and by `CanonicalRecord.type-tests.ts`'s three negative assertions (`"architecture"`, `"ai"`, `"home"` all `@ts-expect-error`).

## Record type vs. owner

`CanonicalContentType` is a separate 17-value union (IA §13.3's approved core vocabulary, verbatim: Project, Case Study, Research Project, Publication, Essay, Talk or Presentation, Experiment, Prototype, Tool, Artwork, Art Series, Exhibition, Product, Service, Collection, Profile Record, Organization or Venture), kept fully independent of `CanonicalOwnerDistrict`. A record's owner and its content type are two different questions — nothing in the contract couples them (e.g. nothing prevents a `"lab"`-owned record from having `contentType: "tool"` vs. `"prototype"`).

## Route identity

Only `slug: CanonicalSlug` is stored. **No computed `href`, `canonicalUrl`, or `canonicalRoute` field exists anywhere** — enforced both structurally (no such field is declared) and by `records-source-contract.test.ts`'s explicit negative assertions for all three names. Full canonical-route *resolution* (guaranteeing one public route per record, rejecting identity based on temporary state/technology/campaign/filter/presentation mode) is `IMPLEMENTATION_PLAN.md` §7's separate **M3.3 — Canonical-route resolver** package and is not attempted here.

## Public/lifecycle state model

IA §6.2's four independent dimensions are handled as follows — three owned by this contract, one deliberately excluded:

| Dimension | Type | Owned here? |
|---|---|---|
| A — Curatorial inclusion | `CuratorialInclusion = "included" \| "excluded"` | Yes |
| B — Visibility | `Visibility = "public" \| "unlisted" \| "private"` | Yes |
| C — Lifecycle | `Lifecycle = "draft" \| "active" \| "complete" \| "failed" \| "abandoned" \| "speculative" \| "archived"` | Yes |
| D — Domain-specific state | (district-owned) | No — M3.2's territory |

These are three **sibling fields**, never flattened into a generic `status`. IA §6.3 ("The unqualified term `status` must not be used as a universal IA field because it collapses distinct concepts") is enforced by `records-source-contract.test.ts` (`not.toMatch(/\bstatus\??:\s/)`) and `CanonicalRecord.test.ts` (asserts `hasOwnProperty(record, "status") === false` on every fixture), plus a compile-time `@ts-expect-error` in `CanonicalRecord.type-tests.ts` proving a `status` field is rejected on a fully-valid record shape.

## Curatorial-threshold handling

`isComplete !== isPublic` is never encoded as an implication anywhere in the module — verified three ways:
1. **Structurally** — `records-source-contract.test.ts`'s "does not couple completion to publication" test asserts no conditional/derivation logic anywhere places `lifecycle` and `visibility`/`curatorialInclusion` in the same expression.
2. **Behaviorally, both directions, with real fixture data** — `fixtureLabRecord` is `lifecycle: "failed"` **and** `visibility: "public"` (a significant failed experiment stays openly documented, IA §6.1/§6.4); `fixtureUnpublishedWorkRecord` is `lifecycle: "complete"` **and** `visibility: "private"`, `curatorialInclusion: "excluded"` (finished work that hasn't cleared the public bar). Both are asserted directly in `CanonicalRecord.test.ts`'s "Public-state logic" describe block, plus a dimension-independence set-size check across the full fixture array.
3. **At compile time** — `CanonicalRecord.type-tests.ts` contains two *positive* (non-`@ts-expect-error`) type-checks, `validCompleteButPrivateRecord` and `validFailedButPublicRecord`, proving the type system itself imposes no coupling.

## Authorship model

`Authorship { primary: AttributionEntry; role?: string; collaborators?: AttributionEntry[] }`, with `AttributionEntry { name: string; role?: string }`. Kept intentionally minimal — a single required primary attribution plus an optional list of typed collaborators, not an overbuilt contributor-graph system. `Credit { name: string; role: string }` is a separate, smaller structure for IA §14.2 "credits" / `CROSS_UNIVERSE_SYSTEM_REQUIREMENTS.md` §8.1 "credits" (contribution credit, distinct from primary authorship — e.g. a photographer credited on an Art record who is not the record's author).

## Relationship model

`CanonicalRelationshipReference { targetId: CanonicalRecordId; type: CanonicalRelationshipType; priority?: number }`. `CanonicalRelationshipType` is the **exact IA §5.3 v1.0 vocabulary, verbatim, and nothing else**: `related-to`, `derived-from`, `informed-by`, `tested-in`, `developed-into`, `commercialized-as`. IA §5.3's own words — "the vocabulary is intentionally small. Additional types require a demonstrated recurring need and terminology governance" — are honored by not inventing any additional type. A relationship stores a `targetId` reference only, **never an embedded copy of the target record** (IA §5.1: "represented through explicit relationships rather than duplication") — enforced at compile time (`CanonicalRecord.type-tests.ts`'s `invalidRelationshipEmbedsRecord` `@ts-expect-error`) and at the structural-test level (`CanonicalRecord.test.ts`: `hasOwnProperty(relationship, "target") === false`). `relationships?: CanonicalRelationshipReference[]` is asserted present (never a bare `string[]`) by `records-source-contract.test.ts`.

## Relationship direction

Relationships are **not automatically symmetric or materialized**. `fixtures.ts` reproduces IA §5.4's own directional example verbatim: `research-001 —tested-in→ lab-001`, `lab-001 —developed-into→ work-001`, `work-001 —informed-by→ research-001` — three distinct, independently-authored, non-reciprocal edges, not a mirrored pair generated from one relationship. `CanonicalRecord.test.ts`'s "Relationships" describe block asserts each direction individually by looking up each fixture's own `relationships` array — nothing auto-derives the reverse edge. No `label` field exists on `CanonicalRelationshipReference`: a rendered/reciprocal label is presentation-derived (IA §5.4: "may be adapted to context without changing the stored relationship"), which is a later package's (M2.7 consumer code / M3.5) concern, not stored truth here.

## Media-reference model

`MediaReference { id: string; kind: MediaKind; source: string; accessibility: MediaAccessibilityMetadata; documentationRole?: MediaDocumentationRole; duration?: string; order?: number }`. `source` is a plain string path/URI — **data only**. No `ReactNode`, no component import, no rendered element anywhere in this module; confirmed by `records-source-contract.test.ts`'s import/usage checks and directly asserted in `CanonicalRecord.test.ts` (`typeof media.source === "string"`). `MediaDocumentationRole = "artwork" | "documentation"` implements `PLATFORM_SPECIFICATION.md` §30's explicit "clear distinction between artwork and documentation" requirement, and is exercised by `fixtureArtRecord`.

## Accessibility-metadata model

`MediaAccessibilityMetadata` is a three-branch discriminated union on `role`:

- `"decorative"` — `caption?`, `credit?` only. **May not carry `altText`** (nothing to describe) — enforced at compile time.
- `"informative"` — `altText: string` (required), plus optional `caption`, `credit`, `transcript`, `audioDescription`.
- `"complex"` — `altText: string` and `longDescription: string` (both required), plus the same optional fields as `"informative"`.

This mirrors the same discriminated-union discipline M2.5 already established for `Action`'s `iconOnly`/`aria-label` pairing and M2.8's `VideoFrame` `autoPlay`/`muted` pairing — an invalid combination (alt text on a decorative reference, missing alt text on an informative/complex one) is a **compile error**, not a runtime bug, verified by four separate `@ts-expect-error` assertions in `Canonical Record.type-tests.ts`. No alt text, caption, or long description is ever auto-generated anywhere in this module — every value in every fixture is hand-authored fixture prose.

## Work / Research / Lab / Art / Product district extension boundaries

M3.1's own exact scope is the *universal* contract only — per-district extension is explicitly `IMPLEMENTATION_PLAN.md` §7's separate **M3.2 — District extensions** package ("Add validated extensions for Work, Research, Lab, Art, Products, and About without duplicating universal identity"). Accordingly, M3.1 does not implement any Work/Research/Lab/Art/Product-only field. What it does do, per district, is provide one fixture record proving `CanonicalRecordBase` alone is sufficient to represent a real instance from that district without any missing capability:

- **Work** — `fixtureWorkRecord` (`contentType: "project"`, `lifecycle: "complete"`) and `fixtureUnpublishedWorkRecord` (the curatorial-threshold counter-example).
- **Research** — `fixtureResearchRecord` (`contentType: "research-project"`), the origin of the IA §5.4 relationship chain.
- **Lab** — `fixtureLabRecord` (`contentType: "experiment"`, `lifecycle: "failed"` + `visibility: "public"` — the other curatorial-threshold direction).
- **Art** — `fixtureArtRecord` (`contentType: "artwork"`), the only fixture carrying a real `MediaReference` with full accessibility metadata and a `commercialized-as` relationship to a Product record.
- **Products** — `fixtureProductRecord` and `fixtureSecondProductRecord` (`contentType: "product"`), both deliberately containing **no commercial fields** (no `price`, `availability`, `discount`, etc. — those are M3.2's territory for Products specifically). Confirmed by `records-source-contract.test.ts`'s explicit negative check for nine commercial field names.

No deeper per-district modeling was attempted, per this task's own instruction to implement only what M3.1's exact scope covers.

## About / Home treatment

**About** is one of the six approved canonical-owner districts (IA §4.2) and is modeled identically to the other five — `fixtureAboutRecord` (`contentType: "profile-record"`) confirms this. **Home is not a canonical-record owner at all** (IA §4.2, quoted above) and therefore has no fixture, no owner-district value, and no special-cased field anywhere in the contract — its absence is the correct, IA-mandated treatment, not an oversight. `CanonicalRecord.type-tests.ts` proves this at compile time (`"home"` is rejected as a `CanonicalOwnerDistrict` value).

## Serialization strategy

Every exported type is a plain object/union/string shape — no class, no function-valued field, no `ReactNode`, no DOM/browser object anywhere in `CanonicalRecord.ts`. `CanonicalRecord.test.ts`'s "is fully JSON-serializable" test round-trips every fixture through `JSON.parse(JSON.stringify(record))` and confirms identity fields survive, plus asserts no fixture field is ever `typeof "function"`. `records-source-contract.test.ts` additionally confirms no `ReactNode` import or type annotation exists anywhere in the two source files.

## Presentation boundary (M2.7/M2.9)

This module has **zero import from `src/components`**, confirmed by `records-source-contract.test.ts`'s import checks. M2.9's `MetadataRail` `tier` prop (`"primary" | "secondary" | "latent"`) is explicitly **not** reproduced anywhere on `CanonicalRecordBase` — `tier` is a presentation-weight decision made by whatever renders a record's metadata, not a fact stored on the canonical record itself (`records-source-contract.test.ts` asserts no `tier:`/`tier?:` field and no `opacity` reference in the contract source). No adapter function mapping `CanonicalRecordBase` → M2.7/M2.9 component props was built — this task marked that demonstration optional, and given M3.1's already-substantial scope (14 field categories, 3 state dimensions, typed relationships, accessibility discriminated unions), it was left undone rather than added speculatively; wiring real presentation adapters belongs naturally to whichever package first connects real records to real routes.

## Security / public-delivery boundary

Documented explicitly in `registry.ts`'s own doc comments on `isPubliclyDiscoverable`/`isDirectlyAccessible` (IA §7.3's eligibility predicates): **"fetch everything, then filter client-side" is called out by name as the unsafe architecture this task warned against.** Both predicates are pure functions over an already-loaded single record — they define the *rule* a safe query boundary must enforce, not a substitute for building one. The doc comment states directly that once a real storage/query layer exists, it must apply this exact rule at the query level (e.g. a database `WHERE` clause) so that excluded/private/unlisted records are never transmitted to a public client in the first place — not loaded into application memory and then filtered. No persistence layer exists yet (out of M3.1's scope), so this is documentation of a binding constraint on future work, not an implementation of the safeguard itself.

Separately, `CanonicalRecordBase.editorial` (internal timestamps) is nested under its own key rather than flattened alongside public-facing fields like `title`/`summary`, so that a future serialization boundary can omit `editorial` wholesale from any public-facing payload with a single field-level check rather than an enumeration of individual timestamp fields.

## Search/Index-readiness boundary

No query, filter, or ranking logic exists in this module. What it establishes is the **canonical truth** a future Index/Search implementation (`IMPLEMENTATION_PLAN.md` §7's M3.10/M3.12, "Use the same canonical public set as Index") will need: a stable `id`, a `title`, a `contentType`, an `ownerDistrict`, a `date`, classification slots (`disciplines`/`themes`), and the two visibility predicates in `registry.ts`. `createRecordRegistry` builds the `id → record` map real Index/Search code will eventually need, and `assertRelationshipsResolve` guarantees the relationship graph it will need to traverse is internally consistent. Neither actual querying nor ranking is attempted — both are explicitly later packages.

## Metadata boundary (M2.9)

`DESIGN_SYSTEM.md` v1.1 §22/§34.2/§97's Primary/Secondary/Latent metadata *tier* is a **presentation-weight decision** (how prominently a fact is displayed), not a fact about the record itself. `CanonicalRecordBase` stores facts (`date`, `disciplines`, `themes`, `credits`, etc.); it never stores which *tier* a future renderer should display them at. This boundary is protected by `records-source-contract.test.ts`'s explicit `tier`/`opacity` negative assertions.

## Validation strategy

**TypeScript types only — no new dependency (no `zod` or equivalent) was added.** Justification: (1) the repository audit found no existing runtime-validation library or convention to extend; (2) `IMPLEMENTATION_PLAN.md` §7 itself says "schema technology is an implementation choice," not a requirement; (3) M3.1 has no real data-ingestion boundary yet (no CMS, no file-based content loader, no API) — the only "untrusted" data in this package is the hand-authored fixtures, which the TypeScript compiler already fully validates at author-time; (4) adding a validation library now, with nothing yet parsing untrusted external input, would be exactly the kind of speculative dependency this task explicitly warned against. **Where TypeScript's structural typing alone cannot prove an invariant** (discriminated-union branch exclusivity under excess-property checking, e.g. "a decorative reference must not carry altText"), compile-time tests via `@ts-expect-error` in `CanonicalRecord.type-tests.ts` close that gap — checked automatically by the existing `tsc --noEmit` step already in the validation gate, requiring no new tooling. If/when M3.1's contract needs to validate genuinely untrusted external input (a future content-loading package), that is the moment to reconsider a runtime-validation library — not before.
