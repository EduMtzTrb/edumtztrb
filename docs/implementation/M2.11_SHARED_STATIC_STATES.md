## Architecture

One internal shared foundation, `StaticState` (`heading` + optional `explanation`/`detail`/`action`, a fixed consumer-supplied `className`, and an optional live-region `role`), composed by eight of the nine semantic wrappers (`EmptyState`, `SparseState`, `NoResultState`, `UnavailableState`, `ArchivedState`, `ErrorState`, `SuccessState`, `RestrictedState`). `LoadingState` deliberately does **not** use `StaticState`: reserved geometry plus `aria-busy` is a genuinely different shape from "heading + explanation + detail + action," and forcing it into the same anatomy would blur a real distinction rather than express one.

This is a middle ground between the two anti-patterns this task explicitly warned against: not `<State type="everything">` (each wrapper has its own name, its own fixed semantic `className`, and — where relevant, like `RestrictedState`'s required `explanation` — its own type-level constraints a generic component couldn't express), and not nine unrelated mini systems (the real, substantial shared anatomy — heading typography, explanation/detail typography, action-slot spacing — lives in exactly one place). This mirrors `Figure`'s role in M2.8 and the label/guidance/error anatomy `TextField`/`TextAreaField` share in M2.10, adapted to this package's own genuinely more homogeneous set of states.

## State-Dimension Separation

Every component in this package stays strictly inside DESIGN_SYSTEM.md v1.1 §21's "system state" dimension (loading/empty/error/success/unavailable) or is explicitly labeled as touching the lifecycle dimension only through consumer-supplied text (`ArchivedState`, `RestrictedState`) — none of the four dimensions (interaction, system, lifecycle/public, commercial) are flattened into one component or one meaning:

- `ErrorState`'s own docstring explicitly distinguishes system error from a failed Lab experiment or failed Research hypothesis (§21.2/§21.3) — a domain's own "failed" lifecycle state is that domain's concern (Milestone 3), never this component's.
- `UnavailableState`'s own docstring explicitly distinguishes commercial unavailability from `ArchivedState`'s lifecycle archival (§21.4: "unavailable ≠ archived, discontinued ≠ archived").
- `ArchivedState`'s own docstring cites §86 directly ("Archive is represented through lifecycle state, not deletion styling") and never renders a default current-action affordance.
- No component here decides "complete ≠ automatically public" or "incomplete ≠ automatically private" (§21.3) — that remains entirely Milestone 3's/Information Architecture's, per **Restricted / Unpublished** below.

## Loading

`LoadingState` (`src/components/state/LoadingState.tsx`) reserves geometry via an author-supplied `minHeight` (a genuinely dynamic value, applied via inline style — the same category of necessary literal M2.5's `44px` hit area and M2.8's grid `minmax()` values already established as acceptable) and exposes `role="status" aria-busy="true"`. No spinner, no shimmer, no skeleton shape, no animated gradient — `state.css` contains no pseudo-element, `background-image`, or `transition`/`animation` property anywhere (asserted by contract test). The label is always visible plain text (never hidden-for-screen-readers-only) — sighted users benefit from knowing content is loading too, consistent with every prior package's "nothing essential is hover/AT-only" posture.

## Empty

`EmptyState` explains genuine absence via a required `heading`, optional `explanation`, and optional `action` — never a default filler message, never error/alert semantics (protected by test). A next valid action renders only when a consumer supplies one; none is invented.

## Sparse

`SparseState` is deliberately the most minimal wrapper: `heading` + optional `explanation`, **no `action` prop at all**. Sparse content isn't a dead end needing a recovery step — it's orientation, per this task's own "primarily provide explanatory orientation rather than a 'warning.'" Distinguished structurally from `EmptyState` by its own `.static-state-sparse` class (never `.static-state-empty`), protected by test.

## No Result

`NoResultState` is the presentation state only — `query` is whatever already-resolved criterion text a future Search/Index/filter consumer supplies; this component never queries, filters, or inspects anything itself. `action` supports a reset/edit hook. Renders nothing beyond what's supplied — no implication of hidden content (protected by test: an unsupplied `query`/`action` renders no extra DOM at all).

## Unavailable

`UnavailableState` accepts a single free-form `reason` slot — deliberately **no hard-coded reason taxonomy** (temporary/permanent/regional/sold-out/capacity/etc.) exists in the component itself, per this task's own explicit "do not hard-code a universal reason taxonomy beyond approved semantics." A consumer supplies whichever specific reason text applies; the component doesn't classify it.

## Archived

`ArchivedState` never renders a default action — only when a consumer genuinely supplies one (e.g., "View current version") does an affordance appear, so an archived record can never accidentally look like it has a live, current-state action available. `context` supports successor/related-record information. Uses no functional color, no `role` — archived is neither an error nor a live announcement, it's a stable historical fact.

## Error

`ErrorState` sets `role="alert"` (implicit assertive live-region) and reinforces its heading with `--color-error` — but the actual meaning is carried by the explicit heading text and the programmatic `role`, not the color (protected by test asserting text content and class independent of any color computation, which jsdom doesn't perform anyway). The component's own docstring is explicit that a failed Lab experiment or failed Research hypothesis is a different semantic dimension entirely (§21.2/§21.3) — this component is for genuine system/technical failure only.

## Success / Confirmation

`SuccessState` realizes the Plan's "success, confirmation" as one component (§21.2 itself lists them as one system state). `role="status"` (never `"alert"`) — good news should not interrupt. Concise: a required `heading`, optional `explanation`, optional next-step `action` — no celebratory graphic, no animation (`state.css` has none anywhere).

## Restricted / Unpublished

`RestrictedState` is the one component in this package with a **required** `explanation` prop (every sibling's equivalent slot is optional) — enforced at the type level, so it is a compile error to render this component with no explanation, and there is no internal fallback wording ("Draft," "In Review," etc.) it could silently use instead (protected by test: renders exactly the supplied text, and asserts none of those internal-workflow terms appear anywhere in the output). This directly implements `INFORMATION_ARCHITECTURE.md` §6.5 and this task's own explicit "the state component must accept already-approved public wording rather than deriving it" — **M2.11 does not decide publication eligibility**; a consumer only renders this component after its own domain logic (Milestone 3's, eventually) has already decided a public-safe statement may be shown.

## StatusTag Boundary

`StatusTag` (M2.6) remains a compact, neutral, non-interactive informational label — used, for example, inside an `IndexRecord` row. M2.11's states represent a whole contextual condition (a heading, an explanation, sometimes an action) — a fundamentally different unit than a short inline label. Neither replaces the other: `Integration.test.tsx` renders a `StatusTag` and an `ArchivedState` side by side, confirming they remain two genuinely distinct primitives (`.status-tag` vs. `.static-state-heading`), not a badge-vs-state naming collision. `StatusTag.tsx` was not modified.

## FormConfirmation Boundary

`FormConfirmation` (M2.10) is deliberately left **independently thin**, not refactored to compose `SuccessState`. Both options this task explicitly offered were considered: composing `FormConfirmation` into `SuccessState` would require either `FormConfirmation` losing its current three-line simplicity for no functional gain (it would need to accept/forward `SuccessState`'s broader `explanation`/`action` API even though every existing form-confirmation use case only ever needed a message), or `SuccessState` being constrained down to `FormConfirmation`'s narrower single-message shape (losing the "expose next steps where relevant" capability this task's own scope explicitly asks `SuccessState`/success-confirmation to have). Neither served the actual goal — this task's own instruction was "do not break its existing contract," and `FormConfirmation.tsx` was therefore left completely unmodified (confirmed by diff). `Integration.test.tsx` renders both together to confirm they coexist correctly as two distinct, uninvalidated components — a future consumer chooses `FormConfirmation` for a form-local save confirmation and `SuccessState` for a general-purpose (non-form) completion moment.

## Action Integration

`Integration.test.tsx` demonstrates a real M2.5 `Action` (not a bespoke button) used as `ErrorState`'s `action` — no state-specific button styling exists anywhere in `state.css`; every action slot across all seven wrapper components that support one is designed to receive a real `Action`/`ActionLink`, never to render its own control.

## Functional Color / Signal Isolation

Only two of nine states apply any color at all — `ErrorState` (`--color-error`) and `SuccessState` (`--color-success`), both already-resolved semantic tokens from M2.1, reinforcing (never carrying alone) their already-explicit heading text and live-region role. `EmptyState`/`SparseState`/`NoResultState`/`UnavailableState`/`ArchivedState`/`RestrictedState` all stay fully neutral — asserted directly by contract test (`color` appears in exactly two `.static-state-{variant} .static-state-heading` rules across the whole file). No hue-per-state badge taxonomy, no new chromatic palette, and Signal does not appear anywhere in `state.css` (asserted by contract test).

## Accessibility

- **Error:** `role="alert"` (implicit assertive live region) — announced without a consumer needing to wire that up.
- **Success/confirmation:** `role="status"` (implicit polite live region) — never interrupts.
- **Loading:** `role="status"` + `aria-busy="true"` — both programmatically exposed.
- **No excessive repeated announcements:** each state renders its live-region role exactly once per instance; nothing in this package re-announces on every render.
- **State meaning not color-only:** verified per-component (see **Functional Color / Signal Isolation**); every state's meaning is carried first by its explicit consumer-supplied heading text.
- **Semantic headings:** `.static-state-heading` is a `<p>`, not an `<h1>`–`<h6>` — these states are contextual explanatory content inside whatever section already has its own heading hierarchy, not a new document-outline-level heading; this avoids silently inserting an unplanned heading level into a page a future consumer controls.
- **Keyboard-reachable actions:** every action slot receives a real `Action`/`ActionLink`/native control from the consumer — nothing here intercepts or reimplements keyboard behavior.
- **No hover dependency, no motion dependency:** `state.css` has no `:hover` rule and no `transition`/`animation` property anywhere (asserted by contract test).
- **200% zoom:** no fixed-height container, no `overflow: hidden`, anywhere in `state.css`.

## Responsive Behavior

`.static-state` is a plain `display: flex; flex-direction: column` block with no fixed width and no viewport-specific rule — it inherits whatever width its container (a record, a page section, a form) provides at any of the task's named widths (~390/768/1024/1440–1600px), and text wraps normally in block flow. `.loading-state` similarly has no fixed width; only its author-supplied `minHeight` is ever set, and that's a deliberate reserved-space value, not a responsive concern. No component in this package assumes desktop width to render correctly.
