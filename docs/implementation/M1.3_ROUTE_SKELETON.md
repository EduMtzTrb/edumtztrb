## Dynamic-Route Decisions

- **No fixtures, no `generateStaticParams`, no database, no CMS.** `next.config.ts` does not set `output: "export"`, so dynamic segments without `generateStaticParams` are not prerendered at build time — Next.js marks them `ƒ (Dynamic)` and resolves them at request time. This is exactly the "route structure compatible with runtime resolution" this task calls for instead of inventing content, and the production build (`npm run build`) confirms it works: all 10 dynamic routes below built successfully as `ƒ (Dynamic)` with zero static params supplied.
- **Dynamic segment naming.** The Platform Specification's `{placeholder}` notation (e.g. `/work/practice/{practice-area}`, `/index/type/{content-type}`) describes the *value* that occupies a URL segment, not a required internal parameter identifier — the placeholder name never appears in the resulting URL. Where the spec's placeholder name isn't a valid JavaScript identifier (contains a hyphen), the Next.js dynamic-segment folder was named with the camelCase equivalent (`[practiceArea]`, `[contentType]`) instead. This changes nothing about the public route structure; `/work/practice/some-value` and `/index/type/some-value` resolve exactly as specified.
- **Page content.** Each dynamic page reads its own `params` (the only way to "verify routing" per this task's Core rule) and echoes the resolved value back in the `<h1>` (e.g. `<h1>Work — {entry}</h1>`). This is not invented content — it is a literal reflection of whatever the requester's URL already contained, used solely to confirm the route captured the correct segment. No sample/seed values are hardcoded anywhere.
- **Route ordering.** Static siblings of a dynamic segment (e.g. `/work/selected` next to `/work/[entry]`) were verified not to conflict: Next.js always matches the literal segment first, so this is safe and is the standard, spec-compatible way to combine curated/organizational routes with a catch-most canonical-record route at the same depth.
