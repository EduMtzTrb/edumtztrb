## Component-consumer audit

Audited every shared component family already carrying a static version of these states (`controls.css`, `selection.css`, `form.css`) before changing anything:

| Family | States it genuinely has |
|---|---|
| Action / ActionLink (`controls.css`) | hover, press, focus-visible, disabled, loading (`aria-busy`) |
| Tab (`selection.css`) | hover, focus-visible, selected |
| Segmented option (`selection.css`) | selected, focus-visible, disabled — **no hover** (none existed statically) |
| Filter toggle (`selection.css`) | hover, focus-visible, selected (`aria-pressed`), disabled |
| Checkbox / Radio (`selection.css`) | checked, focus-visible, disabled — **no hover** (none existed statically) |
| Select (`selection.css`) | focus-visible, disabled — **no hover, no selected** (native `<select>`) |
| TextField / TextAreaField (`form.css`) | focus-visible, disabled, error (`aria-invalid`) |
| Status tag, Removable filter | none — informational/non-interactive by design; correctly excluded |

No component was forced to grow a state it doesn't genuinely have (this task's own §C1: "a normal link has no loading state unless actual component semantics support one"). Every addition below is a `transition` on a state that **already existed as a static CSS rule** — no new visual treatment, no new color, no new state was invented; M4.3 only adds the timing.

## Feedback vs. State Change

Kept structurally distinct via token choice, not by inventing separate mechanisms: **Feedback** (hover, press) uses `--motion-duration-fast`/`--motion-duration-immediate`; **State Change** (selected, loading, error, disabled) uses `--motion-duration-standard`. Nothing in this package uses `--motion-duration-deliberate` or above — those remain Focus/Passage territory, explicitly out of scope (§C2).

## Hover / Approach

`controls.css`'s `.action-*`/`.link` and `.tab`/`.filter-toggle` (`selection.css`) each gained exactly one hover-relevant transition: `opacity` at `--motion-duration-fast`. No hover rule anywhere combines more than one property change (verified directly, `motion-consumption-contract.test.ts`: "no hover rule combines more than two dominant visual changes" — every one found has exactly one). Essential information was never hover-only before this package and remains so; nothing here changes what information exists, only how its (already-existing) hover cue arrives.

## Focus-visible

**Deliberately untouched.** No `transition` was added to any `:focus-visible` rule anywhere (verified directly: `motion-consumption-contract.test.ts` scans every `:focus-visible` block across every modified file and confirms none contains `transition`). Per this task's own §C4 ("focus indication is visible immediately... animation does not delay recognition... a simple immediate boundary/contrast change may be better than movement"), the existing instant outline appearance is already correct — adding motion here would only risk violating the requirement it exists to prevent.

## Press

`controls.css`'s `:active` rules gained `transition-duration: var(--motion-duration-immediate)`, overriding the base rule's hover-speed duration specifically for the press transition — CSS applies the *new* state's own transition declaration, so entering `:active` genuinely begins faster than entering `:hover`. No bounce, no scale, no delayed reaction — only the existing opacity dip now arrives immediately (verified: `motion-consumption-contract.test.ts` — "press (:active) transitions use the immediate duration token").

## Selected

Tab, Segmented option, Filter toggle (+ its marker) all gained a `--motion-duration-standard` transition on whichever property their existing selected-state rule already changes (`color`/`border-color`/`background-color`) — never opacity-only, since selected must "use more than color alone" (M2.6's own governing rule, unchanged). Checkbox/Radio's checked-state fill uses the same standard-speed transition on the box/dot itself, while the checkmark/inner-dot's `opacity: 0 → 1` uses the shorter `--motion-duration-fast` with `--motion-ease-enter` — a mark *appearing* reads differently from a container settling. Once selected, nothing continues to animate — every transition is a one-time settle, never a loop (this task's own §C6).

## Loading

Action's `aria-busy` state now settles via the same base-rule opacity transition already covering hover/press/disabled — no spinner, no branded indicator, no skeleton (unchanged from M2.5's own explicit exclusion, `ANIMATION_SYSTEM.md` §18: "loading is a State Change, not a spectacle"). Layout does not shift (only `opacity`/`cursor` change, never dimensions).

## Success / Confirmation

`SuccessState` (M2.11) itself receives no new CSS — it is conditionally *mounted*, not a class toggled on an always-present element, so a CSS `transition` has no prior value to animate from at first render. Adding a genuine mount-in animation would require restructuring the component to always render and toggle a class/opacity instead (a component-architecture change, not a CSS timing addition) — deliberately out of scope for "apply motion to already-correct static states." The structural presence of the heading text is what already carries the meaning (M2.11's own §21.5 priority: language → typography → placement → structure → icon → **color last**) — motion was never the requirement.

## Error

Same reasoning as Success for `ErrorState`'s mount. `TextField`/`TextAreaField`'s `[aria-invalid="true"]` border-color, however, toggles on an **always-rendered** `<input>`/`<textarea>` element, so it genuinely benefits from and receives the same `--motion-duration-standard` transition as disabled-entry — a quiet border-color settle, explicitly **never** a shake (`ANIMATION_SYSTEM.md` §17.3, tested directly: no `@keyframes`, no transform-based shake pattern anywhere).

## Disabled

Every family's disabled-entry (`opacity` toward `--opacity-disabled`) now settles at `--motion-duration-standard` instead of snapping instantly — still no hover/press motion is reachable once disabled (native `disabled`/`pointer-events: none` already prevented that, unchanged).

## Warning boundary

Not implemented — `IMPLEMENTATION_PLAN.md`'s own M4.3 list has no "warning" entry; static warning semantics (wherever they exist) are untouched by this package, per this task's own explicit §C11 instruction.

## M4.1 token consumption

Every `transition` declaration added by this package references a `--motion-*` custom property — never a raw duration/easing literal. Enforced at the source level in three places: each touched stylesheet's own updated M2-era contract test (`controls-contract.test.ts`, `selection-contract.test.ts`, `form-contract.test.ts` — each reconciled from "no transition/animation property" to "every transition uses only motion tokens," since M4.3 is now the authorized first consumer those M2 tests were written before), plus one new cumulative cross-file test (`motion-consumption-contract.test.ts`, mirroring M2.12's own cross-cutting pattern).

## M4.2 capability consumption

No CSS-level reduced-motion override was added anywhere in this package — the pre-existing global rule (M1, reconciled by M4.2) already collapses every transition this package adds to an imperceptible, still-real state change under `prefers-reduced-motion: reduce`. The fixture's interruption demo (`InterruptionDemo.tsx`) is the one place this package's own code reads `useReducedMotion()` and `createMotionCancellation()` directly, proving both M4.2 primitives work as real consumers, not just in their own unit tests.

## Motion contracts

Rather than a runtime configuration object (this task's own explicit "the goal is coherent reusable implementation, not a motion DSL," §C14), each touched CSS rule carries its own contract in a short comment: which role (Approach/Feedback/State Change), which token pair, and why. This is intentionally documentation-as-contract, not a new abstraction layer.

## Performance

Every transition added is `opacity`, `color`, `background-color`, or `border-color` — never `width`/`height`/`margin` (this task's own §C15: "avoid transitions that trigger expensive layout recalculation"). No layout shift is introduced anywhere (confirmed: no dimension property appears in any new `transition` declaration).

## Accessibility

Meaning survives with motion fully disabled (the pre-existing reduced-motion rule already guarantees this — verified once more directly for this package's own additions). No state is motion-only: every state this package touches already had, and retains unchanged, its own non-motion cue (border/fill/text-weight/native attribute) — motion only changes how quickly that cue arrives, never whether it exists.

## Fixture

`src/components/motion/MotionFixture.tsx` (+ `InterruptionDemo.tsx`), composing real, unmodified shared components (`Action`, `ActionLink`, `FilterToggle`, `Checkbox`, `TextField`, `SuccessState`, `ErrorState`) to demonstrate all eight states plus the required interruption/latest-intent proof in one compact section.

**No new route was added.** An initial dev-only route (`/dev/motion-fixture`, gated by a `NODE_ENV` check inside the component) was built and then removed after empirically confirming it still registers as a real entry in Next.js's build manifest (`npm run build` listed it as a static route, changing the total from 53 to 54) — Next.js discovers routes from the filesystem regardless of a runtime check inside the page, so a guard *inside* the component cannot prevent the route from existing in the build output. This directly contradicted this task's own explicit "do not add an unapproved permanent public route." **Resolution**: reused the exact same discipline M3.10/M3.12 already established for Index/Search — a query-parameter flag (`?motion-fixture=m4a`) gated server-side by `NODE_ENV`, this time on the already-approved `/contact` utility route (`src/lib/motion/fixtureGate.ts`, `isMotionFixtureActive`). This adds zero new routes; `/contact` moves from static to dynamic (the same category of consequence M3.10/M3.12 already documented for `/index`/`/search`), confirmed and accepted as the only route-table change in this package.

Labeled unmistakably: `M4-A Motion Foundation Fixture — not real public content`, rendered only when the flag is active.
