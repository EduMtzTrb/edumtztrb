## Starting-state audit

One pre-existing reduced-motion artifact was found (already identified during M4.1's own audit): a blanket `@media (prefers-reduced-motion: reduce)` rule in `src/app/globals.css` (M1-era), setting `animation-duration`/`transition-duration` to `0.01ms !important`, `animation-iteration-count: 1 !important`, and `scroll-behavior: auto !important`. No other reduced-motion code, `matchMedia` usage, cancellation helper, or capability model existed anywhere in the repository before this package.

## CSS reconciliation — no new CSS rule was added

Audited whether the existing blanket rule needed to change, or whether a second, token-level reduced-motion override (redefining `--motion-distance-*`/`--motion-depth-*`/`--motion-environment-*` under the media query) should be added alongside it. **Concluded no second rule is needed:**

- Forcing every `transition-duration`/`animation-duration` to `0.01ms` already makes any `translateX`/`scale` distance (however large a component's own CSS specifies) complete imperceptibly fast — the visual result is an immediate snap to the final state, which **is** "replace spatial travel with... immediate state changes" (§28), not a workaround for it.
- Forcing `animation-iteration-count: 1` already kills any future looping/environmental animation after a single, imperceptibly short cycle — exactly "stop ambient loops" (§28) and "environmental animation is the first layer removed" (§21), with no separate environment-token override required.
- Adding a second, token-level override would have created exactly the risk this task's own Phase D §D2 audits against: **two independent motion-reduction mechanisms that can drift** out of sync with each other.

`globals.css` is confirmed byte-for-byte unchanged by this package (verified directly). This is the deliberate outcome of §B2's audit instruction ("do not create a second reduced-motion system if one already exists... reconcile it").

## Capability architecture

Two new, dependency-free modules under `src/lib/motion/` (a new top-level directory for reusable, non-visual motion logic — distinct from `src/components/` (UI) and `src/domain/` (canonical-record business logic)):

- **`capability.ts`** — the preference/capability model: `prefersReducedMotion()`, `useReducedMotion()`, `shouldPreferLowerCost()`, `isDocumentHidden()`, `shouldRunEnvironmentalMotion()`.
- **`cancellation.ts`** — the latest-intent primitive: `createMotionCancellation()`.

One source of preference: every reduced-motion decision in this repository reads through `capability.ts`, never a component-local `matchMedia` call (§B4) — enforced structurally today by the simple fact that this is the only such call in the codebase (confirmed at the source level).

## `prefers-reduced-motion` implementation

`prefersReducedMotion()` — a synchronous read via `window.matchMedia("(prefers-reduced-motion: reduce)").matches`, guarded for environments without `matchMedia` (returns `false`, the least-restrictive default). `useReducedMotion()` — the same preference as a live-updating React hook, for the rare case a component's *JavaScript* (not just its CSS) needs to branch on the preference (e.g. M4.3's interruptible fixture, Phase C).

## SSR behavior

`useReducedMotion()` is built on React's `useSyncExternalStore` — the React-recommended primitive for subscribing to an external, mutable browser source like `matchMedia` (it also avoids the tearing risk a manual `useState`+`useEffect` subscription can have under concurrent rendering). Its `getServerSnapshot` argument always returns `false`, the exact value React also uses for the very first client render before hydration reconciles — so the server-rendered HTML and the first client render agree, and there is no hydration mismatch. (An initial `useState`+`useEffect` implementation was attempted first and worked correctly, but `eslint-plugin-react-hooks`'s `set-state-in-effect` rule correctly flagged the synchronous `setState` call needed to sync the real preference on mount as an avoidable anti-pattern; `useSyncExternalStore` is the structurally correct replacement, not a lint suppression.) No top-level `window`/`document`/`navigator` access exists anywhere in either module outside a function body (confirmed at the source level, `motion-capability-source-contract.test.ts`).

## Reduced CSS behavior

Unchanged — see **CSS reconciliation** above. The pre-existing blanket rule remains the entire CSS-side mechanism; nothing new was added.

## Functional parity

No animation exists yet to lose feedback from (M4.3 is the first real consumer). The contract this package establishes for M4.3 to honor: reduced motion must *replace* travel with an immediate, still-real state change — never delete the state change itself. This is exactly what the pre-existing `0.01ms` mechanism already guarantees mechanically (the `transition`/`animation` still runs and its end-state still applies, just without perceptible duration) — functional parity is a property of the CSS mechanism already in place, not something this package has to add on top.

## Cancellation model

`createMotionCancellation()` returns a `{ begin, isActive, cancel }` controller backed by a plain `Map<string, AbortController>`. Calling `begin(key)` aborts any still-active controller previously registered under the same `key` before creating a new one — so at most one controller per key is ever active, by construction. No app-wide singleton is exported (this task's own explicit boundary against building "the complete route-transition manager"); a consumer creates its own registry, scoped to its own need.

## Latest-intent guarantee

Tested directly (`cancellation.test.ts`, 7 tests): motion can start (`begin()` returns a fresh, non-aborted signal); a second `begin()` under the same key aborts the first; the superseded signal's `isActive()` check returns `false` (so a consumer's "commit final state" step, gated on `isActive`, cannot fire late for obsolete motion); three rapid `begin()` calls under one key leave exactly one active signal; `cancel()` aborts without starting new motion (the unmount case); independent keys never interfere; a worked example demonstrates the exact pattern a reduced-motion consumer uses (skip straight to the `isActive`-gated final state, still correctly resolving to the latest of two rapid calls).

## Lower-cost fallback

`shouldPreferLowerCost()` — `true` when reduced motion is preferred, **or** when the Network Information API reports `navigator.connection.saveData === true` (an explicit, standardized "use less data" signal some browsers expose) — never a fabricated performance score, continuous FPS sampling, or GPU/CPU guess. This is deliberately the entire lower-cost model for M4.2: a two-signal, conservative, non-fingerprinting tier (normal / prefer-lower-cost), exactly per this task's own §B8 ("a simple capability tier... may be sufficient if justified").

## Environmental disabling

`shouldRunEnvironmentalMotion()` composes all three relevant signals — `!prefersReducedMotion() && !shouldPreferLowerCost() && !isDocumentHidden()` — into the one contract any future environmental motion (M4.9+) must consume before running. No environmental animation exists yet to gate (confirmed: no `@keyframes` anywhere in the repository) — this function is the boundary M4.1 itself named as still owed to a later package.

## Visibility/background handling

`isDocumentHidden()` wraps `document.visibilityState === "hidden"`, SSR-safe. Folded directly into `shouldRunEnvironmentalMotion()` rather than exposed as a separate subscription mechanism — no timer or `visibilitychange` listener was added, since nothing yet needs to *react* to a visibility change (M4.3 has no environmental/looping motion to suspend); a live-updating hook can be added when a real consumer needs one, avoiding an unused subscription today.

## Touch/hover handling

No new code was needed: this repository already relies on real `:hover`/`:focus-visible` CSS pseudo-classes throughout (M2.5/M2.6), which browsers do not trigger from a touch tap without an explicit preceding gesture — the existing behavior already satisfies "touch must not require simulated hover" and "no unexplained double-tap-to-hover." For any future hover-only *decorative* enhancement, `@media (hover: hover) and (pointer: fine)` is documented here as the preferred, dependency-free gating mechanism (§B10) — M4.3 (Phase C, next), as the first real hover consumer, is where this gets applied if genuinely needed.
