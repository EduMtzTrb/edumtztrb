# M6.4 — Utility States

## Status

**Complete / Verified.**

## Authority

- `IMPLEMENTATION_PLAN.md` §11, M6.4 — "Apply shared form, overlay, failure, and confirmation mechanics."
- This task's own Phase H — "Audit existing M2.10/M2.11/overlay/focus/reduced-motion systems. Implement any missing utility-level orchestration necessary for: form validation state; submission-in-progress state; recoverable failure; terminal failure; success; confirmation; unavailable/deferred utility; safe return/retry. Do NOT create new state semantics if existing shared states already cover them. Prefer composition/orchestration over new primitives."

## Finding

Every state this package names already has a real, tested, shared primitive: form validation state and recoverable-failure display (M2.10's `TextField`/`TextAreaField` `error` anatomy), terminal/system failure (M2.11's `ErrorState`), confirmation (M2.10's `FormConfirmation`, plus M2.11's static-state family more broadly), and unavailable/deferred (M2.11's `UnavailableState`). None of these needed a new primitive, a new color, or a new semantic meaning — this package's real work is *orchestration*: deciding, for one real utility flow, which of these existing states applies when.

**Contact (`src/components/contact/ContactForm.tsx`, M6.1) is that orchestration**, and — as of this task — the *only* real utility flow that needs it. Legal/admin (M6.2) and Language (M6.3) are both blocked with no code to orchestrate; Products' transaction boundary (M6.5) is a pure data-derivation function, not a stateful UI flow with its own pending/failure/success lifecycle (Product commitment execution itself is M6.6's own blocked scope).

## Why No Separate Module Was Built

Building an abstract, reusable "utility state machine" module with exactly one real consumer would be the premature abstraction this project's own stated discipline explicitly avoids ("Three similar lines is better than a premature abstraction... Don't design for hypothetical future requirements"). `ContactForm`'s own local `useState`-based orchestration (validation → attempted/error state → focus management → the honest deferred-delivery state) already demonstrates the complete state lifecycle this package's scope names, using only existing shared primitives:

1. **Idle / validation state** — plain controlled inputs, no error shown, per M2.10's own default.
2. **Recoverable failure** — real field-level errors (M2.10's `error` prop), values preserved, focus moved to the first invalid field.
3. **Terminal failure** — not applicable here (there is no network call that can fail; the "terminal" outcome for Contact specifically is the deferred-delivery state below, which is not a failure of the visitor's input).
4. **Success / confirmation** — deliberately **not** used. `FormConfirmation` (M2.10) exists and was audited for this exact moment, and was not used, because no real submission can succeed — using it here would be exactly the fabricated-success path this batch's own critical rule forbids.
5. **Unavailable / deferred** — `UnavailableState` (M2.11, unmodified), the real terminal state for a valid Contact attempt right now.

**Extraction trigger, stated explicitly rather than left implicit:** if a second real utility flow needing this same pending/failure/success orchestration is implemented (a future Product enquiry/quote-request flow is the most likely candidate, once M6.6 or a partial enquiry-delivery mechanism is unblocked), extract the shared orchestration logic at that point — not before. This mirrors the same "reuse an existing resolved primitive rather than invent a new one" discipline this project has applied consistently since M2.4/M4.5, and the same "wait for a second real consumer" discipline M2.5 applied to `Action`'s own `type="submit"` extension.

## Overlay Mechanics

No overlay was used anywhere in this task. Contact does not need one (a full-page form, not a modal interruption, matches `ABOUT_UNIVERSE_v1.1.md` §18's own "direct, calm, low-friction" instruction more closely than a modal would); Legal/Language/Transaction activation are all blocked, so no overlay decision arises for them either. The shared M4.5 overlay system (`Overlay.tsx`, unmodified) remains available, untouched, for whichever future utility genuinely needs it.

No separate test file exists for this package — its behavior is exactly `ContactForm.test.tsx`'s own coverage (8 tests, see `docs/implementation/M6.1_CONTACT.md` "Tests"), since Contact *is* this package's real, only implementation. No pixel-snapshot evidence was used anywhere.
