## Shared public canonical source

`src/domain/records/IndexModel.ts`'s `queryIndex` consumes M3.6's own `selectPublicComprehensiveView` directly — never a second registry, a second taxonomy, or an Index-only content set (confirmed at the source level, `tests/domain/index-model-source-contract.test.ts`). Public eligibility (`isPubliclyDiscoverable`, M3.1) is already enforced upstream of this module; `IndexModel.ts` never re-implements or duplicates that predicate. Tested directly: with no lens applied, `queryIndex`'s result set is identical to calling `selectPublicComprehensiveView` directly on the same records.

## Approved global lenses

Exactly the five `GlobalLensDimension` values M3.4 already closed (`district`, `content-type`, `discipline`, `theme`, `year`) — `IndexLensQuery.dimension` is typed against that same union, so a sixth lens cannot be constructed; this is a compile-time guarantee, not a runtime convention. District-specific classifications (collection, series, territory, contribution-role) remain outside Index's lens vocabulary, exactly as M3.4 established.

## Index query layer

One function, `queryIndex(records, lens?)`, returning `{ entries, count, lens? }`:

- **Complete public set** — `lens` omitted, returns every publicly-discoverable record.
- **Lens projection** — filters the public set by one approved dimension/value pair.
- **Canonical links** — each `IndexEntry.route` is M3.3's own `resolveCanonicalRoute` output, resolved fresh, never a second independently-computed route (tested directly, entry-by-entry).
- **Result count/scope** — `count` always equals `entries.length`; `lens` is echoed back so a caller can render "no results for this scope" accurately.
- **Stable ordering** — deterministic (title, then ID as a tiebreaker) — a systematic browsing order, not a relevance ranking (Search's own concern, M3.12; verified the two are namespace-distinct at the source level).
- **Public archived records included** — Index draws no lifecycle distinction; tested directly with an archived-but-public fixture.
- **Explicit empty/no-result behavior** — an empty record set, or an unknown/unmatched lens value, both produce a correctly empty `IndexResult` (never a thrown error, never fabricated content) — the presentation layer distinguishes "genuinely empty source" (`EmptyState`) from "no match for this scope" (`NoResultState`).

## Presentation

`src/components/index/IndexResults.tsx` reuses, without modification: M2.7's `IndexRecord` (the dense, scannable row primitive already built for exactly this role) and M2.11's `EmptyState`/`NoResultState`. ## Fixture policy

There is still no approved real content corpus and no persistence layer anywhere in this repository. `src/domain/records/devFixtureSource.ts`'s `resolvePublicRecordSource` implements this task's own preferred architecture exactly:

- the M3-B fixture corpus (M3.1's own `allFixtureRecords` — no new fixture file was created) is served **only** when the request's `?fixture=m3b` query parameter is present **and** `process.env.NODE_ENV !== "production"`;
- the `NODE_ENV` check happens server-side, inside this function — a client cannot force fixture data into a production response merely by sending the query string, since Next.js sets `NODE_ENV=production` for any production build/`next start` regardless of what a request contains (tested directly: `vi.stubEnv("NODE_ENV", "production")` with the flag present still returns an empty source);
- in every other case (flag absent, or production), the public source is a genuinely empty array, and the page renders `EmptyState`'s truthful "no public records exist yet" — never fabricated filler;
- when fixtures are active, the page renders an explicit, unmistakable `M3-B Fixture Data — not real public content` notice (tested directly);
- **one fixture source, shared identically** by Index now and Search (M3.12, next phase) — no separate Search fixture corpus was created, satisfying this task's own explicit "one fixture source" instruction for the whole M3-B batch.

No unapproved permanent dev-only route was added — the existing approved `/index` route family gained a query-parameter flag, nothing more.

## Accessibility

- Every result is a real link (`next/link`, via `IndexRecord`) — full keyboard reachability, no custom key handling.
- `EmptyState`/`NoResultState` (M2.11) already carry their own accessible heading structure — reused unchanged.
- No hover-only content, no motion, no fixed pixel width was introduced (`tests/tokens/index-results-contract.test.ts`).
- Current lens/scope is stated in the page's own `<h1>` (e.g. "Index — District: work") and, on a no-result page, restated in `NoResultState`'s `query` slot.
