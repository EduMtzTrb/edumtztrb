## Direct-entry law

Every route touched by this package is rendered "cold" — fresh `params`/`searchParams`, no prior render, no session state — matching this task's own §G1 assumption that a visitor may land on any deep route with zero prior context. Every fact `DirectEntryOrientation` displays is derived from the route itself: district (from the URL segment/layout), current label (from the route's own slug/param), and — only when a caller genuinely supplies one — parent grouping. Nothing is inferred from browsing history, because none exists to infer from.

## No fake Return history

`DirectEntryOrientation`'s "next actions" list offers exactly four kinds of truthful, always-valid destination: district overview, comprehensive/archive access (only when the district actually has one), Index, and Search — never "Return to where you came from" or any other phrase implying real session history. Tested directly, both at the component level and the source level (`tests/domain/direct-entry-orientation-source-contract.test.ts` scans the stripped source for `return to`/`where you came from`/`go back` and finds none).

## Record orientation

The five canonical-record `[entry]` routes (`/work/[entry]`, `/research/[entry]`, `/lab/[entry]`, `/art/[entry]`, `/products/[entry]`) now each compose `DirectEntryOrientation` into `CanonicalRecordShell`'s existing `context` region (M1.5's own "Project/record context" slot — no shell change was needed for these routes). No parent grouping is fabricated: since no real content/data source exists yet, `orientationForSection` is called with just the district and the route's own slug — truthful, not manufactured from classification similarity (this task's own explicit prohibition, §G3).

## Grouping / archive / lens / search entry

- **Six grouping routes** (`/work/practice/[practiceArea]`, `/work/collections/[collection]`, `/research/themes/[theme]`, `/art/series/[series]`, `/art/medium/[medium]`, `/products/collections/[collection]`) each compose `DirectEntryOrientation` into `GroupingViewShell`'s `children` slot (already added by M3.10).
- **Five archive/comprehensive routes** (`/work/all`, `/research/archive`, `/lab/archive`, `/art/archive`, `/products/archive`) likewise — `ComprehensiveViewShell` gained the same additive `children` prop `GroupingViewShell`/`UtilityPageShell` already had (this task's own §G4).
- **All eight About routes** (`/about` + seven sections) — `DistrictOverviewShell` and `CuratedViewShell` (used by `/about` and `/about/current-focus` respectively) likewise gained the additive `children` prop.
- **All five Index routes** (`/index` + four already-lens-scoped routes; `/index/district/[district]` shown as the fifth, all identical in shape) and **Search** (`/search`) now each render a `Breadcrumb` (via `orientationForUtility`) alongside their existing M3.10/M3.12 content — an Index lens route's breadcrumb shows "Index" as parent and the active lens as current, proven directly.

Active lens state, where present, is passed straight into the orientation context (`activeLens`) — no new filter/lens logic was added, only its display, per this task's own §G4 ("active lens/filter state should be clear when present").

## M3.9 integration — no second implementation

`DirectEntryOrientation.tsx` composes M3.9's own `Breadcrumb` component and `buildBreadcrumbTrail`/`orientationForSection`/`orientationForUtility` functions directly — confirmed at the source level (`tests/domain/direct-entry-orientation-source-contract.test.ts`: imports `Breadcrumb` from `./Breadcrumb`, contains no `<nav aria-label="Breadcrumb">` or `<ol>` of its own). This task's own explicit instruction (§G5) is satisfied structurally, not by convention.

## M3.9 extension: utility-route parent grouping

While wiring Index lens routes, a genuine gap was found: `orientationForUtility` had no way to express "this utility route is itself nested under another utility" (e.g. `/index/district/work` under `/index`) — only district-owned sections could carry a `parentGrouping`. Extended `UtilityOrientationInput`/`orientationForUtility` (`orientation.ts`) with the same optional `parentGrouping` field district-owned sections already had; `buildBreadcrumbTrail`'s existing logic required no change (the `parentGrouping` branch was already independent of the `district` branch). Tested directly (`src/components/shell/orientation.test.ts`).
