## Search source parity (non-negotiable, §F1)

`src/domain/records/SearchModel.ts`'s `searchRecords` consumes M3.6's own `selectPublicComprehensiveView` — the exact same function `IndexModel.ts` (M3.10) calls, confirmed at the source level (`tests/domain/search-model-source-contract.test.ts`). A **direct parity test** (`tests/domain/search-index-parity.test.ts`, this task's own explicit §F1 requirement) proves: for every fixture record, Index's public-eligibility decision and Search's own (searched by the record's exact title) agree exactly; a private/excluded record is absent from both; an archived-but-public record is reachable through both identically. No Search-specific record copy, taxonomy, or archive-eligibility rule exists anywhere.

## Searchable information

`matchDirect` checks, in priority order: exact title, title-substring, all-query-tokens-present-in-title ("title word match"), summary substring, discipline term substring, theme term substring — all fields M3.1 already marks public-facing. Internal publication state (M3.6's side-table) is never read here — confirmed at the source level; it was never mergeable into `CanonicalRecordBase` in the first place (M3.6's own architecture), so there is nothing for this module to accidentally search.

## Ranking

No search-engine dependency was added (`package.json` confirmed unaffected — `tests/domain/search-model-source-contract.test.ts`). One small, deterministic, fully explainable rank hierarchy: exact title (0) → title contains (1) → title word match (2) → summary (3) → discipline/theme (4) → relationship context (5), tie-broken by title then ID. Running the same query twice yields byte-identical ordering (tested directly) — never a black-box relevance score.

**Token-match correction found during testing**: an early version matched a title if *any* query word was a title-word prefix — since every fixture title happens to start with the word "Fixture," a multi-word query like "Fixture work outcome" incorrectly matched the entire fixture corpus. Corrected to require *every* query token to prefix-match some title token, which is both the more honest interpretation of "word match" and resolves the test-corpus-specific symptom without weakening genuine single-word search.

## Match reason

Every result carries a short, visitor-facing `matchReason` string ("Exact title match," "Title match," "Title word match," "Summary match," "Discipline match," "Theme match," or `Related to "{target title}"` for relationship-context matches) — never a raw score or internal rank number exposed to the visitor.

## Relationship-context matching

Implemented as the lowest-priority signal: if no direct match is found, a record's own outgoing relationships (M3.5's `relationships` array) are scanned, and a match is reported if a **public** related record's title contains the query — `Related to "{title}"`. Deliberately resolved only against a registry built from the already-public set, so a private/excluded record's title can never leak through another record's search result (the same caution M3.5/M3.6 already documented for relationship traversal, applied concretely here).

## Result model

`SearchResultEntry { record; route; matchReason }`. The presentation layer (`SearchResults.tsx`) surfaces title, content type, canonical link (M3.3), lifecycle ("public state," via `IndexRecord`'s `status` slot), and the match reason (via `IndexRecord`'s `supporting` slot) — reusing M2.7's `IndexRecord` unmodified, exactly like M3.10's Index. Not every optional field (date, principal classification, relationship display) is forced onto every row — only what `IndexRecord` already exposes was wired in, consistent with this task's own "do not make every optional field mandatory."

## Query state

`GET /search?q=...` — a plain, native `<form method="get">` (`SearchForm.tsx`), no client JavaScript required. The query is visible (in the `TextField`) and persistent through the URL exactly like M3.11's filter state. An empty query renders `EmptyState` as a neutral browse invitation with a link to Index — never an error, and never `NoResultState` (which would incorrectly imply a search was attempted and failed). A query matching nothing renders `NoResultState`, preserving the query text.

## Development fixture mode

Reuses M3.10's `resolvePublicRecordSource`/`devFixtureSource.ts` **unchanged** — the exact same `?fixture=m3b` flag, the exact same `NODE_ENV !== "production"` server-side gate, the exact same fixture corpus (M3.1's `allFixtureRecords`). No second fixture source was created, satisfying this task's own explicit "one fixture source" instruction. `SearchForm` includes a hidden `fixture=m3b` field whenever fixtures are active, so submitting a new query doesn't silently drop dev-mode.

## Accessibility

- Persistent visible label (`TextField`'s real `<label>`, M2.10, unmodified).
- Keyboard submission: a real `<button type="submit">` (M2.5's `Action`, unmodified) inside a native form — Enter-to-submit works with zero JavaScript.
- Clear result count, stated with the query text.
- Canonical links throughout (`IndexRecord`, M2.7).
- No-result semantics reuse `NoResultState` (M2.11) unmodified.
- No hover dependency, no motion (`tests/tokens/search-contract.test.ts`).
