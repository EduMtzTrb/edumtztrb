## §D1 — Native-history audit

A direct, repository-wide search (`src/**/*.{ts,tsx}`) for `history.pushState`/`replaceState`/`back()`, `history.scrollRestoration` assignment, `useRouter` imports, and `popstate` listeners found **zero** matches outside prose/comments (the only raw grep hits were this project's own doc-comments explicitly describing what each module does *not* do, and one unrelated use of the English word "history" in a fixture's business-domain comment). Every route transition in this repository goes through Next.js's own `<Link>` component (confirmed via `next/link` import search — used consistently across `GlobalNav`, `DistrictNav`, `Breadcrumb`, every record-family component, `FilterBar`, and `ActionLink`) — untouched by any M1–M4.6 work. `next.config.ts` sets no custom `scrollRestoration` or router behavior of its own.

This audit is now a permanent, automated regression guard, not a one-time manual finding: `tests/lib/native-history-source-contract.test.ts` re-runs the same checks on every test run, plus verifies directly (by reading the actual M4.4/M4.5/M4.6 source files) that `FocusRegion.tsx`, `Overlay.tsx`, and `returnMemory.ts` individually contain zero `window.location`/`history.*` references of any kind.

## §D2/§D7 — Back/Forward and rapid navigation

Two properties are what make Back/Forward and rapid navigation *predictable* in a URL-driven architecture, and both are proven directly rather than asserted:

1. **Pages are pure functions of their params.** `IndexPage` is re-rendered three times in sequence with different `searchParams` (`district=work` → `district=research` → back to `district=work`, the exact shape a real Back/Forward round-trip produces) and produces the correct, uncorrupted output every time — no hidden client-side state leaks between renders. This is the property that makes Next.js's own re-invocation of a Server Component on navigation safe: there is nothing in this codebase for Back/Forward to desynchronize.
2. **Rapid intent resolves to only the latest.** Reusing M4.2's real `createMotionCancellation` directly (not a new mechanism), three rapid `begin()` calls under one "navigation" key leave only the third's signal active — the same guarantee M4.3's `InterruptionDemo` and M4.6's Return fixture already proved for local feedback and Return respectively, reconfirmed here explicitly framed as the navigation scenario this task's own §D7 names.

## §D3 — Direct links

A cold `IndexPage` render (fresh `searchParams`, no prior capture) is confirmed to have nothing in Return memory — `retrieveReturnContext` returns `null` for a key that was never captured, reconfirming M4.6's own boundary in this cross-package context. M3.13's `DirectEntryOrientation` (Milestone 3, unmodified) remains the authoritative structural-orientation fallback for direct entry; M4.6's Return memory is additive only, never assumed.

## §D4 — Overlay + history

`ANIMATION_SYSTEM.md`'s own law — "overlay does not imply a new architectural destination" — is upheld exactly as M4.5 built it: `Overlay.tsx` was audited again here and confirmed to contain no history reference of any kind. Opening/closing an overlay never creates a history entry; Browser Back is therefore never "hijacked" to close one, because there is nothing overlay-related in history to navigate away from.

## §D5 — Focus + history

Same conclusion, independently reconfirmed for `FocusRegion.tsx`: no route-based detail exists here, and no Focus action is ever converted into URL navigation.

## §D6 — Return + history

Return is not a replacement for Back — `returnMemory.ts` contains no history reference at all (reconfirmed). Where a Return control genuinely needs to navigate to a captured origin, the fixture now demonstrates the correct pattern directly: a plain, native `<a href={context.originUrl}>` (`ReturnMemoryFixture.tsx`, added by this package) — real, ordinary navigation, not a `history.pushState` trick. Because it is an ordinary link, Browser Back afterward behaves exactly like Back after any other link click; there is no special Return-specific history state that could desynchronize, and no possible "record → Return → record → Return" oscillating loop, since Return itself never pushes anything — only a genuine link click (the visitor's own action) ever adds a history entry.

## §D8 — Scroll

Native scrolling remains intact repository-wide: `history.scrollRestoration` is referenced nowhere (M4.7's own audit, §D1). M4.5's overlay scroll-lock (`document.body.style.overflow`) is reconfirmed here as correctly scoped — applied only while a specific `Overlay` instance is open, and restored to its exact prior value on close — never a global, persistent scroll-behavior change.

## §D9 — Filter/lens history

M3.11's `buildToggleHref`/`buildResetHref` are exercised directly and confirmed to preserve every non-filter parameter (the `fixture` development flag, specifically) untouched while correctly adding/removing filter parameters — the same URL-authoritative mechanism M3.11 always used, unaffected by anything M4.4–M4.6 added. A captured Return `originUrl` containing filter parameters is confirmed to round-trip faithfully through `parseFilterCriteria`, reconfirming M4.6's own "no duplicate filter store" boundary in a full end-to-end shape (capture → retrieve → re-parse).

## Cumulative test suite

## Browser-only items requiring human confirmation

jsdom has no real multi-document navigation model — the following genuinely cannot be mechanically proven by this repository's test suite and are explicitly flagged for the M4-B integrated human review:

- Real Back/Forward **browser-chrome button** behavior across an actual multi-page navigation sequence.
- Real scroll-position restoration behavior native browsers provide on Back/Forward (as distinct from this package's own explicit, opt-in `restoreScroll` helper, which *is* mechanically tested).
- Whether a real click on the fixture's new "Go to captured origin" link, followed by a real Back click, feels ordinary and unsurprising in an actual browser.
- General perceived responsiveness of rapid navigation in a real browser under real network/render latency, as distinct from the synchronous/fake-timer proofs this suite already provides.
