## Architecture

`src/domain/commerce/transactionBoundary.ts` — one pure, dependency-free function, `deriveCommitmentAvailability`, plus one exported constant, `TRANSACTION_ACTIVATION_CONFIGURED`.

**Product record** stays exactly as M3.2 already built it — `ProductsExtension`'s own fields (`commercialState`, `commitmentLabel`, `priceBasis`, etc.) are unchanged, untouched by this package. This module reads them; it does not extend, wrap, or duplicate the record shape.

**Origin record** ownership is untouched — this package adds no relationship logic; M5.6's own `listIncomingRelationships` usage (M3.5, unmodified) remains the sole cross-district mechanism.

**Transaction adapter** — `deriveCommitmentAvailability` itself is the adapter boundary this task's own Phase J describes, in its minimal real form: it "initiates" nothing yet (there is nothing to initiate until M6.6), but it already normalizes state into one real, honest shape (`CommitmentAvailability`) a future provider integration would consume without needing to know anything about `ProductCommercialState`'s thirteen raw values itself.

**Provider** — no provider (Stripe, PayPal, or otherwise) is named, imported, or referenced anywhere in this module or its consumer. Confirmed directly by this package's own test (`carries no provider-specific field anywhere in its own return shape`), which asserts the module's own serialized output never contains the substrings `stripe`, `paypal`, `checkout`, `provider`, or `sdk`.

**Disabled boundary** — this is the module's entire current purpose. `NON_COMMITTABLE_STATES` (eight of `ProductCommercialState`'s thirteen values: forthcoming, temporarily-unavailable, capacity-closed, sold-out, discontinued, superseded, archived, regionally-unavailable) always block commitment, regardless of configuration — a real state fact. Even a genuinely committable state (available, limited, made-to-order, preorder, free-access) additionally requires `TRANSACTION_ACTIVATION_CONFIGURED` to be `true` — currently `false`, a real, repository-verified fact (see "M6.6 Gate" below), not a placeholder.

## Action Derivation

```
Product's real commercialState
  → NON_COMMITTABLE_STATES membership? → blocked, real state named as reason
  → otherwise: TRANSACTION_ACTIVATION_CONFIGURED?
      → false (current, real): state-permitted but execution-blocked, real M6.6 gap named as reason
      → true (future, once real config exists): permitted, real commitmentLabel returned
```

No new commitment-kind taxonomy was invented (no `"kind": "purchase" | "reserve" | ...` union anywhere) — `commitmentLabel` remains the exact same free-text field M3.2 already approved, matching `PLATFORM_SPECIFICATION.md` §33.1's own "commitment labels are literal" instruction directly: this module decides *whether* the label may currently be shown/acted on, never invents what the label says.

## Provider Independence

Proven directly, not merely asserted: `transactionBoundary.test.ts`'s own `carries no provider-specific field anywhere in its own return shape` test serializes a real result and asserts it contains no provider-related substring. The module has zero imports beyond one type-only import from `DistrictExtensions.ts` (M3.2, unmodified) — no HTTP client, no SDK, no environment variable read.

## Product-Record Isolation

`ProductsExtension` (`src/domain/records/DistrictExtensions.ts`) is completely unmodified by this package — confirmed via `git diff` scoping. This module is a pure consumer, one directional dependency (`transactionBoundary.ts` → `DistrictExtensions.ts`), never the reverse.

## Consumption

`/products/[entry]/page.tsx` (M5.6, extended here) now derives its "Commitment" metadata entry from `deriveCommitmentAvailability` instead of a blanket string check on `commitmentLabel`'s mere presence. Concretely:

- A record whose real state is non-committable (e.g. a future `archived`/`sold-out` fixture) shows **no** commitment label at all, with the real state named as the reason — "unavailable cannot purchase" and "archived cannot purchase" as tested, real invariants, not incidental truths.
- A record whose real state *would* permit commitment (the current fixture, `commercialState: "available"`) still shows no functional control — only the real label as disclosed text, with the real M6.6 configuration gap named as the reason.
- No fake Buy button exists in either case — confirmed directly (`tests/routes/products-composition.test.tsx`'s own pre-existing "never renders a functional Buy/checkout control" test, reconfirmed passing against this new implementation).

## M6.6 Gate

`TRANSACTION_ACTIVATION_CONFIGURED = false` encodes a real, freshly audited repository fact (see `docs/implementation/M6_UTILITIES_READINESS.md` "M6.6 — Transaction activation" for the full itemized audit: no seller identity, no real price/currency/tax/shipping/licensing/payment-provider configuration exists anywhere in this repository). This is not a feature flag a developer would casually flip — the comment directly above it in source states plainly that flipping it requires the actual configuration to exist first.
