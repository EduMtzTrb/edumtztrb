# M2.1 — Token Foundation

## Status

**Complete (reconciled)**

This report was corrected after a review found that the original implementation had silently converted several Design-System-approved *ranges* and *unvalued approved names* into single, final-looking token values — the low end of each typography range, the midpoint of each grid margin/gutter range, and a chosen neutral for `color-disabled`/`color-district-accent`/three of the four surface levels. None of those specific numbers is actually approved anywhere in `DESIGN_SYSTEM_v1.0.md`; presenting them as resolved tokens was this implementation making a design decision it doesn't own. All of them have been reverted to a deliberately **unresolved** state (see **Range-Based Values Corrected** and the provenance table below). Every token that *is* populated now traces to an exact approved value, an exact approved scale entry, or a technical default alias explicitly justified by this repository's own already-existing behavior — never a guessed point within a range.

Every token family `DESIGN_SYSTEM_v1.0.md` §60 approves (Typography, Spacing, Grid, Neutral color, Semantic color, Line and geometry, Surface — 68 individually named tokens) is declared. 45 hold a real, traceable value; 23 are declared with an intentionally empty value, each with a comment recording exactly what the Design System does and doesn't specify. Opacity and layer order — named in the Implementation Plan's own M2.1 description but absent from the Design System entirely — remain unimplemented, unchanged from the original pass.

## Purpose

Translate the Approved Design System into the first reusable static implementation foundation — raw design tokens — before any district-specific composition begins, without silently resolving any decision the Design System hasn't actually made. Per `IMPLEMENTATION_PLAN_v1.0.md` §7, M2.1 ("Token foundation"): "Implement semantic token families for typography, spacing, grid, neutral/semantic color, line weight, radius, opacity, layer order, focus, surfaces, borders, actions, states, and district accents."

## Governing Sources

Unchanged from the original pass — `IMPLEMENTATION_PLAN_v1.0.md` §7; `DESIGN_SYSTEM_v1.0.md` §6–§12 (typography, spacing, grid, color, surfaces, line/border/radius) and §60–63 (the approved token registry and implementation governance). This reconciliation re-read §6, §7, §9.1, §10.2, §10.6, §11, and §12.1 line by line specifically to separate exact values from ranges and from purely descriptive/relational text — see **Range-Based Values Corrected** and **Unresolved Values**.

## Baseline Before (of this correction)

M2.1 as originally implemented: all 68 approved token names declared, all populated with a concrete value. Re-inspection against the exact wording of `DESIGN_SYSTEM_v1.0.md` found that a meaningful subset of those values were never actually approved — the document gives a *range* or a *name only*, and the implementation had picked a specific point (or a specific neutral-color reuse) and presented it identically to the values that genuinely are exact and approved, with no way for a reader to tell the two apart. That is the defect this task corrects. Nothing about the file/route/component structure from M2.1's first pass changed — only which token values are populated versus left deliberately empty.

## Token Classification Method

Every token was re-classified into exactly one of six states before deciding whether to populate it:

- **Exact approved value** — `DESIGN_SYSTEM_v1.0.md` states one specific number/hex/name for this role, no range.
- **Approved fixed scale value** — part of an explicitly enumerated scale with no ambiguity (e.g. the spacing scale).
- **Approved range — unresolved application** — the Design System gives a min–max range and states sizes are "fluid," without specifying a point or interpolation curve.
- **Approved token name — value unresolved** — §60 registers the name; no value of any kind is given anywhere in v1.0.
- **Derived technical alias explicitly supported by source** — not itself a design decision: either (a) a standard CSS implementation technique for an unambiguous approved concept (e.g. `9999px` for "circular"), or (b) a default pointing at an already-exact approved value, justified by this repository's own already-existing, already-tested behavior (not a Design System preference) — e.g. `color-focus`'s dark-field default, justified by `html { color-scheme: dark }` having been the site's actual rendering since Milestone 1, not by the Design System expressing any preference for dark over light.
- **Implementation interpretation** — this implementation chose a specific value with no textual anchor strong enough to qualify as the alias category above. **No token may remain populated under this classification** — this is exactly what the correction removes.

Only the first three categories, plus (b)-type technical aliases, are populated below. Everything that was previously an "Implementation interpretation" — the low end of each typography range, the midpoint of each grid margin/gutter range, the `color-disabled`/`color-district-accent` neutral reuse, and three of the four surface-level tone assignments — is now declared with an intentionally empty CSS value.

## Unresolved Values

23 approved token names are now declared with a deliberately empty CSS value (`--token-name: ;` — valid per the CSS Custom Properties spec, which permits an empty token stream) rather than a guessed point value:

`type-display`, `type-h1`, `type-h2`, `type-h3`, `type-body-large`, `type-body`, `type-body-small`, `type-caption`, `type-metadata`, `type-annotation`, `type-label`, `margin-compact`, `margin-medium`, `margin-wide`, `gutter-compact`, `gutter-medium`, `gutter-wide`, `color-disabled`, `color-district-accent`, `line-standard`, `surface-1`, `surface-2`, `surface-overlay`.

Each is documented in its own file with the approved range (where one exists) and which later work package owns resolving it (M2.2 for typography, M2.3 for grid margin/gutter, M2.4/whichever work package first builds real disabled-state UI or overlay composition for the rest, and Milestone 5/district-level work for `color-district-accent`, which is explicitly not a shared-system decision at all per §10.6/§63).

An empty custom property is intentionally *not* the same as omitting the token entirely: the approved **name** is still registered and protected by the token-contract test suite (so it can't be silently deleted or renamed), while the **value** correctly reflects that no design decision has been made yet. Referencing an empty custom property without a `var(--x, fallback)` fallback produces an invalid declaration that the browser ignores — a safe failure mode if any future code accidentally reaches for one of these before it's resolved, rather than silently rendering a plausible-but-wrong number.

## Temporary Technical Fallbacks

Only one token in this codebase is a genuine "technical fallback" in the sense this task's instructions describe (a value needed for something to work now, clearly labeled as not a final design truth): **`surface-field`** (and its `-on-dark`/`-on-light` components).

- `surface-field` is the only surface-level token with **strong, near-verbatim textual support**: §10.2 literally describes Void 1000 as "Deep environmental field" and Paper 50 as "Primary light field," which is essentially §11's own definition of Field ("The environmental background") restated. This is markedly stronger evidence than the other three surface levels have (see the provenance table) — closer to "derived technical alias" than to a guess.
- It is also **load-bearing right now**: `src/app/globals.css`'s `body { background: var(--surface-field); }` is real, currently-rendering, already-established page background — reverting it to empty would remove the page's background entirely, a real visible regression, not a neutral correction.
- It is retained, explicitly labeled in `surface.css`'s header comment as resting on inferred-but-strongly-supported textual evidence rather than an explicit named cross-reference, so a future reader (or M2.4, which owns the compositional Field/Plane/Frame primitives that will eventually consume this properly) can re-evaluate it with full context rather than mistaking it for an equally-exact §10.2 table entry.

No other token in this codebase is currently depended upon by any real, rendering CSS while also resting on anything less than an exact approved value — confirmed by inspecting every `var(--...)` usage in `globals.css` and `shell.css` before deciding what could safely be reverted to unresolved.

## Tests Updated

`tests/tokens/token-contract.test.ts` restructured, net +77 tests (170 → 247 total in the suite):

- `APPROVED_TOKENS` is now `[...RESOLVED_TOKENS, ...UNRESOLVED_TOKENS]` (still 68 total, still transcribed independently from §60 — unchanged as the source-of-truth for *names*).
- **New**: `it.each(RESOLVED_TOKENS)` — asserts each of the 45 resolved tokens has a non-empty declared value. Protects against a resolved token *regressing* to empty by accident.
- **New**: `it.each(UNRESOLVED_TOKENS)` — asserts each of the 23 unresolved tokens has exactly an empty declared value. This is the test that directly encodes this correction: it fails if anyone re-introduces a guessed point value for a range-only or name-only token without going through this file's own review process.
- **New**: `it.each(UNRESOLVED_AUXILIARY_TOKENS)` — same check for the 8 non-registry `-on-light`/`-on-dark` auxiliary variants that follow their unresolved parent.
- **New**: a check that `globals.css`/`shell.css` reference *no* unresolved token at all (not even with a fallback) — protects against something silently starting to depend on one of these before it's actually resolved.
- Unchanged: the "all 68 names declared," "no retired Milestone-1 name remains," and "`index.css` imports all six files" checks from the original pass.

This suite still does not test exact hex/px *values* for anything beyond presence/absence of a value (per M2.1's own testing scope, unchanged: "do not over-test visual details that are better verified later") — it tests the *resolved-vs-unresolved contract* this correction establishes, not specific numbers.
