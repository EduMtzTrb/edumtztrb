## District navigation architecture

One shared system, not six incompatible components:

- **`src/components/shell/districtNavigation.ts`** — pure data configuration. `DistrictNavRole` (`"overview" | "curated" | "grouping" | "comprehensive" | "section"`) encodes the shared conceptual order once; `DISTRICT_NAVIGATION` assigns each district's own approved labels/routes to those roles.
- **`src/components/shell/DistrictNav.tsx`** — the one component every district's layout composes, parameterized by `district`. No per-district component variant exists.
- **`src/styles/district-nav.css`** — one stylesheet, one set of class names, shared by all six districts.

## Six district configurations

Every `href` is one of the 53 routes already approved and built by M1.3 (`PLATFORM_SPECIFICATION.md` §5.3–§5.8) — none invented, verified directly by `DistrictNav.test.tsx`'s "route validity" test against an independently transcribed approved-route list (the same "don't self-confirm" discipline `tests/routes/route-contract.test.ts` already established).

| District | Overview | Curated | Groupings | Comprehensive |
|---|---|---|---|---|
| Work | `/work` | Selected → `/work/selected` | *(none — see below)* | All Work → `/work/all` |
| Research | `/research` | Current → `/research/current` | Publications, Writing, Talks | Archive → `/research/archive` |
| Lab | `/lab` | Active → `/lab/active` | Prototypes, Tools, Studies | Archive → `/lab/archive` |
| Art | `/art` | Selected → `/art/selected` | Exhibitions | Archive → `/art/archive` |
| Products | `/products` | Featured → `/products/featured` | Digital, Physical, Services | Archive → `/products/archive` |

**About** does not follow this order at all — Platform Specification §5.8's approved route family is a fixed profile/practice/experience/education/capabilities/recognition/current-focus section structure, not a curated-vs-archive distinction. Modeling it with the same `curated`/`grouping`/`comprehensive` roles would misrepresent it as something it isn't (this task's own explicit instruction against forcing false cross-district symmetry). About's nav uses a distinct `role: "section"` for its seven section links, with only `overview` (`/about`) shared with the other five districts' first item.

## Deliberately omitted grouping routes

`PLATFORM_SPECIFICATION.md`'s own route tables (§5.3–§5.7) confirm several grouping families are **dynamic-only, with no static index page**: `/work/practice/{practice-area}`, `/work/collections/{collection}`, `/research/themes/{theme}`, `/art/series/{series}`, `/art/medium/{medium}`, `/products/collections/{collection}` — verified directly against `src/app/**` (each of those directories contains only its `[param]` subfolder, no sibling `page.tsx`). Per this task's own instruction ("do not invent unapproved routes to make every district symmetrical"), none of these appears as a top-level district-nav destination. They remain reachable contextually — from a record's own metadata/relationships (M3.5) — once real records exist; inventing a "browse all collections" page to fill this tier would have been exactly the kind of unapproved route this task forbids. This is why Work's configuration has no `grouping`-role item at all: none of its grouping routes has a real static destination.

## Shared conceptual order — item 5, Search

No district was given a local "Search" item. Global Search (`/search`) already provides that access (M1.4/M3.7), and no district specification requires an independent local search route — adding one would have been "a fake Search item," this task's own explicit prohibition. `DistrictNav.test.tsx` asserts directly that no district item links to `/search` or contains the word "search."

## Global vs. district navigation distinction

Structurally: two separately labeled `<nav>` landmarks per page (`GlobalNav`'s "Primary"/"Utilities", `DistrictNav`'s `"{District} navigation"`), never merged into one list, confirmed by `DistrictNav.test.tsx`. Visually: `district-nav.css` uses its own class names (`.district-nav-list`) and never reuses `shell.css`'s `.global-nav-list`/`.global-utilities-list`, confirmed at the source level (`tests/tokens/district-nav-contract.test.ts`). `GlobalNav.tsx`, `AppShell.tsx`, and `shell.css` (beyond the M3.7 commit already made) are untouched by this package.

## Active district view — a distinct semantic from active district

`GlobalNav`'s single district link intentionally treats every nested route as "within this district" (prefix match — correct for one link representing an entire district). `DistrictNav` uses **exact-path matching only**: every item is a sibling destination at the same rank (Overview, Selected, Archive, ...), so applying `GlobalNav`'s prefix logic here would incorrectly mark "Overview" (`/work`) as active on every other district page, since `/work` is a literal string prefix of `/work/selected`, `/work/all`, etc. Tested directly: on `/work/selected`, "Selected" carries `aria-current="page"` while "Overview" and "All Work" carry none; on a canonical-record route (`/art/some-artwork`), no district-nav item is marked current at all (that page isn't one of the district nav's own destinations) — exactly this task's own §B4 distinction between "active district," "active district view," and (later, M3.11) "selected filter/lens."

## Responsive behavior

`.district-nav-list` uses `flex-wrap: wrap` (verified at the source level) — items reflow onto additional lines rather than clipping or requiring a disclosure menu, matching the same "no elaborate mobile choreography" principle M3.7 established. No breakpoint was introduced beyond the already-approved 768px/1024px vocabulary (none needed — no `@media` rule exists in `district-nav.css` at all, since simple wrapping already keeps every item reachable at every width, given the maximum item count is eight, for About).

## Accessibility

- Every item is a native `<a>` (via `next/link`) — full keyboard reachability, no custom key handling, no gesture/hover-only path (confirmed: zero `:hover` rules in `district-nav.css`).
- 44px minimum touch target (`min-height: 44px`), matching the existing `shell.css` convention exactly.
- `:focus-visible` outline reuses the shared `--color-focus` token (not a new focus treatment).
- Active state uses `aria-current="page"` plus non-color visual treatment (underline + weight), matching `GlobalNav`'s established pattern.
- No motion: zero `transition`/`animation`/`@keyframes` in `district-nav.css`.
