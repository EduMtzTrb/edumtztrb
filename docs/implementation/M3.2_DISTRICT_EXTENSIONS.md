## Architecture

**Owner-correlated discriminated extension**, not a district god-object. Each district gets its own extension interface (`WorkExtension`, `ResearchExtension`, `LabExtension`, `ArtExtension`, `ProductsExtension`, `AboutExtension`), each carrying its own literal `extensionFor` discriminant. A generic mapping type,

```ts
export type ExtensionForDistrict<D extends CanonicalOwnerDistrict> = Extract<DistrictExtension, { extensionFor: D }>;

export interface DistrictRecord<D extends CanonicalOwnerDistrict = CanonicalOwnerDistrict> extends CanonicalRecordBase {
  ownerDistrict: D;
  extension: ExtensionForDistrict<D>;
}
```

composes `CanonicalRecordBase` (M3.1) with exactly the one extension type correlated to `D`. `WorkRecord = DistrictRecord<"work">`, etc.; `AnyDistrictRecord` is the union of all six. This is a real generic owner→extension mapping (this task's own §A3 requirement), not a comment-only convention — see "Compile-time invariants" below for the proof.

No single interface holds every district's fields (§A4) — each extension interface stays small (fewer than 16 fields; the largest, `AboutExtension`, has 12), and `district-extensions-source-contract.test.ts` protects this mechanically. No `WorkRecord`/`ResearchRecord`/etc. duplicates the universal contract independently — each is `CanonicalRecordBase` plus one small `extension` object, never a parallel reimplementation.

## Validation strategy

Dependency-free runtime validators (`validateDistrictRecord`, `assertValidDistrictRecord` in `DistrictExtensions.ts`) — no new dependency added, for the same reasoning M3.1 already established (`IMPLEMENTATION_PLAN.md`: "schema technology is an implementation choice"; no real data-ingestion boundary exists yet in this repository). Compile-time types cannot protect data arriving already untyped (e.g. `JSON.parse`), so the validators exist specifically for that boundary:

- **Extension discriminant/owner consistency** — `extension.extensionFor === record.ownerDistrict`, checked first; a mismatch short-circuits further validation.
- **Structural field validity** — every present string field must be a non-empty string; every present enum field must be a member of its approved vocabulary; arrays must actually be arrays of the correct nested shape.
- **Non-empty required semantic values** — no field is invented as complete; a present-but-blank string is rejected, but an absent field is not (matching "do not impose mandatory content where upstream says 'where applicable'").
- **Invalid cross-district fields** — an unknown-key check (`checkUnknownKeys`) runs against every extension object using a per-district allow-list; a Product's `price` field appearing on a Work extension is rejected by name, not merely absent from the type.
- **Impossible enum/value combinations** — `ProductPriceBasis`'s four-variant discriminated shape is checked per `kind` (a `"fixed"` price without `amount`/`currency` is rejected; an unrecognized `kind` is rejected).
- **Malformed nested values** — `AboutValue`, `AboutExperienceEntry`, and `AboutEducationEntry` array entries are each individually validated for their own required fields.
- **Duplicated extension identities** — each record carries exactly one `extension` object (a 1:1 relationship enforced by the type itself), so there is no "duplicate extension" case at the single-record level to guard against; duplicate canonical-record IDs across a record set remain M3.1's `createRecordRegistry`'s responsibility (unchanged, not duplicated here).

## Universal-identity preservation

No extension interface redefines `id`, `slug`, `title`, `ownerDistrict`, `visibility`, `curatorialInclusion`, `lifecycle`, `authorship`, `media`, or `relationships` — all nine remain owned exclusively by `CanonicalRecordBase`. This is enforced three ways: (1) structurally, none of the six extension interfaces declares any of those field names; (2) by `district-extensions-source-contract.test.ts`'s explicit per-interface negative assertions; (3) at compile time, `DistrictExtensions.type-tests.ts` proves an extension object literal carrying an `id` field is rejected (excess-property check).

## Work extension

`WorkExtension`: `context`, `contribution`, `collaborationContext`, `process`, `outcome` — all optional strings. Sourced from Work Universe §13 (Project Presentation: "identity, context, intent, personal role, contribution, method, outcome, credits") and §16 (WU-16: "Collaborative work must distinguish personal contribution from total project authorship"), and `PLATFORM_SPECIFICATION.md` §12.1. Practice areas/disciplines are **deliberately not modeled here** — Work Universe §9 itself calls them "lenses," and IA §15.1/§11.2 treats discipline as a classification dimension; `CanonicalRecordBase.disciplines` (M3.1) is already the correct capability slot (this task's own §A14 option 1: reuse the existing classification-reference abstraction rather than inventing a parallel one). Full controlled-vocabulary classification mechanics remain M3.4's territory.

## Research extension

`ResearchExtension`: `inquiry`, `context`, `methods`, `evidenceSummary`, `currentPosition`, `uncertainty` (all optional strings) plus `researchActivityState?: "ongoing" | "concluded"` — IA §6.2.D's own worked example of a Research domain-specific state, kept fully separate from `CanonicalRecordBase.lifecycle`. Sourced from Research Universe §10 (Organization Model) and §11 (Editorial Language: "the state of knowledge stays visible... the interface must never make a hypothesis look like a verified result") and `PLATFORM_SPECIFICATION.md` §12.2. `currentPosition` is the field that lets a record represent an evolving, provisional understanding honestly, tested directly in `DistrictExtensions.test.ts`.

## Lab extension

`LabExtension`: `experimentQuestion`, `version`, `lineageNote`, `method`, `evidence`, `observation`, `failureNote`, `nextQuestion` (optional strings) plus `experimentState?: LabExperimentState` — Lab Universe §14's approved ten-value vocabulary (`framed`, `trial`, `active`, `branching`, `stabilized`, `paused`, `concluded`, `abandoned`, `transferred`, `archived`), reproduced verbatim as the enum's members. This is Lab's own domain-specific state (IA §6.2.D), never flattened into `CanonicalRecordBase.lifecycle`.

**Critical invariant, tested directly:** `fixtureLabRecordWithExtension` sets `experimentState: "abandoned"` while the base record (from M3.1's own `fixtureLabRecord`) is `lifecycle: "failed"`, `curatorialInclusion: "included"`, `visibility: "public"` — proving a failed/abandoned experiment remains a fully valid, fully public canonical record, and that the district-specific state and the universal lifecycle never have to agree with each other, let alone be derived from one another. `lineageNote` is a narrative field only; formal branch/successor links between Lab records use `CanonicalRecordBase.relationships` (`derived-from`/`related-to`), never a duplicate relationship mechanism inside the extension.

## Art extension

`ArtExtension`: `medium`, `dimensions`, `artistStatement`, `exhibitionContext`, `editionNote` (optional strings) plus `presentationCondition?: ArtPresentationCondition` — Art Universe §17's shared preservation-state vocabulary (`live`, `partially-functional`, `documented`, `reconstructed`, `emulated`, `no-longer-reproducible`), Art's own domain-specific state. `editionNote` is deliberately restrained: Art Universe §20 states exactly what stays in Art when a work becomes purchasable — "whether an edition exists, edition size when artistically relevant, material or format, and a labeled passage to Products" — and exactly what does not ("price, currency, stock or remaining edition count..."). `editionNote` is a free-text field for that restrained factual note only; `district-extensions-source-contract.test.ts` and `DistrictExtensions.test.ts` both assert no `price`/`stock`/commercial field can appear on `ArtExtension`, at the source level and via a runtime unknown-key rejection test.

## Products extension

`ProductsExtension`: `proposition`, `intendedRecipient`, `included`, `exclusions`, `fulfilmentMethod`, `leadTime`, `licenseSummary`, `requirements`, `support`, `commitmentLabel` (optional strings), `productFamily?: ProductFamily` (Products Universe §7's seven approved families: digital, physical, service, license, edition, subscription, commission), `priceBasis?: ProductPriceBasis` (a four-variant discriminated union matching Products Universe §12's four permitted price framings — fixed, from, quotation-required, hourly-or-package — descriptive data only, never a computed or binding value), and `commercialState?: ProductCommercialState` (Products Universe §13's thirteen-value approved lifecycle). `commitmentLabel` holds the literal action text (`PLATFORM_SPECIFICATION.md` §33.1: "commitment labels are literal") — a string only, with no executable action anywhere in this module.

**`productFamily` versus "Product family" as a grouping dimension** — worth stating explicitly, since the word appears in two places in the source authority. Products Universe §8's Product Hierarchy uses "Product Families" as Level 2 (digital/physical/service/license/edition/subscription/commission) — a *structural* determination of which commercial mechanics apply to a given offer, functionally identical in role to `CanonicalRecordBase.contentType` on the base contract. This is what `productFamily` models here. "Collections" (Product Hierarchy Level 3 — curated groupings that reference records without owning them) are a separate, genuinely classification/relationship concern and are **not** modeled in this package — they remain M3.4/M3.5 territory.

**No checkout, cart, payment, tax, or fulfilment-service logic exists anywhere in this module** — confirmed by `district-extensions-source-contract.test.ts`'s explicit function-name check and by `DistrictExtensions.test.ts`'s assertion that no field on the fixture Products extension is ever `typeof "function"`.

## About extension

`AboutExtension`: `practiceStatement`, `biography`, `location`, `affiliations`, `recognition` (optional strings), `methods`, `capabilities`, `languages` (optional string arrays), `availability?: AboutAvailabilityState` (About Universe §15's four states), plus two typed array fields with real internal structure: `experience?: AboutExperienceEntry[]` (`organization`, `role` required; `period`, `context` optional) and `education?: AboutEducationEntry[]` (`institution`, `qualification` required; `field`, `period` optional), and `values?: AboutValue[]`.

`AboutValue` deliberately encodes About Universe §13's own stated invariant — "each requires four parts: the principle, its interpretation, its consequence in practice, and its tension or limitation" — as required fields (`principle`, `interpretation`, `consequence`) plus one optional (`tension`, since not every value is under active tension). This is validated at runtime (`DistrictExtensions.test.ts`'s "enforces About Universe §13's four-part Value structure" test constructs a value with only `principle` and confirms both missing fields are individually reported).

Not all twelve About Universe §28 record types are modeled — building all twelve would overbuild well past "smallest coherent architecture" for a first extension package. Credential and Timeline Event are deferred (see "Deferred items"). Contact pathways are a utility-page concern (`PLATFORM_SPECIFICATION.md` §18.3, `/contact`), not canonical About record content, and are intentionally not modeled here.

## Home exclusion

Home receives no extension type. `CanonicalOwnerDistrict` (M3.1) already excludes `"home"` as a valid value, so `DistrictRecord<"home">` cannot be named — `DistrictExtensions.type-tests.ts` proves this with a `@ts-expect-error` directly on the type instantiation. No `HomeExtension` interface exists anywhere in the module, confirmed by `district-extensions-source-contract.test.ts`.

## State-dimension boundary

Four dimensions stay separate everywhere in this package: curatorial inclusion, visibility, and universal lifecycle remain exclusively `CanonicalRecordBase`'s (M3.1, untouched); the fourth — domain-specific state (IA §6.2.D) — is represented per district with a precisely named field (`researchActivityState`, `experimentState`, `presentationCondition`, `commercialState`), never a generic `status`. No extension interface declares a field literally named `status`, confirmed by the same source-contract test suite that already protects this invariant on `CanonicalRecordBase` (M3.1). `DistrictExtensions.test.ts` includes direct behavioral proof that a district-specific state value never has to (and structurally cannot, since they are unrelated object fields) agree with the base record's universal lifecycle or visibility.

## Classification boundary

No `tags: string[]` or equivalent uncontrolled tag cloud exists anywhere in this module (`district-extensions-source-contract.test.ts` asserts this directly). Fields that are genuinely classification dimensions — Work's practice areas/discipline, Art's series, Products' collections, Research's territory, About's affiliations-as-grouping — are **not** modeled as new ad hoc fields here. Where M3.1 already provides a suitable capability slot (`disciplines`, `themes`), districts are documented as reusing it rather than duplicating it (Work, above). Where no such slot exists yet and the concept is genuinely a controlled-vocabulary grouping rather than record-body content (Collections for Products, Series for Art, Territory for Research), it is left entirely to M3.4/M3.5 rather than invented here as a placeholder string field.

## Relationship boundary

No extension interface declares a `relationships` or `media` field — both remain exclusively `CanonicalRecordBase`'s. Lab's `lineageNote` and Art's `editionNote` are narrative text only; any *formal* connection between two canonical records (a Lab experiment maturing into Work, an Art record connected to its Products edition) uses `CanonicalRecordBase.relationships` with M3.1's already-approved six-type IA §5.3 vocabulary. Several district Universe documents use their own richer relationship-label vocabulary in prose (Lab Universe §20: "Developed into, Applied in, Tested through, Earlier iteration, Resulted in, Shared method"; Research Universe §9: "Informed by, Applied in, Tested through, Generated by, Extended in, Reframed by, Developed into") — these are **not** new relationship types invented here. They map onto IA's existing approved six (`related-to`, `derived-from`, `informed-by`, `tested-in`, `developed-into`, `commercialized-as`) exactly as M3.1's own fixtures already demonstrate for the Research→Lab→Work chain (IA §5.4). No new relationship type was added in this package.

## Serialization

Every extension field is a plain string, string array, enum-typed string, or a small nested plain-object shape (`ProductPriceBasis`, `AboutValue`, `AboutExperienceEntry`, `AboutEducationEntry`) — no function, `ReactNode`, or class instance anywhere. `DistrictExtensions.test.ts`'s "Serialization" describe block round-trips every district-extended fixture through `JSON.parse(JSON.stringify(...))` and confirms every extension field value is never `typeof "function"`.

## Compile-time invariants

`DistrictExtensions.type-tests.ts` (never imported, checked only by `tsc --noEmit`) proves, via `@ts-expect-error`:

- A Work-owned record cannot receive a Research extension.
- A Research-owned record (via the generic `DistrictRecord<"research">` form directly, not just the named alias) cannot receive a Products extension.
- A Lab-owned record cannot receive an Art extension.
- `DistrictRecord<"home">` cannot be instantiated at all — `"home"` fails the `D extends CanonicalOwnerDistrict` constraint.
- An extension object literal cannot carry an `id` field (excess-property rejection).

Plus one positive check (a fully valid, correlated About record) proving the mapping accepts a genuinely matching owner/extension pair. Confirmed via a clean `npm run typecheck` run — a directive that stopped matching a real error would itself surface as an "unused `@ts-expect-error`" compile error.

## Runtime validation evidence

`DistrictExtensions.test.ts` includes direct tests for: owner/extension mismatch rejection (both `validateDistrictRecord`'s issue list and `assertValidDistrictRecord`'s thrown message), an unrelated key (`id`) inside an extension object being rejected, a blank-string field being rejected, cross-district field leakage (a `price` key on a Work extension, `price`/`stock` keys on an Art extension) being rejected by name, invalid enum values (`researchActivityState`, `experimentState`) being rejected, malformed `priceBasis` (missing `amount`, unknown `kind`) being rejected, and malformed `AboutValue`/`AboutExperienceEntry` nested entries being rejected with a field-specific path.
