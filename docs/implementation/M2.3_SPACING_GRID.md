## Compositional Spacing

Implemented as `.field-interval` in the new `src/styles/layout.css`, a single fluid `padding-block`:

```css
padding-block: clamp(3rem, 0.6667rem + 9.3333vw, 10rem);
```

Derived the same way as M2.2's type scale: a linear interpolation hitting 48px (3rem — already larger than `space-6`/32px, appropriately "compositional" from the narrowest viewport up) at a 400px viewport, growing to 160px (10rem — well beyond the largest fixed token, `space-12`/256px is still bigger by design, but 160px is a deliberately generous mid-to-large architectural interval) at a 1600px viewport. This satisfies §13.3 ("may be fluid, viewport-sensitive... larger than the fixed token scale") directly. Applied to each page shell's `<header>` — the element wrapping the dominant heading/anchor — giving every shell the "concentrated void around a major anchor" behavior from §15.3, without inventing per-route values. **Not** built as a family of named tokens (`space-giant`, `space-huge`, etc.) — one reusable class is the whole mechanism, per the task's explicit instruction to prefer the simplest formulation.

Relation to fixed local spacing: completely separate mechanisms. `space-*` tokens remain for small/local/reusable UI relationships (unaffected, unused by `.field-interval`); `.field-interval` is for the one or two major architectural intervals per page. Both coexist; neither was collapsed into the other.

## Grid Token Calibration

| Breakpoint class | Columns | Margin (calibrated) | Gutter (calibrated) | Composition behavior |
|---|---:|---|---|---|
| Compact (<768px) | 4 | `clamp(1rem, 0.6421rem + 1.7897vw, 1.5rem)` — 16→24px | `clamp(0.75rem, 0.571rem + 0.8949vw, 1rem)` — 12→16px | Full width minus margin, single grid |
| Medium (768–1023px) | 8 | `clamp(2rem, -1.0118rem + 6.2745vw, 3rem)` — 32→48px | `clamp(1.25rem, 0.4971rem + 1.5686vw, 1.5rem)` — 20→24px | Full width minus margin, single grid |
| Wide (1024–1600px) | 12 | `clamp(3rem, -0.5556rem + 5.5556vw, 5rem)` — 48→80px | `clamp(1.5rem, 0.6111rem + 1.3889vw, 2rem)` — 24→32px | Grid reaches `composition-max` at 1600px |
| Ultra-wide (>1600px) | 12 (unchanged) | Same as Wide, capped — outer space becomes void | Same as Wide, capped | `max-width: composition-max` + `margin-inline: auto` centers the grid; excess viewport becomes architectural field automatically, no new token |

**Calibration method** (same rigor as M2.2's `clamp()` derivation, computed exactly, not estimated): each token's `clamp()` is a linear interpolation that reaches its approved range's *minimum* at the start pixel of its own breakpoint band and its *maximum* at the end pixel of that band — verified by direct arithmetic (e.g. margin-wide evaluates to exactly 48px at 1024px and exactly 80px at 1600px). No token uses a fixed midpoint, a fixed minimum, or a fixed maximum throughout its whole band — each moves fluidly and predictably within its approved envelope. Band boundaries: 320–767px (compact), 768–1023px (medium), 1024–1600px (wide) — the wide band's ceiling is deliberately the same 1600px as `composition-max`, so "wide" and "ultra-wide" meet exactly at the guardrail with no gap or overlap.

Ultra-wide deliberately has **no separate token** — the approved token registry (§60) has no ultra-wide margin/gutter names, and §14.2 describes ultra-wide behavior qualitatively ("gains margin, void, field depth") rather than as a numeric range. `max-width: var(--composition-max)` + `margin-inline: auto` on `.composition` produces exactly that behavior structurally: any viewport beyond 1600px simply centers the capped grid, turning the excess into browser-computed outer void — verified directly in the served CSS during this task (see **Browser Verification**).

## Maximum Composition Behavior

`composition-max: 1600px` (already resolved, unchanged) is applied as `max-width` on `.composition`, combined with `margin-inline: auto`. Below 1600px, `.composition` fills the viewport minus margins as before. At and above 1600px, the grid stops growing and centers — content stays at its calibrated wide-breakpoint width; the browser mechanically converts any additional viewport width into equal void on both sides. This is not a "hard boundary" in the sense of clipping anything — it's a natural centering behavior, matching §14.2's "not a universal hard boundary" framing exactly.

## Proportional Grammar

§15's relational principles (content-to-void balance, semantic scale authority, record anchor, evidence zones, full-bleed conditions) are explicitly **not** implemented as fixed ratios or templates in this task — per §15.2 ("no universal image/text ratio is approved") and the task's own prohibition on rigid universal proportional templates. What M2.3 provides instead is *capacity*: `.composition`'s 4/8/12 grid establishes shared axes any future content can align to or deliberately offset from (§14.3, §11.3–§11.4); `.composition > * { grid-column: 1 / -1 }` gives every current shell full-width occupancy by default without forcing narrower spans that no content yet needs (§14.3: "the grid provides alignment without requiring occupancy") — a future component can opt into `grid-column: span N` once real content requires an unequal split. No proportional decision was frozen in.

## Accessibility

- **No horizontal overflow expected:** `.composition` uses `width: 100%` with `max-width`, not a fixed width, and margins are `padding-inline` (subtracted from available width, not added on top) — the standard non-overflowing pattern. Not visually confirmed (no browser).
- **Mobile margin is not excessive:** at 390px, calibrated margin is 17.25px per side (34.5px total) — leaves 355.5px of usable width, comfortably more than half the viewport.
- **Semantic reading order intact:** `grid-column: 1 / -1` (full-width) does not reorder anything — CSS Grid's `order` property was never used, so DOM order and visual order remain identical (verified by direct inspection of `layout.css` — no `order:` declaration exists anywhere in it).
- **Zoom/reflow:** consistent with M2.2's typography, `.composition`'s margin/gutter are `clamp()`-based with `rem` bounds, so they scale correctly with text-only zoom by the same CSS-mechanics reasoning documented in `M2.2_TYPOGRAPHY.md`. Not empirically tested.
- **Touch-target space:** not reduced — no existing interactive element (`GlobalNav`, skip-link) was touched by this task.
