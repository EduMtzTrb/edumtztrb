# M1.4 — Shared Application Shell

## Status

**Complete**

Every approved route now renders inside one stable, accessible shared application shell. The visitor can reach every primary district and global utility from anywhere, current platform context (district/utility) is identifiable without relying on color alone, and the full 49-route architecture from M1.3 continues to build without introducing later-milestone functionality.

## Purpose

Establish the common application structure that surrounds every approved route: application/document root, global navigation, global utilities access, active district context, and a stable orientation layer — per `IMPLEMENTATION_PLAN_v1.0.md` §6, work package M1.4.

## Baseline Before

- `src/app/layout.tsx` rendered only `<html lang="en"><body>{children}</body></html>` — no navigation, no shared chrome of any kind.
- Each of the 7 district layouts (`work`, `research`, `lab`, `art`, `products`, `about`) and 3 utility layouts (`search`, `index`, `contact`) wrapped their children in a `data-district="..."` / `data-utility="..."` `<div>` only — no navigation.
- All 49 M1.3 route pages rendered a bare `<main>` with a single identifying `<h1>` and nothing else.
- No shared component directory existed (`src/components/` did not exist).
- `src/app/globals.css` imported only the token stylesheet (`src/styles/tokens/index.css`) plus a base reset and reduced-motion rule.
- No skip link, no focus styling beyond the browser default, no way to reach any route except by typing its URL directly.
- Git status confirmed no unrelated uncommitted work would be disturbed (see the pre-existing uncommitted documentation-reorganization files already flagged by M1.1/M1.1A, left untouched throughout).

## Shell Architecture

Two new files under `src/components/shell/`, composed from the root layout:

- **`AppShell.tsx`** (Server Component) — the application/document-root-adjacent shell. Renders, in order: a skip link, a `<header>` containing `GlobalNav`, and a `<div id="main-content" tabIndex={-1}>{children}</div>` wrapping every page's existing route tree unchanged.
- **`GlobalNav.tsx`** (Client Component — the only client boundary in the shell) — renders two `<nav>` landmarks (Primary districts, Utilities) and computes which link is "active" using `useSelectedLayoutSegment()` from `next/navigation`.

`src/app/layout.tsx` now wraps `{children}` in `<AppShell>`; nothing else in the root layout changed. `src/app/globals.css` gained one new `@import "../styles/shell.css";` line (after the existing tokens import) for the shell's structural CSS — no other stylesheet was touched, and no design-token file was modified.

**Relationship to each page's own `<main>`:** the shell never renders a `<main>` itself. Every route's pre-existing `<main>` (from M1.3) remains the page's sole main landmark; the shell's `#main-content` div is a plain, non-landmark anchor point used only as the skip-link target. Verified directly in the built HTML output (see **Validation**) — exactly one `<main>` per rendered page, in every case checked.

## Global Navigation

`GlobalNav` renders the seven permanent primary destinations — Home, Work, Research, Lab, Art, Products, About — using the exact approved labels from `PLATFORM_SPECIFICATION_v1.0.md` §7.1 / `CROSS_UNIVERSE_SYSTEM_REQUIREMENTS.md` CUR-NAV-02, each a `next/link` to its canonical top-level route. No label was renamed, no destination (Blog, Journal, News, Shop, Portfolio, or any other) was invented. District navigation logic (overview → curated → grouping → archive → Search) is not implemented here — per this task's instruction, that belongs to district-specific secondary navigation, out of M1.4's scope, and was left deferred, not inferred from the route tree.

## Global Utilities

A second, separately labeled `<nav aria-label="Utilities">` links to `/search`, `/index`, and `/contact` — kept structurally distinct from the primary district `<nav>` (two landmarks, not one merged list), directly satisfying "Utilities remain distinct from districts" (Implementation Plan Milestone 1 acceptance criterion) and CUR-NAV-03. No Search, Index, or Contact behavior was implemented — all three remain the M1.3 route shells; the shell only links to them.

Language and legal/admin utilities were **not** added: `PLATFORM_SPECIFICATION_v1.0.md` §18.4 states language is a global utility "only when multilingual content is activated," and no launch language has been approved; §18.5 only "defines ownership" for legal/admin, without requiring a route now, and no legal/admin route exists from M1.3 to link to. Adding either would have meant inventing a fake switcher or a route that doesn't exist, which this task explicitly forbids.

## Active Context

`useSelectedLayoutSegment()`, called from a small Client Component (`GlobalNav`) mounted just below the root layout, returns the first route segment under root — e.g. `null` for `/`, `"work"` for any route starting `/work/...` regardless of depth, `"search"`/`"index"`/`"contact"` for the utilities. This is exactly the per-Next.js-version documented pattern for building an active-link component from a Server Component layout (`node_modules/next/dist/docs/.../use-selected-layout-segment.md`), and it naturally covers every case this task requires — top-level district routes, deep district routes (`/work/selected`), dynamic canonical-record routes (`/work/[entry]`), global utilities, and Home — with no per-route special-casing and no parallel routing-state system. The matching link receives `aria-current="page"` plus a non-color visual cue (underline + weight change, see **Accessibility**). Verified in production output for `/work` (static), `/work/selected` (deep static), `/index` (utility, disambiguated from the root `/` which also happens to build to a file literally named `index.html`), and `/work/some-project` (dynamic, server-rendered) — in every case the correct single link carried `aria-current="page"` and the `<h1>` correctly identified the page.

Only `GlobalNav` is a Client Component; `AppShell` and the root layout remain Server Components, per this task's instruction not to make the whole shell a Client Component when a smaller boundary suffices.

## Accessibility

- **Skip link:** `<a class="skip-link" href="#main-content">Skip to main content</a>` is the first focusable element in `<body>`, visually hidden until focused (off-screen positioning, revealed on `:focus`), jumping to the `tabIndex={-1}` div that immediately precedes every page's `<main>` — satisfying WCAG 2.2 AA's Bypass Blocks expectation now that a repeated navigation block precedes page content on every route (this task's own instruction: implement a skip link now if the approved accessibility system requires one; `DESIGN_SYSTEM_v1.0.md` §33 sets WCAG 2.2 AA as the explicit minimum).
- **Semantic navigation:** two `<nav>` landmarks with distinguishing `aria-label`s ("Primary", "Utilities"), each an unordered list of `next/link` elements — real anchors, not buttons or JS-only click handlers, so browser-native link semantics (history, right-click, open-in-new-tab, screen-reader link rotor) all work unmodified.
- **Current-page indication:** `aria-current="page"` (semantic) plus underline + font-weight change (visual, non-color) on the active link — satisfying `DESIGN_SYSTEM_v1.0.md` §39 / CUR-ACC-07 ("no single-channel meaning… color alone").
- **Focus visibility:** `:focus-visible` on every nav link and the skip link gets a 2 px outline in `--state-focus`, offset 2 px, never clipped — matching `DESIGN_SYSTEM_v1.0.md` §35's approved focus treatment exactly (2 px line, platform focus color, never replaced only by a color shift).
- **Keyboard:** every nav link and the skip link is a native `<a>`, reachable and activatable via Tab/Enter with no custom key handling — no essential gesture-only or hover-only path exists anywhere in the shell (CUR-NAV-09, CUR-ACC-03).
- **Touch targets:** every nav link has `min-height: 44px` and horizontal padding via `--space-3`, meeting the 44×44 px minimum in `DESIGN_SYSTEM_v1.0.md` §37 / CUR-ACC-05.
- **No new landmark conflicts:** confirmed exactly one `<main>` per rendered page (see **Validation**); the shell's `<header>` and two `<nav>`s are additive, standard landmarks that do not compete with or duplicate `<main>`.
- **Browser history:** navigation uses plain `next/link` (real `<a href>` under the hood); no custom routing state was introduced, so Back/Forward continue to behave exactly as the browser expects (`PLATFORM_SPECIFICATION_v1.0.md` §24.3, CUR-ACC-10) — unchanged from M1.3.

## Responsive Behavior

Both nav lists use `display: flex; flex-wrap: wrap;` so links reflow onto additional lines rather than being clipped, hidden, or requiring a hamburger/overlay/hover-reveal pattern at any width — every one of the ten destinations (7 districts + 3 utilities) is always simultaneously present and reachable at compact, medium, wide, and ultra-wide viewports, directly satisfying `DESIGN_SYSTEM_v1.0.md` §29's "controls remain reachable and full-sized" / "navigation cannot depend on hover or gesture discovery" and this task's explicit instruction not to hide essential destinations without an accessible replacement. No breakpoint-specific choreography, no collapsing menu, and no JavaScript-driven responsive behavior was implemented — this is deliberately the simplest approved composition, left ready to receive full Design System responsive styling (§28–31) in a later milestone.
