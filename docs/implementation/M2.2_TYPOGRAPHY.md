## Typeface Calibration

Three complete candidate systems were presented to the user (Editorial Architecture: Fraunces/Source Sans 3/JetBrains Mono; Geometric Grotesk: Space Grotesk/Source Serif 4/IBM Plex Mono; Warm Grotesque: Archivo/Newsreader/JetBrains Mono), each evaluated against §7.1–§7.3's stated character criteria. **System B — Geometric Grotesk — was selected by the user.**

| Role | Family selected | Why it satisfies the approved voice | Alternatives considered |
|---|---|---|---|
| Display Voice | **Space Grotesk** | Geometric-but-humanist sans with structured, squared proportions — reads as authored/architectural rather than generic-SaaS or generic-Swiss. Moderately distinctive without becoming expressive spectacle. | Reading Voice | **Source Serif 4** | Adobe's screen-optimized serif; warm and editorial, gives visual contrast against the sans Display voice, purpose-built for sustained reading (Research/About), still human rather than technical. | Newsreader (also editorial serif, considered in System C), Source Sans 3 (sans alternative, considered in System A) |
| Functional Mono | **IBM Plex Mono** | Neutral, technical notation face — not decoratively expressive (satisfies DS-110: "notation, not a technical-aesthetic identity device"). **Rejected as a class:** re-proposing "universal Inter" for any single voice — the Supersession Note (§117 point 1, DS-108/109) explicitly retires that model; none of the three proposed systems included it as the primary choice for more than possible continuity mentions.

## Font Loading

`next/font/google` in `src/app/layout.tsx`, self-hosted at build time (no runtime request to Google, no manual font files, no licensing review needed — Google Fonts are open-license and this is Next.js's standard, framework-native loading strategy):

```ts
Space_Grotesk({ subsets: ["latin", "latin-ext"], weight: ["500", "600"], variable: "--font-display-loaded", display: "swap" })
Source_Serif_4({ subsets: ["latin", "latin-ext"], weight: ["400"], variable: "--font-reading-loaded", display: "swap" })
IBM_Plex_Mono({ subsets: ["latin", "latin-ext"], weight: ["400"], variable: "--font-mono-loaded", display: "swap" })
```

- `latin-ext` is included on all three for French/Spanish/English accented-character coverage (é, ñ, ü, etc.), per the task's own multilingual criterion.
- `display: "swap"` avoids invisible text during load (better perceived performance and avoids a FOIT accessibility issue).
- Only the weights actually assigned to a role are loaded: 500/600 for Display (its two roles, H2/H3 at 500, Display/H1 at 600), 400 for Reading (all Reading roles use 400), 400 for Mono. **Weight 700 ("exceptional" per the approved weight model) is not loaded at all** — nothing currently needs it, and loading an unused weight is pure waste.
- Verified for real: `npm run build` succeeded, which is only possible if Next.js could actually resolve every requested family+weight+subset combination against Google's font catalog — this is a genuine build-time check, not an assumption.
- Each loader outputs only its raw CSS variable (`--font-display-loaded` etc., applied via `className` on `<html>`); the semantic tokens (`--font-display`, `--font-reading`, `--font-mono-functional`) are composed in `typography.css` with a generic system-font fallback chain appended, matching the pattern already used throughout the token layer (e.g. `color-focus`'s aliasing).

## Type-Role Implementation

All eleven approved roles, each a `.type-*` CSS class (independent of HTML tag — see **Semantic Heading Independence** below), plus one cross-cutting `.type-mono` utility:

| Role | Voice | Size behavior (`clamp()`, 400px→1600px viewport) | Weight | Line height | Tracking | Case |
|---|---|---|---|---|---|---|
| Display | Display | `clamp(4.5rem, 3.5rem + 4vw, 7.5rem)` — 72→120px | 600 | 1.05 | -0.02em | none |
| H1 | Display | `clamp(2.75rem, 2.17rem + 2.33vw, 4.5rem)` — 44→72px | 600 | 1.1 | -0.015em | none |
| H2 | Display | `clamp(2rem, 1.67rem + 1.33vw, 3rem)` — 32→48px | 500 | 1.15 | -0.01em | none |
| H3 | Display | `clamp(1.375rem, 1.17rem + 0.83vw, 2rem)` — 22→32px | 500 | 1.2 | normal | none |
| Body Large | Reading | `clamp(1.25rem, 1.17rem + 0.33vw, 1.5rem)` — 20→24px | 400 | 1.5 | normal | none |
| Body | Reading | `clamp(1rem, 0.96rem + 0.17vw, 1.125rem)` — 16→18px | 400 | 1.6 | normal | none |
| Body Small | Reading | `clamp(0.875rem, 0.83rem + 0.17vw, 1rem)` — 14→16px | 400 | 1.5 | normal | none |
| Caption | Reading | `clamp(0.8125rem, 0.79rem + 0.08vw, 0.875rem)` — 13→14px | 400 | 1.4 | 0.01em | none |
| Metadata | Reading | `clamp(0.75rem, 0.73rem + 0.08vw, 0.8125rem)` — 12→13px | 400 | 1.4 | 0.02em | none |
| Annotation | Reading | `clamp(0.75rem, 0.71rem + 0.17vw, 0.875rem)` — 12→14px | 400 | 1.4 | 0.01em | none |
| Label | Reading | `clamp(0.8125rem, 0.77rem + 0.17vw, 0.9375rem)` — 13→15px | 500 | 1.3 | 0.02em | none |
| *(Mono, cross-cutting)* | Functional Mono | inherits (`1em`, sizes to context) | 400 | inherits | normal | none |

Every `clamp()` triple was derived by solving the linear-interpolation formula between viewport widths 400px (narrow-mobile floor) and 1600px (the platform's own approved `--composition-max`, `grid.css` §9.2) so that each role hits its exact approved range **minimum** at 400px and exact approved **maximum** at 1600px by construction — not a guessed midpoint, not a modular scale. The 1600px anchor deliberately reuses the platform's own already-approved wide-composition boundary rather than an arbitrary number, and every role interpolates against the *same* window, so all roles sit at the same relative position in their own range at any given viewport width — hierarchy is preserved proportionally rather than jumping at breakpoints (satisfies "hierarchy should respond to semantic authority," not mechanical uniform scaling).

**Voice-to-role mapping rationale:** Display/H1/H2/H3 all use the Display Voice — the Design System frames Display Voice's purpose as covering "major titles... threshold moments... major record anchors," which spans the full heading range, not just the single largest size. Body Large through Label all use the Reading Voice — all are body/interface/metadata text, not authored titles. Functional Mono is **not** bound to any single size role — per §7.3/§91 it's applied narrowly at content level wherever fixed-width notation genuinely helps (IDs, versions, coordinates), which the Design System explicitly frames as cutting across roles, not owning one.

**Weight discipline:** only 400, 500, and 600 are used anywhere (the approved model); 700 is not assigned to any role and is not loaded, kept "exceptional" and available only if a future genuine need arises — consistent with "no broader 100–900 variation merely because a variable font supports it."

**Case:** every role leaves `text-transform` at the browser default (mixed/sentence case). None was forced to uppercase — Metadata, Annotation, and Label were specifically checked against the task's own warning not to turn them into "universal uppercase architectural-magazine styling," and none is.
