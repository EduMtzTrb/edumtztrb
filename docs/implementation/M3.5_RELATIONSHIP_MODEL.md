## Starting-state audit

M3.1's `CanonicalRecordBase.relationships?: CanonicalRelationshipReference[]` (`CanonicalRecord.ts`) already stores `targetId` and `type` (and optional `priority`) per relationship, with the containing record's own `id` implicitly serving as source. M3.1's `registry.ts` already provides `assertRelationshipsResolve`, rejecting any relationship whose target isn't present in a given record set. M3.1's own fixtures (`fixtures.ts`) already reproduce IA §5.4's exact directional example chain (Research → `tested-in` → Lab → `developed-into` → Work, Lab → `commercialized-as` → Product, Art → `commercialized-as` → Product, Work → `informed-by` → Research) — no new fixture data was required for this package. What did **not** yet exist: canonical-destination *route* resolution (M3.3 didn't exist at M3.1's time), self-relationship rejection, duplicate-edge rejection, and any visible-label derivation (M3.1's own report explicitly deferred label derivation to "whatever later package renders it — M3.5").

## Reconciliation with M3.1's existing relationship references

This package does **not** introduce a second relationship system. `src/domain/records/RelationshipModel.ts` is additive only — it imports and operates on M3.1's existing `CanonicalRelationshipReference`/`CanonicalRelationshipType` types unchanged, and it reuses (never duplicates) M3.1's `assertRelationshipsResolve` for the "every relationship resolves" Gate criterion. The smallest addition needed to complete M3.5's exact scope on top of the existing structure was: self/duplicate-edge rejection (`validateRelationships`), canonical-route resolution (`resolveRelationship`, composing M3.1's registry with M3.3's `resolveCanonicalRoute`), and derived visible labels in both directions (`deriveRelationshipLabel`). `CanonicalRecord.ts` and `registry.ts` are both byte-for-byte unchanged.

## Architecture

One new module, `RelationshipModel.ts`, providing exactly five capabilities (this task's own §A18: "implement only what M3.5 genuinely needs... do not build a full graph database abstraction"):

- `deriveRelationshipLabel(type, direction)` — pure label derivation.
- `validateRelationships(record, registry)` — self-loop, unresolved-target, and duplicate-edge rejection.
- `resolveRelationship(record, relationship, registry)` — full resolution into target route + label.
- `listOutgoingRelationships(record)` — trivial accessor.
- `listIncomingRelationships(targetId, records)` — derived reverse-edge scan, no persisted inverse.

## Six-type ontology

Unchanged from M3.1: `related-to`, `derived-from`, `informed-by`, `tested-in`, `developed-into`, `commercialized-as`. No seventh type was added, confirmed at the source level (`relationship-model-source-contract.test.ts`: "declares exactly the six approved stored relationship types, no more") and behaviorally (every fixture relationship checked against the approved set). Richer editorial phrasing used across the Universe/Cross-Universe documents (Developed From, Applied In, Tested Through, Reframed By, Generated By, etc.) is **not** treated as additional stored types — it becomes derived label *text* only (see "Visible label" below), exactly matching IA §5.3's "the vocabulary is intentionally small."

## Source / destination model

Source is implicit: the containing record's own `id`. Destination is `targetId`, unchanged from M3.1. No redundant `source` field was added to `CanonicalRelationshipReference` — the stored source→destination orientation (a relationship living inside the source record's own `relationships` array) already provides this unambiguously, matching this task's own guidance ("do not add redundant direction data unless the architecture genuinely requires it").

## Direction

The array-membership orientation (which record's `relationships` array holds the edge) provides direction; no separate `direction` field exists. `resolveRelationship`'s `sourceId`/`targetId` pair on its return value makes the direction explicit in any resolved output without needing to store it a second time on the input structure.

## Visible label

`deriveRelationshipLabel(type, direction)` returns a label string per stored type, in both the forward and reverse direction — derived, never stored (IA §5.4: "the displayed reciprocal wording may be adapted to context without changing the stored relationship"). Forward labels stay close to the stored type name (`"tested-in"` → "Tested in"); reverse labels draw on the richer editorial vocabulary the Universe/Cross-Universe documents already use for the *same* semantic edges (e.g. Research Universe §9's own "Reframed by"/"Generated by" family informs the reverse wording for `informed-by`/`tested-in`) — mapped onto the existing six-type ontology, never expanding it. A future presentation layer may further adapt wording by context (per IA §5.4) without requiring any change to this module.

## Canonical-destination resolution

`resolveRelationship` composes: `targetId` → target record (via a caller-supplied registry, typically M3.1's `createRecordRegistry`) → canonical route (via M3.3's `resolveCanonicalRoute`, imported directly, never duplicated). No route string is ever persisted on the relationship reference itself — it is resolved fresh every time, confirmed at the source level (`relationship-model-source-contract.test.ts`: "never copies a route literal into stored relationship data"). Tested directly: `Lab → developed-into → Work` resolves to `/work/fixture-work-outcome`, matching M3.3's own resolution for that fixture exactly.

## Broken-edge validation

`validateRelationships` rejects an unresolved target (a relationship whose `targetId` is not present in the supplied registry), returning a structured issue rather than silently omitting the link, fabricating a target, or substituting generic related content — exactly this task's own explicit instruction. This complements, and does not replace, M3.1's own throwing `assertRelationshipsResolve`, which remains the mechanism behind Gate M3's "every relationship resolves" criterion.

## Duplicate/self-edge handling

- **Self-relationships** — `validateRelationships` rejects `targetId === record.id` by default; no case was found anywhere in current authority (IA §5, Cross-Universe §7) describing a legitimate self-referential canonical relationship, so the default rejection stands without an exception.
- **Duplicate relationships** — defined precisely: a duplicate is the same `(destination, stored type)` pair appearing more than once on one source record's `relationships` array. Two *distinct* stored types to the same destination (e.g. both `informed-by` and `related-to` from Work to the same Research record) are explicitly **not** duplicates — tested directly, matching this task's own note that "two genuinely distinct public labels for one stored semantic edge" is an editorial concern, not this validator's to prevent (and is, in any case, a different scenario from two stored types to the same target, which this validator correctly permits).

## Reciprocal display

`listIncomingRelationships(targetId, records)` scans a record set's outgoing relationships and derives every incoming edge for `targetId`, each carrying the reverse-direction label — proven directly: Lab's incoming relationships include Research's `tested-in` edge, while the Lab fixture itself carries no separately stored inverse edge back to Research. This is the concrete mechanism behind IA §5.2's "the system may derive a reciprocal display from a stored directional relationship... a separately authored reverse relationship is not required." Where a genuinely independent reverse edge *is* intentionally authored (Work's own `informed-by` edge back to Research, alongside Research's `tested-in` edge to Lab — both present in the fixture set from M3.1), both coexist without conflict, tested directly.

## Relationship priority

`priority` (M3.1) is passed through unchanged by `resolveRelationship` and `listIncomingRelationships`; nothing in this module reads or interprets it beyond forwarding the stored value. Tested directly that a prioritized relationship leaves owner district and resolved route completely unaffected — no ranking infrastructure was built (this task's own explicit instruction).

## Ownership invariance

Resolving, validating, or listing relationships never mutates `ownerDistrict` on either the source or the target record — confirmed structurally (`relationship-model-source-contract.test.ts`: no assignment to `ownerDistrict` anywhere in the module) and behaviorally (Research→Lab, Lab→Work, Art→Products all tested to leave both records' owner districts untouched after resolution).

## District-transfer rules

- **Research ↔ Lab (cyclical)** — both directions are legitimate independently-authored edges; tested that Research's own `tested-in` edge exists without requiring Lab to mirror it, matching `CUR-TRN-04`'s "must support both directions without implying a mandatory linear pipeline."
- **Lab → Work** — tested that resolving the `developed-into` relationship leaves the Lab fixture's own `lifecycle: "failed"` and identity completely unchanged, matching `CUR-TRN-05`'s "the Lab record remains available... experimental uncertainty is not rewritten as resolved history."
- **Art → Products** — tested that resolving `commercialized-as` leaves Art `ownerDistrict: "art"` and confirms the target is `ownerDistrict: "products"`, matching `CUR-TRN-07`'s "Art owns the artwork and encounter. Products owns... transaction."

## Attribution boundary

`Authorship`/`AttributionEntry` (M3.1) remain completely outside the relationship ontology — no relationship reference in any fixture carries a `role` or attribution-shaped field, tested directly. This module never imports or touches `Authorship` at all, matching IA §5.6: "authorship, role, collaboration, client, institution, and contributor information are attribution metadata, not project-lineage relationships."

## Classification boundary

`RelationshipModel.ts` never imports `ClassificationModel.ts` (confirmed at the source level) and shared classification (e.g. two records with an overlapping discipline term) never produces an automatically-generated relationship — tested directly by confirming a record's relationship count is unaffected by adding a `disciplines` reference. This directly satisfies IA's implicit boundary and this task's explicit "no `sameTheme -> related-to` automation."

## Visual relationship boundary

No CSS, no Trace/Signal code, no `className`, no rendering of any kind exists in this module — confirmed at the source level. This package produces the semantic *data* (`ResolvedRelationship`, `IncomingRelationship`) that `IMPLEMENTATION_PLAN.md`'s own words require: "visual relationships may only represent semantic relationships present in data." A later visual implementation is exactly the "later package" this module's output is prepared for, not something this package attempts.

## Search/Index boundary

No Search ranking, no Index query logic exists anywhere in this module (confirmed at the source level: no `search`/`buildIndex`/`rankResults` function names). Public-discovery eligibility remains entirely M3.1's own concern (`isPubliclyDiscoverable`/`isDirectlyAccessible`, `registry.ts`, untouched) — this module exposes relationship data a future Search/Index implementation may consume, never implementing that consumption itself.

## Serialization

`ResolvedRelationship` and `IncomingRelationship` are both plain, JSON-serializable shapes — round-tripped directly in tests. No relationship reference anywhere embeds a target record object (`hasOwnProperty(relationship, "target") === false`, tested directly) — only `targetId` (a plain string) is ever stored, consistent with M3.1's own "resolved records and open relationships" principle (IA §5.1).
