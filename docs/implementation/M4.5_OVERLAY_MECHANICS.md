## Starting-state audit

No overlay/modal implementation existed anywhere in the repository before this package (M2.8's own report explicitly notes "no overlay/focus-layer system built — Artwork Viewer is a shell only"). `src/components/overlay/` did not exist.

## Native `<dialog>` audit — a documented, deliberate choice against it

`ANIMATION_SYSTEM.md`'s "prefer native/platform behavior when reliable" (§B3) was taken seriously: `<dialog>` + `showModal()` was evaluated first, since real evergreen browsers support its focus-containment, `::backdrop`, and Escape-to-cancel natively. It was **not** chosen, for one concrete, verified reason: this repository's own test environment does not implement it at all. A direct probe (`dialog.showModal is not a function`, `dialog.close is not a function` against jsdom 29.1.1, this project's actual Vitest environment) confirmed neither method exists. Building the mechanism on an API this repository's own tooling cannot exercise would mean the modal's entire focus-containment/close/Escape behavior could only ever be "trust me" — directly contrary to this project's established "mechanically verified" discipline, which every other M1–M4 package has satisfied with real, running tests.

**Chosen instead:** the WAI-ARIA Dialog (Modal) Pattern — `role="dialog"`, `aria-modal="true"`, an explicit accessible name — with a hand-written, fully tested Tab/Shift+Tab containment loop, Escape handler, and focus-return. This is universally supported (it has been the standard accessible-modal implementation technique for over a decade, predating and remaining valid alongside `<dialog>`), and every single behavioral claim below is backed by a real, running test rather than an assumption about platform behavior this project cannot verify. This audit and its conclusion are exactly what `IMPLEMENTATION_PLAN.md` §9/this task's own §B3 asked for — "audit browser support before choosing... architecture" — rather than picking either option by default.

## Overlay is not a destination

`src/components/overlay/Overlay.tsx` never imports `next/navigation`, calls no router, never touches `window.location` or `history`, and never references a canonical-record or route-resolver module — confirmed directly and by source contract (`tests/tokens/overlay-contract.test.ts`). Opening or closing it is pure in-page state; it creates no fake district, no duplicate canonical record, no route IA does not define. A `RouteResolver`/`ClassificationModel`/domain import would itself be a structural violation of this boundary — none exists.

## Composes M4.4 — no second recession mechanism

`src/components/overlay/useOverlayBackgroundProps.ts` is the entire composition point this task required ("overlay entry must compose M4.4's Focus + Recession mechanism... do not build independent CSS physics"): it returns the exact same `data-focus-state` attribute `focus.css` (M4.4) already styles (`"neutral"` closed, `"receding"` open) — zero new CSS rule for recession exists in `overlay.css` (confirmed by source contract: `overlay.css` declares no `transition` of its own; the only motion applied to a receding background is `focus.css`'s pre-existing rule). It additionally returns the native `inert` attribute (`true` while open, `undefined` closed) — the real interaction-prevention mechanism, returned together with the visual recession signal deliberately, since a background that looks quieted but is still reachable, or one that is inert with no visual cue why, would each be an incomplete signal on their own.

## Modal semantics

The panel carries `role="dialog"`, `aria-modal="true"`, and `aria-label={label}` — a real accessible name is required by the `OverlayProps` type, not optional. It reuses M2.4's existing `.plane` + `.frame` primitives for its visual surface (confirmed by source contract — no new surface/border/radius value is invented anywhere in `overlay.css`) rather than building a fourth content-surface treatment; `overlay.css` owns positioning only (fixed backdrop/content layer, panel max-extent/scroll).

## Explicit close

A real, always-visible `<button>` labeled `Close {label}` sits inside the panel — never conditional on hover, never the only way to dismiss (confirmed alongside Escape and, in the fixture, the origin-trigger toggle). It uses the existing `.action-tertiary` CSS class directly (not the `Action` component itself — `Action` is a plain function component without ref-forwarding support, and this package needed a real DOM ref to move initial focus onto the close control; rather than modify M2.5's already-Complete/Verified component to add ref support for one new caller, the smaller, non-invasive choice was a plain `<button>` carrying the identical class, producing an identical visual result with zero change to M2.5).

## Escape

A `keydown` listener (active only while the panel is mounted) closes on `Escape`, calling the same `onClose` the visible Close button calls — one exit path, two triggers, deterministic either way (tested directly).

## Focus containment

On open, DOM focus moves to the Close button — the same "establish a meaningful focus target" principle M4.4 already used, applied here because a genuinely modal presentation (unlike M4.4's non-modal Focus) really does need focus to move somewhere new. From there, Tab and Shift+Tab are intercepted: the trap computes the panel's real focusable elements fresh on every keypress (never a stale cached list), and wraps forward from the last element back to the first, and backward from the first element to the last — including the case where focus has somehow landed *outside* the panel (treated identically to "at the boundary," pulling it back in). Tested directly in both directions (`Overlay.test.tsx`), including a scenario with a real second component's own button already focused outside the overlay before Tab is pressed, proving focus cannot escape into the underlying page while modal.

## Focus return

On close, focus returns to, in order: the explicit `origin` prop if supplied and still mounted (`document.contains` checked live — never a detached-node `.focus()` call); otherwise whatever had focus immediately before the overlay opened, under the same live-mount check; otherwise nothing is forced. Never an arbitrary `<body>` focus. Both paths are tested directly, including the fallback case with no `origin` prop supplied at all.

## Origin references — same-document only

`OverlayProps.origin` is typed `HTMLElement | null` — a live, same-document reference, exactly the boundary `FocusRegion`'s own `origin` field already established in M4.4. Its doc comment states explicitly that cross-route origin persistence is M4.6's separate concern; this package does not serialize or store anything beyond the current mount.

## Background interaction prevention

`useOverlayBackgroundProps`'s `inert` value is the real mechanism: a background region carrying `inert` cannot receive pointer activation, cannot be tabbed into, and is excluded from the accessibility tree while true — combined with the explicit focus trap above (which independently also prevents focus from landing there even if a consumer forgot to apply `inert`), background interaction is prevented at two redundant layers, not one. The DOM is never removed to fake this — the background stays visually present (receded, not hidden), satisfying "clear relation to the underlying page."

## Preserved underlying context / scroll

Opening the overlay sets `document.body.style.overflow = "hidden"`, capturing whatever the prior inline value was and restoring it exactly on close (tested directly, including a non-empty prior value). The overlay panel itself scrolls independently (`overflow: auto` in `overlay.css`) so long content inside the overlay is not blocked by the body-level lock. No global scroll-restoration behavior was touched, and no `history.scrollRestoration` was set — native scrolling elsewhere on the page is otherwise untouched.

## Reduced background motion

No environmental/ambient motion exists anywhere in the repository to suspend (confirmed repeatedly since M4.1). `useOverlayBackgroundProps`'s `data-focus-state="receding"` value is itself the "reduced background presence" signal — reusing M4.2's already-established reduced-motion collapse (the same `globals.css` rule M4.3/M4.4 already rely on) for the transition's *duration*, without this package needing a second mechanism. M4.2's `shouldRunEnvironmentalMotion()` contract was deliberately **not** extended with an "overlay open" parameter here: no environmental-motion consumer exists yet to pass it to, and this task's own instruction is explicit ("use M4.2's capability contract so future environment layers have one path for suspension... do not invent one now") — this is documented as the exact signal a future environmental-motion consumer would combine with `shouldRunEnvironmentalMotion()`, not something M4.5 needs to build today.

## No `--layer-*` token invented

`overlay.css` needed a real `z-index` (the first genuine consumer in the repository that does) but does not invent the six-token layer-order model `DESIGN_SYSTEM.md v1.1` §99 approves only in name — `PROJECT_STATE.md`'s own Blockers entry leaves those numeric values implementation-calibrated by whichever package first needs one, and resolving all six is a larger, separate calibration this package does not attempt. Instead, `overlay.css` reuses `shell.css`'s own existing precedent (a plain literal `z-index: 100` on the persistent header) and sets `200` — one step above it, the smallest change that reliably keeps an open overlay above the header, documented in the CSS file itself as not resolving the broader model.

## Reconciled — one M4-A test, same pattern M4.4 already used

`focus.css`, `FocusRegion.tsx`, `FocusItem.tsx`, `motion.css`, `capability.ts`, `cancellation.ts` are all confirmed unchanged. `overlay.css`'s backdrop rule reuses `--motion-recession-overlay` (no new token), which extended `tests/integration/m4a-motion-foundation-journeys.test.tsx`'s Journey 4 permitted-consumer list to include `overlay.css` alongside the `focus.css` addition M4.4 already made there — the identical reconciliation discipline, applied a second time to the same test as new, authorized motion-token consumers are added package by package.

## Browser-only behavior requiring human confirmation

The Tab/Shift+Tab trap, Escape handling, and focus-return are all mechanically proven with real (simulated) keyboard events in jsdom. What jsdom cannot confirm — and what the M4-B integrated human review should specifically check — is the *visual* experience: whether the backdrop/recession genuinely reads as "background, not gone," whether the panel remains legible and reachable at 390px, and whether the close/Escape/reduced-motion behavior feels correct in a real browser and with real assistive technology, not just correct by assertion.

## Acceptance result

A single Overlay component provides explicit close, Escape, mechanically proven modal focus containment and return, and background-interaction prevention, composing M4.4's Focus + Recession for its background treatment rather than duplicating it, and reusing M2.4's Plane/Frame for its own surface rather than inventing a new one — satisfying `IMPLEMENTATION_PLAN.md` §9's exact M4.5 wording. **M4.5 — Overlay Mechanics: Implemented / Mechanically Verified — awaiting M4-B integrated human review.**
